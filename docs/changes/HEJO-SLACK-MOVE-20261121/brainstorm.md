# HEJO-SLACK-MOVE 브레인스토밍 결정 요약

- 날짜: 2026-11-21. 상태: 사용자 결정 완료, 계획 단계로 넘김.
- 진행 방식: 연합개발, 계획 검증 켜기(사용자 선택 2026-11-21).
- 근간: [ARCHITECTURE.md](../../ARCHITECTURE.md) 7절 3번 "Slack 은퇴" 단계에 해당한다.

## 목적

모든 알림·보고·대화가 Slack 대신 hejo로 온다. Slack 문은 켜 두되 아무것도 보내지 않는 비상 통로로 남긴다.

게이트웨이는 바꾸지 않는다. 같은 게이트웨이에 Slack 문과 hejo 문이 함께 열려 있고, 보고가 Slack 문으로 나가도록 적힌 곳을 hejo 문으로 바꾼다.

## 하는 것 · 하지 않는 것

하는 것

- 직원이 듣는 Slack 채널 5개를 같은 이름의 hejo 방으로 만든다.
- 예약 보고가 방으로 갈 수 있게 hejo 문에 방 대상을 추가한다.
- 예약 보고와 시스템 알림의 받을 곳을 hejo로 바꾼다.
- Slack을 직접 부르는 team-kit 스크립트와 Slack 전용 규칙을 hejo에서도 동작하게 한다.
- 한 번에 전환한다.

하지 않는 것

- 과거 Slack 대화 이관(HEJO-FOUNDATION 결정 유지).
- Slack 문 끄기, Slack 전용 코드 삭제.
- 직원이 듣지 않는 나머지 Slack 채널.
- hejo 방에 사람 초대.
- Hermes 본체 수정.

## 실측 (2026-11-21, 서버 읽기 전용 확인)

- [확인] hejo 문은 게이트웨이에 연결돼 있고 모든 직원 프로필이 hejo로 1:1 대화를 받는다(`gateway_state.json`).
- [확인] hejo 방이 이미 2개 있다(문 기록장).
- [확인] 켜진 예약 보고 중 11개가 Slack 채널 2곳으로 간다. 한 곳은 직원 2명이 7개, 다른 한 곳은 직원 1명이 4개를 보낸다(각 프로필 `cron/jobs.json`, `owner/policy.yaml`의 `schedule_bindings`).
- [확인] 시스템 알림(재시작·온라인)은 Slack의 직원 DM 한 곳으로 간다(`config.yaml` `gateway.system_notifications`).
- [확인] Slack 목록의 단체 채널은 15개, 직원이 듣도록 허용된 채널은 5개, 보고 채널은 2개다(`channel_directory.json`, `config.yaml` `platforms.slack`).
- [확인] hejo 문의 보고 대상 문법은 직원 id뿐이다. 방은 대상이 될 수 없다(`gate/__init__.py` `parse_target`).
- [확인] hejo 방은 직원 2명 이상과 대표 직원이 있어야 한다(`gate/rooms.py` `room_command`).
- [확인] 운영 저장소의 team-kit과 직원 스크립트 약 34개 파일이 Slack API를 직접 언급한다. 쓰기인지 읽기인지는 계획 단계에서 파일별로 확인한다.
- [확인] team-kit에 플랫폼이 Slack일 때만 동작하는 규칙이 여러 곳 있다(안내원, 프로젝트 스레드, 대기 작업, 금고 백업 승인, 사용량 꼬리말 등).
- [미확정] 설정에 hejo용 도구 묶음 키가 없다. hejo 세션이 받는 도구 묶음이 Slack과 같은지 확인하지 못했다.

## 선행 조사

생략한다. 자체 문과 자체 team-kit 사이의 배선 변경이라 채택할 외부 제품이 없다.

## 대안과 선택

| 항목 | 선택 | 기각 |
|---|---|---|
| Slack 끝 상태 | 연결만 남기고 비움 | 완전히 끔(비상 통로 없음), 일부만 Slack 유지 |
| 방 범위 | 직원이 듣는 5개 | 보고 가는 2개만, 15개 전부 |

## 가정

사용자 결정

- Slack 채널은 사장 혼자 본다. 다른 사람이 없다.
- Slack 연결은 남기고 비운다. 방은 5개. 한 번에 전환한다.

에이전트 제안(계획 단계에서 확인)

- 방 이름은 Slack 채널 이름 그대로, 방 구성원은 그 채널에 글을 쓰던 직원으로 한다.

## 추가 실측과 결정 (2026-11-21, 계획 단계 첫 조사)

추가 실측

- [확인] 직원이 듣는 채널 5개는 모두 직원 4~5명이 설정돼 있어 방 규칙(2명 이상)에 맞는다.
- [확인] 직원 1명이 예약 보고 4개를 보내는 시스템 채널은 그 5개 밖에 있다.
- [확인] hejo 문이 여는 입구는 앱 연결·첨부·사진뿐이다. 게이트웨이 밖 프로그램이 글을 올릴 입구가 없다(`gate/server.py`의 경로 등록).
- [조사 보고, 계획에서 핵심 줄 재확인] 운영 저장소에서 게이트웨이를 거치지 않고 Slack에 직접 쓰는 파일은 약 28개이고 hejo 분기는 없다. 16개는 team-kit의 공통 전송 함수 하나로 모이고, 독립 전송 경로는 7곳이다. 받을 곳 값은 Slack 채널 id 형식으로 검증된다. 실행 주체에 상주 프로그램이 여럿 있다.
- [조사 보고, 계획에서 재확인] hejo 이벤트는 team-kit 안내원을 타지 않고 문이 답할 직원을 정한다(`gate/rooms.py` `recipients`). 예약 관리 도구와 진단 사용량 조회는 hejo에서 막혀 있고, 금고 백업 승인 답장 처리·일 넘기기는 hejo에서 건너뛴다.
- [조사 보고] 시스템 알림은 Hermes 본체가 지정 플랫폼 어댑터의 `send`를 부르는 구조라 설정만 바꿔도 hejo로 간다. 재시작 알림을 지우는 기능은 본체 안에서 Slack 전용이다.
- [미실행] hejo 세션의 실제 도구 목록. 코드상으로는 설정에 hejo용 목록이 없어 Hermes 기본 묶음을 받는다.

사용자 결정

| 항목 | 결정 |
|---|---|
| 시스템 채널의 보고 | 그 보고를 보내는 직원과의 1:1로 받는다. 방 규칙은 그대로 둔다 |
| 게이트웨이 밖 프로그램의 전송 | hejo 문에 서버 안에서만 쓰는 글 올리기 입구를 만들고 team-kit 공통 전송 함수가 그 입구를 쓴다 |
| 옮길 Slack 전용 규칙 | 일 넘기기(프로젝트 허브), 스레드 주인 유지, 재시작 알림 자동 지우기. hejo에서 막힌 예약 관리 도구·금고 백업 승인·진단 사용량 조회도 옮긴다 |
| 옮기지 않는 규칙 | 낱말로 직원 부르기(hejo는 `@이름`만), 사용량 꼬리말(2026-11-17 결정 유지), 공개 채널 자동 가입(Slack 전용) |
| 도구 묶음 | 직원마다 hejo 도구 목록을 지금 Slack 목록과 같게 맞춘다 |

## 열린 질문

1. 재시작 알림 자동 지우기는 Hermes 본체 안의 Slack 전용 코드다. 본체는 고치지 않으므로 문 쪽에서 같은 결과를 내는 방법을 설계에서 정한다. 방법이 없으면 멈추고 보고한다.
2. 서버 안 전용 입구의 인증 방식(누가 어느 직원 이름으로 올릴 수 있는가)을 설계에서 정한다.
3. 대기 작업 결과를 방으로 보낼 때 대기를 만든 직원 이름으로 올라가는지 확인한다.

## 위험도 1차 판단

고위험. 운영 서버 설정 변경과 게이트웨이 재시작이 들어가고, 한 번에 전환이라 빠진 스크립트가 있으면 그 보고가 조용히 사라진다. 전환 전 받을 곳 전수 목록과 롤백 절차가 필요하다. 저장소 두 곳(hejo, 운영 저장소)에 걸친다.
