## 2. 단계

### 1단계: 준비와 되돌리기 예행(운영 변경 없음)

1. 이 작업이 바꾼 운영 저장소 파일 목록을 만든다(`git diff --name-only <착수 기준>..fcdec420`, 시험·fixture 제외). 파일마다 실행본의 sha256이 작업 브랜치의 변경 전 기준(운영 main의 그 파일)과 같은지 확인한다. 다르면 그 파일의 차이를 읽고, 이 작업과 무관한 다른 변경이면 작업 브랜치를 최신 운영 main 위로 올려(병합 충돌이 없을 때만) 다시 시험한 뒤 진행한다. 충돌이 있거나 판단이 서지 않으면 멈추고 보고한다.
2. 최신 운영 main과 합친 상태에서 team-kit 시험 묶음(verdict 6차의 49개 파일)과 인스타·네이버톡 격리 시험을 다시 돌린다. 종료 0이 아니면 멈춘다.
3. M7: 임시 홈에서 design 7절의 되돌리기 절차를 끝까지 한 번 실행하고 기록한다(보관 → `hejo`로 바꿈 → 되돌림 → 복원 파일 sha256 일치, 스위치를 읽는 함수의 답이 `slack`).
4. 네이버톡 사건 표가 바뀐다(열 3개 추가). 임시 홈에 지금 운영 표의 **모양만** 본뜬 빈 표로 옛 코드가 새 열이 있는 표를 읽고 쓰는지 확인한다(운영 표의 내용은 읽지 않는다).

### 2단계: 코드 적용(동작 불변)

절차의 틀은 HEJO-CONNECTIONS design 7.2다. 적용 전에 되돌리기 기록을 impl-report에 먼저 쓴다(명령마다 대상·커밋·sha256, 빈 칸 없음. 실제 경로는 이 저장소 밖 기록 파일에).

1. 한가한 때 확인: 진행 중 직원 턴 0(기존 재시작의 BUSY 검사), 인스타·네이버톡의 진행 중 외부 전송 0.
2. 보관: 바꿀 실행본 파일 전부와 네이버톡 사건 표 파일을 0700 임시 폴더에 복사하고 sha256을 적는다. 문은 공용 릴리스의 `RELEASE` 커밋을 적는다.
3. 상주 프로그램 잠시 멈춤: 인스타 감시와 네이버톡 다리처럼 바뀌는 파일을 읽는 상주·타이머 프로그램을 멈춘다(목록 기록). 실행 중 프로세스 0을 확인한다.
4. 교체: team-kit, 고객 응대 직원 플러그인, 네이버톡 다리, 그 밖에 바뀐 실행 파일을 임시 파일에 쓴 뒤 이름 바꾸기로 교체한다.
5. 문: 이 저장소의 기준 커밋으로 `install/hejo-release` → 게이트웨이 전체 재시작(운영 저장소 AGENTS의 재시작 규칙).
6. 확인(하나라도 실패하면 7번으로)
   - 게이트웨이 로그에 Slack 연결 전부와 iMessage, hejo 문이 다시 연결됨. 오류 로그에 재시작 뒤 새 줄 없음. 새 프로세스 시작 시각이 교체한 파일의 수정 시각보다 뒤.
   - 입구 소켓 파일이 있고 권한이 0600. 입구에는 **읽기 요청 하나만** 보낸다. 글을 올리지 않는다. 요청은 정확히 이것이다(2판, 구현 검토 7차): `GET /local/v1/threads/<방금 만든 무작위 UUID>?room=<방금 만든 다른 무작위 UUID>`. 쿼리에 `employee`를 함께 넣지 않는다(규격은 둘 중 하나만 받는다). 기대 응답은 HTTP 400과 오류 이름 `room_not_found`다([확인] `gate/local.py`의 스레드 읽기, 구현 담당의 격리 재현). 받은 HTTP 상태와 오류 이름을 **판정하기 전에** 기록 파일에 적는다. 기대와 다르면 실패다.
   - 스위치를 읽는 함수의 답이 `slack`.
   - `hermes-connections status --json`과 `apps --json` 성공.
   - 3번에서 멈춘 프로그램을 다시 띄우고 한 차례 정상 종료(또는 정상 대기)를 확인. 네이버톡 사건 표에 새 열 3개가 생겼고 기존 행 수가 보관본과 같음.
   - Slack에 시험 글을 보내지 않는다. 다음에 저절로 나가는 보고(예: 인스타 매시 요약)가 Slack에 평소대로 올라왔는지 기록 파일의 시각으로 확인한다. 한 시간 안에 확인하지 못하면 "미확인"으로 적고 반환한다.
7. 되돌리기(복구 조건: 6번의 어느 확인이든 실패): 프로그램 멈춤 → 보관본 복원(sha256 일치 확인, 네이버톡 표 포함) → 기록한 `RELEASE` 커밋으로 `install/hejo-release` → 재시작 → 6번 확인을 다시 → 멈추고 보고.
8. 성공하면 운영 저장소에서 `./sync` → `./airport-check` → 작업 브랜치의 변경이 운영 main에 반영되게 커밋한다(`git commit --only`로 자기 경로만, `./sync`가 토큰 경고를 내면 커밋하지 않고 보고). 임시 worktree는 지우지 않는다.

### 3단계: 전환 준비물(운영 변경 없음)

모두 이 저장소 밖 파일에 만든다. 보고에는 경로와 줄 수, 빈 칸 수만 적는다.

1. **방 표**(M1): 직원이 듣는 Slack 채널 5개마다 방 이름(Slack 채널 이름과 같게), 구성원(그 채널을 듣는 직원), 대표 직원 **제안**(근거 한 줄). 구성원이 2명 미만인 채널이 있으면 표시한다. 이미 같은 이름의 hejo 방이 있으면 구성원·대표 직원 비교 결과를 적는다(읽기만).
2. **받을 곳 전수 대조표**(M1): design 4.2 표와 impl-report TASK-06 대조표의 줄마다 보내는 것, 지금 Slack 받을 곳의 직책 키, hejo 받을 곳(방 또는 직원 1:1), 금고 `hejo.*` 키 이름, 확인 방법. 빈 칸이 없어야 한다. 아래 세 줄을 따로 넣는다.
   - 일 넘기기(프로젝트 허브): Slack 허브 채널에 남음.
   - 위키 일일 보고와 금고 백업 승인: Slack에 남음(`vault_backup`).
   - 사장의 Slack 대화에 답하는 도구(파일 올리기, 보고 상태 고치기): Slack에 남음(`slack_session`).
3. **예약 보고 목록**: 프로필마다 `cron/jobs.json`에서 받을 곳이 Slack인 예약의 수와 hejo로 바꿀 값(읽기만). 공개 채널 자동 가입 예약을 표시한다.
4. **시스템 알림 변경안**: design 8절대로 바꿀 `config.yaml` 줄(읽기만).
5. **도구 집합 비교**(M5): 운영 프로필마다 조립기를 **쓰지 않는 방식**(임시 사본에 조립)으로 돌려 hejo·Slack 도구 집합의 차이를 구한다. 차이가 0이 아니면 목록을 적는다.
6. **멈출 프로그램 목록**: 4단계 1번에서 멈출 상주·타이머 프로그램 전부.

3단계까지 마치면 멈추고 결과를 반환한다.

### 4단계: 전환(다음 지시, 사장이 표를 확인하고 자리에 있을 때)

사장 확정(2026-11-22): 방 표는 3단계 초안 그대로 쓰되 **고객 방의 이름만 `flowave`로 바꾼다.** 나머지 네 방의 이름·구성원·대표 직원, 대조표, 시스템 알림 변경안은 초안대로다. 전환은 오늘 바로 하고 사장이 지금 자리에 있다.

먼저 할 일(전환 전)

- 가. 자연 보고 확인: 2단계 재시작 뒤 저절로 나간 보고가 Slack에 올라간 기록이 있는지 다시 읽는다(기록 파일만, 시험 글·강제 실행 없음). 있으면 적는다. 없으면 "미확인"으로 적고 그대로 진행한다(사장이 오늘 바로 하기로 했다. 이 경우 되돌릴 때 Slack 보고가 이상하면 2단계 보관본으로 코드까지 되돌린다).
- 나. 운영 저장소 기록(2단계 8번)은 **미룬다**(4판, 구현 검토 9차). `./airport-check`가 진단 직원의 지시서 조립 불일치 한 건으로 실패한다. 이 불일치는 이 작업의 44개 경로와 무관한 다른 작업의 변경이고([확인] 운영 저장소 커밋 `f86cf350`이 그 지시서에 단락 하나를 직접 넣었다. 지금 파일은 운영 main과 같다) 이 작업이 고칠 것이 아니다. 운영 저장소 작업 트리의 44개 경로는 커밋하지 않은 채 둔다. 전환은 이 커밋을 기다리지 않는다.
- 다. 지시서 조립기(`hermes-soul-assemble`)를 **쓰기로 돌리지 않는다.** 돌리면 그 단락이 지워진다. 5번의 "조립기"는 설정 조립만이다. 전체 조립 명령이 지시서까지 다시 쓰는 구조라면 설정 조립만 따로 부르고, 따로 부를 수 없으면 멈추고 보고한다.

전환(design 7절. 순서를 바꾸지 않는다)

6판에서 달라진 것(구현 검토 11차). 아래 번호 목록보다 이 문단이 우선한다.

- 승인 대기 항목은 멈춤 조건이 아니다(사장 지시 2026-11-22). 2번에서 승인 대기 수는 적기만 한다. 에이전트는 승인·거절 버튼이나 대기 상태를 건드리지 않는다.
- 방 5개는 이미 만들어져 있다(5판 실행). 4번에서는 새로 만들지 않고, 기록된 방 5개의 이름·구성원·대표 직원이 확정 표와 같은지 확인해 그 id를 쓴다. 다르면 프로그램을 다시 띄우고 멈춰 보고한다.
- 보관을 두 번 한다. 3번의 보관은 그대로 하되, **5번에서 게이트웨이를 멈추고 프로세스 0을 확인한 직후 같은 파일들을 한 번 더 보관한다(멈춘 뒤 보관본).** 되돌리기의 기준은 멈춘 뒤 보관본이다. 게이트웨이가 떠 있는 동안 예약 파일의 실행 시각 값은 계속 바뀌므로, 3번 보관본과 예약 파일의 바이트가 다른 것은 실패가 아니다.
- 멈춘 뒤 보관본과 3번 보관본의 비교: 지시서 파일, 금고, `config.yaml`의 내용이 다르면 그 사이 누군가 바꾼 것이므로 쓰지 않고 게이트웨이와 프로그램을 다시 띄운 뒤 멈춰 보고한다. 예약 파일은 실행 상태 값(마지막 실행·다음 실행·갱신 시각 같은 값)만 다르면 정상이다. 그 밖의 필드가 다르면 같은 방식으로 멈춘다.
- 예약 파일은 멈춘 뒤의 최신 내용에서 **받을 곳 필드와 자동 가입 예약의 켜짐 값만** 바꾼다. 실행 상태 값은 그대로 둔다(옛 보관본으로 덮으면 이미 끝난 예약이 다시 나갈 수 있다).
- 어느 단계든 실패하면 되돌리기 전에 그때의 파일 사본을 보관 폴더에 남긴다(무엇이 달랐는지 나중에 볼 수 있게).

1. 멈추기(5판): 3단계 멈출 프로그램 목록의 **상주·타이머 프로그램 15개만** 멈춘다. 게이트웨이는 아직 멈추지 않는다(입구가 게이트웨이 안에 있어 방을 만들려면 떠 있어야 한다. 구현 검토 10차 S-6). 본체의 일시정지 기능은 쓰지 않는다(막는 범위를 확인하지 못했다). 멈춘 목록 기록.
2. 비우기 확인(M2): 진행 중 직원 턴 0, 승인 대기 초안·보고 0, 멈춘 프로그램의 실행 중 프로세스 0, 진행 중 외부 전송 0. 하나라도 남으면 기다린다. 15분을 기다려도 남으면 1번에서 멈춘 것을 다시 띄우고 멈춰 보고한다. 승인 대기 중인 인스타·네이버톡 초안이 있으면 사장에게 Slack에서 먼저 처리해 달라고 보고에 적는다(에이전트가 승인·거절하지 않는다).

6. 켜기: 게이트웨이를 띄운다 → Slack 연결 전부·iMessage·hejo 문 연결, 오류 로그에 새 줄 없음, 입구 확인 요청 하나(2단계 6번과 같은 요청, 기대 400 `room_not_found`), 스위치를 읽는 함수의 답 `hejo`, 방 5개가 기록에 있음 → 그다음에 1번에서 멈춘 프로그램 15개를 다시 띄운다.
7. 확인(M3)
   - 대조표의 hejo 받을 곳마다 **hejo 시험 글 한 줄**을 공통 전송으로 올린다(본문은 "전환 확인"과 받을 곳의 직책 이름만. Slack으로는 아무것도 보내지 않는다). 입구 응답의 글 id를 기록한다.

   - 인스타(M4): 프로그램을 띄운 뒤 감시 한 차례가 오류 없이 끝났는지 로그로 확인한다. 실제 다음 DM이 hejo 고객 방 스레드로 오고 초안이 붙는지는 사장과 함께 본다. **에이전트는 승인·거절 버튼을 누르지 않고 고객에게 글을 보내지 않는다.** DM이 30분 안에 오지 않으면 "미확인(대기)"으로 적고 반환한다. 실패가 아니다.

되돌리기(5판: 5번 뒤라면 게이트웨이를 멈춘 상태에서 보관본을 복원하고 띄운다. 4번까지만 했다면 프로그램만 다시 띄운다. 복구 조건: 6번의 확인 실패, 방 충돌 뒤 진행 불가, 7번의 시험 글이 하나라도 올라가지 않음, 프로그램을 띄운 뒤 인스타 감시가 오류로 끝남): 1번처럼 멈추기 → 3번 보관본 복원(sha256 일치 확인) → 조립 → 재시작 → 프로그램 다시 띄우기 → 스위치 답이 `slack`인지 확인 → 멈추고 보고. ### 5단계: 전환 뒤 정리(7판, 구현 검토 12차)

전환은 적용됐다(2026-11-22). 남은 정리 하나를 한다.

- 예약 조립 원본 맞추기. 예약 조립기는 지시서 `schedule_bindings`의 받을 곳·켜짐 값을 그대로 예약 파일로 만든다(`hermes_schedule/catalog.py`). 전환에서 예약 파일 14개의 받을 곳과 자동 가입 예약의 켜짐 값만 바꿨기 때문에 원본은 아직 Slack·켜짐이다. 누가 예약 조립기를 쓰기로 돌리면 예약 보고가 다시 Slack으로 돌아간다. 그래서 **원본을 실제 값과 같게 고친다.**
  1. 지시서 파일을 0700 보관 폴더에 보관하고 sha256을 적는다.
  2. `schedule_bindings`에서 그 14개 예약의 받을 곳(실패 때 받을 곳 포함)을 지금 예약 파일의 hejo 값과 같게, 자동 가입 예약의 켜짐 값을 꺼짐으로 고친다. 다른 필드와 다른 예약은 건드리지 않는다. 임시 파일에 쓴 뒤 이름 바꾸기로 교체한다.
  3. `hermes-schedule-assemble --check`가 종료 0인지 확인한다(읽기 검사만. 쓰기로 돌리지 않는다). 종료 0이 아니면 보관본으로 지시서를 되돌리고 멈춰 보고한다.
  4. 스위치를 읽는 함수의 답이 여전히 `hejo`인지, 예약 파일이 바뀌지 않았는지(sha256) 확인한다. 게이트웨이는 재시작하지 않는다.
  5. `./sync` → `./airport-check`. 실패가 진단 직원 지시서 조립 불일치 한 건뿐인지 기록한다. 커밋하지 않고 변경 경로 수를 보고한다.
- 되돌리기 기준 갱신: 전환을 되돌릴 일이 생기면 지시서도 전환 전 보관본(멈춘 뒤 보관본)으로 돌아가므로 원본과 예약 파일이 함께 Slack으로 돌아간다. 따로 할 일은 없다.
- 그 밖에는 서버를 건드리지 않는다. 실제 인스타 DM과 다음 날 확인은 사장과 계획 담당이 본다.
