## 2. 단계

### 1단계: 준비와 되돌리기 예행(운영 변경 없음)

1. 이 작업이 바꾼 운영 저장소 파일 목록을 만든다(`git diff --name-only <착수 기준>..fcdec420`, 시험·fixture 제외). 파일마다 실행본의 sha256이 작업 브랜치의 변경 전 기준(운영 main의 그 파일)과 같은지 확인한다. 다르면 그 파일의 차이를 읽고, 이 작업과 무관한 다른 변경이면 작업 브랜치를 최신 운영 main 위로 올려(병합 충돌이 없을 때만) 다시 시험한 뒤 진행한다. 충돌이 있거나 판단이 서지 않으면 멈추고 보고한다.
2. 최신 운영 main과 합친 상태에서 team-kit 시험 묶음(verdict 6차의 49개 파일)과 인스타·네이버톡 격리 시험을 다시 돌린다. 종료 0이 아니면 멈춘다.
3. M7: 임시 홈에서 design 7절의 되돌리기 절차를 끝까지 한 번 실행하고 기록한다(보관 → `hejo`로 바꿈 → 되돌림 → 복원 파일 sha256 일치, 스위치를 읽는 함수의 답이 `slack`).
4. 네이버톡 사건 표가 바뀐다(열 3개 추가). 임시 홈에 지금 운영 표의 **모양만** 본뜬 빈 표로 옛 코드가 새 열이 있는 표를 읽고 쓰는지 확인한다(운영 표의 내용은 읽지 않는다).

### 2단계: 코드 적용(동작 불변)

절차의 틀은 HEJO-CONNECTIONS design 7.2다. 적용 전에 되돌리기 기록을 impl-report에 먼저 쓴다(명령마다 대상·커밋·sha256, 빈 칸 없음. 실제 경로는 이 저장소 밖 기록 파일에).

1. 한가한 때 확인: 진행 중 직원 턴 0(기존 재시작의 BUSY 검사), 인스타·네이버톡의 진행 중 외부 전송 0.
2. 보관: 바꿀 실행본 파일 전부와 네이버톡 사건 표 파일을 0700 임시 폴더에 복사하고 sha256을 적는다. 문은 공용 릴리스의 `RELEASE` 커밋을 적는다.
3. 상주 프로그램 잠시 멈춤: 인스타 감시와 네이버톡 다리처럼 바뀌는 파일을 읽는 상주·타이머 프로그램을 멈춘다(목록 기록). 실행 중 프로세스 0을 확인한다.
4. 교체: team-kit, 고객 응대 직원 플러그인, 네이버톡 다리, 그 밖에 바뀐 실행 파일을 임시 파일에 쓴 뒤 이름 바꾸기로 교체한다.
5. 문: 이 저장소의 기준 커밋으로 `install/hejo-release` → 게이트웨이 전체 재시작(운영 저장소 AGENTS의 재시작 규칙).
6. 확인(하나라도 실패하면 7번으로)
   - 게이트웨이 로그에 Slack 연결 전부와 iMessage, hejo 문이 다시 연결됨. 오류 로그에 재시작 뒤 새 줄 없음. 새 프로세스 시작 시각이 교체한 파일의 수정 시각보다 뒤.
   - 입구 소켓 파일이 있고 권한이 0600. 입구에는 **읽기 요청 하나만** 보낸다. 글을 올리지 않는다. 요청은 정확히 이것이다(2판, 구현 검토 7차): `GET /local/v1/threads/<방금 만든 무작위 UUID>?room=<방금 만든 다른 무작위 UUID>`. 쿼리에 `employee`를 함께 넣지 않는다(규격은 둘 중 하나만 받는다). 기대 응답은 HTTP 400과 오류 이름 `room_not_found`다([확인] `gate/local.py`의 스레드 읽기, 구현 담당의 격리 재현). 받은 HTTP 상태와 오류 이름을 **판정하기 전에** 기록 파일에 적는다. 기대와 다르면 실패다.
   - 스위치를 읽는 함수의 답이 `slack`.
   - `hermes-connections status --json`과 `apps --json` 성공.
   - 3번에서 멈춘 프로그램을 다시 띄우고 한 차례 정상 종료(또는 정상 대기)를 확인. 네이버톡 사건 표에 새 열 3개가 생겼고 기존 행 수가 보관본과 같음.
   - Slack에 시험 글을 보내지 않는다. 다음에 저절로 나가는 보고(예: 인스타 매시 요약)가 Slack에 평소대로 올라왔는지 기록 파일의 시각으로 확인한다. 한 시간 안에 확인하지 못하면 "미확인"으로 적고 반환한다.
7. 되돌리기(복구 조건: 6번의 어느 확인이든 실패): 프로그램 멈춤 → 보관본 복원(sha256 일치 확인, 네이버톡 표 포함) → 기록한 `RELEASE` 커밋으로 `install/hejo-release` → 재시작 → 6번 확인을 다시 → 멈추고 보고.
8. 성공하면 운영 저장소에서 `./sync` → `./airport-check` → 작업 브랜치의 변경이 운영 main에 반영되게 커밋한다(`git commit --only`로 자기 경로만, `./sync`가 토큰 경고를 내면 커밋하지 않고 보고). 임시 worktree는 지우지 않는다.

### 3단계: 전환 준비물(운영 변경 없음)

모두 이 저장소 밖 파일에 만든다. 보고에는 경로와 줄 수, 빈 칸 수만 적는다.

1. **방 표**(M1): 직원이 듣는 Slack 채널 5개마다 방 이름(Slack 채널 이름과 같게), 구성원(그 채널을 듣는 직원), 대표 직원 **제안**(근거 한 줄). 구성원이 2명 미만인 채널이 있으면 표시한다. 이미 같은 이름의 hejo 방이 있으면 구성원·대표 직원 비교 결과를 적는다(읽기만).
2. **받을 곳 전수 대조표**(M1): design 4.2 표와 impl-report TASK-06 대조표의 줄마다 보내는 것, 지금 Slack 받을 곳의 직책 키, hejo 받을 곳(방 또는 직원 1:1), 금고 `hejo.*` 키 이름, 확인 방법. 빈 칸이 없어야 한다. 아래 세 줄을 따로 넣는다.
   - 일 넘기기(프로젝트 허브): Slack 허브 채널에 남음.
   - 위키 일일 보고와 금고 백업 승인: Slack에 남음(`vault_backup`).
   - 사장의 Slack 대화에 답하는 도구(파일 올리기, 보고 상태 고치기): Slack에 남음(`slack_session`).
3. **예약 보고 목록**: 프로필마다 `cron/jobs.json`에서 받을 곳이 Slack인 예약의 수와 hejo로 바꿀 값(읽기만). 공개 채널 자동 가입 예약을 표시한다.
4. **시스템 알림 변경안**: design 8절대로 바꿀 `config.yaml` 줄(읽기만).
5. **도구 집합 비교**(M5): 운영 프로필마다 조립기를 **쓰지 않는 방식**(임시 사본에 조립)으로 돌려 hejo·Slack 도구 집합의 차이를 구한다. 차이가 0이 아니면 목록을 적는다.
6. **멈출 프로그램 목록**: 4단계 1번에서 멈출 상주·타이머 프로그램 전부.

3단계까지 마치면 멈추고 결과를 반환한다.

design 7절의 1~7번 그대로다. 이번 지시에서는 하지 않는다. 시작 조건: 사장이 방 표와 대조표를 확인했다는 계획 담당의 다음 인계.
