|---|---|---|---|---|

점검 질문(8절):

1. **각 부분이 어느 칸인가? 두 번째 원본이 없는가?** 위 표와 같다. 새 칸·새 저장 위치·새 설정 키는 0이다. 이전판 판정은 앱 한 곳에만 둔다(`get-hejo` 복제 금지, D-03).
2. **쓰기 주체는? 시설 코드가 사장 칸을 쓰지 않는가?** 앱이 옮기는 것은 자기 이전판(같은 번들 ID)뿐이다. 이것은 관제 화면 칸 자신의 낡은 사본이다. 금고·지시서·공방·명부·사물함·공용 창고와 `~/Library/Application Support/hejo`(화면 설정)는 건드리지 않는다.
3. **갱신·제거 때 누가 보존·삭제하는가?** 6절 "갱신 = 앱을 바꾼다"의 범위 안이다. 갱신 뒤 앱이 이전판 사본을 휴지통으로 옮긴다(복구 가능). 보존 칸 목록은 그대로다. TASK-07에서 ARCHITECTURE 3절 관제 화면 행 수명과 6절 갱신 행에 한 구절을 덧붙인다.
4. **개인값이 없는가?** 코드·시험은 임시 폴더와 가짜 번들 ID만 쓴다. 로그의 경로는 실행 중 OS 로그에만 남고 저장소에는 없다. `scan_private`로 확인한다.
5. **다른 사장의 공항에서도 같은가?** 경로 상수 없이 번들 ID·`~/Applications`(홈 기준)로 판정하므로 어느 Mac에서나 같다.

**D-09 근간 개정(사용자 결정 2026-11-26: 계획 담당 추천대로).** 3절 칸 표의 정비 격납고 행 원본 위치에 `tests/`(수락 시험)와 `githooks/`를 추가한다. 그 행의 "둘 것"에 이미 "빌드·시험"이 있어 새 칸이 아니다. 개발·공개 `docs/ARCHITECTURE.md`에 TASK-07에서 반영한다.

## 2. 결정

- **D-01 통합 순서.**
  - 새 공개 worktree를 `github/main` tip에서 만든다.
  - `a6d5e9a`(DISCORD-SECTIONS)를 먼저 합친다. 원격 대비 차이가 작고 verdict 6차로 확정된 후보다. 그다음 `1ca2cbb`(TELEGRAM-REMOVE)를 합친다.
  - 충돌 규칙:
    - `gate/server.py`·`TestMain.swift`: 두 쪽 추가를 모두 유지한다. 텔레그램 관련 줄만 빠진다.
    - `test_slack_move_gate.py` AT-SM-02 해시: 최종 합친 규격의 sha256으로 갱신한다.
    - 규격 `schemas/hejo-wire-v1.json`: 병합별 첫 부모 비교 두 번과 최종 합성 비교 한 번으로 확인한다(spec REQ-TIDY-01 AC-01a, R1-02).
      - 병합 1은 T0 대비 추가만 있어야 한다.
      - 병합 2는 M1에서 텔레그램만 빠져야 한다. AT-HTR-04의 "원격 tip"은 여기서 M1이다.
      - 최종은 T0 + `discord_layout` − 텔레그램이어야 한다.
      - 최종 트리에서는 AT-HTR-04 상시 검사(텔레그램 부재)와 AT-DK-22 6판 구조 검사(a)(b)(c)를 그대로 돌린다.
  - rebase·force는 쓰지 않는다. 두 브랜치 이력은 merge로 보존한다.
- **D-02 정리 시점과 위치.**
  - 앱 시작 직후 한 번, 메인 스레드를 막지 않는 곳에서 돈다. Sparkle 설치 뒤 재실행도 앱 시작이라 같은 경로를 탄다.
  - 설치 위치 판정은 기존 `LoginLaunch.isInstalled`와 같은 기준(두 응용 프로그램 폴더 최상위)을 쓴다. 같은 판정을 두 곳에 복사하지 않는다(공유 또는 재사용).
  - 휴지통 이동은 `FileManager.trashItem`이나 그와 같은 복구 가능한 API로 한다. 영구 삭제는 쓰지 않는다.
  - 시험을 위해 폴더 목록, 자기 정보, 실행 중 번들 목록, 휴지통 처리기를 주입할 수 있게 한다. 이름과 모양은 구현 자유다.
  - 폴더 목록에는 `/Applications`와 `~/Applications`를 모두 넣고, 각각 독립적으로 처리한다(R1-03).
  - 처리 결과는 통합 로그 `Logger(subsystem: 번들 ID, category: "stale-copies")`에 사본마다 한 줄 남긴다. 저장 파일·새 설정은 만들지 않는다.
    - 소비자: M-01 실물 확인과 사용자 문의 진단. `log show --predicate 'subsystem == "io.github.hermes-hejo.hejo" AND category == "stale-copies"'`로 본다.
    - 근거: 에이전트 셸에서는 `~/.Trash`를 읽을 수 없다(TCC, 2026-11-26 확인). 그래서 휴지통 도착 증거는 `trashItem`이 돌려준 결과 경로를 로그에 남기는 것으로 한다.
- **D-03 `get-hejo`는 정리 코드를 갖지 않는다.**
  - 이미 설치 뒤 `open /Applications/hejo.app`을 하므로 앱의 정리가 돈다. 같은 판정을 셸에 복제하면 두 원본이 생긴다(덧대기).
  - 사용자가 고른 "설치 스크립트도"는 이 경로로 충족한다. 수락 시험 AT-TIDY-09가 `get-hejo`의 실행 줄이 남아 있는지 지킨다.
- **D-04 판 비교.**
  - `CFBundleVersion` 정수 비교만 쓴다. 공개 릴리스는 매번 올리는 정수다. 실측: 0.2.7=9, 0.2.8=10.
  - 같은 번호의 개발 빌드는 남긴다. 그 경우는 REQ-TIDY-03 절차로 막는다.
- **D-05 V-4.** `history_queries.py` 176줄 근처에서 이어 붙일 때 멘션 줄의 앞뒤 공백을 뺀 값을 쓴다. 판정 규칙과 300 글자 묶음은 그대로 둔다.
- **D-06 V-3.** 기존 `history_transport_app.py` `test_alert_seen`·`HistoryAlertSeenHarness`에 말풍선·섬 클릭 시나리오를 추가한다. 공개 worktree의 `.build/alert-seen/bubble-probe/`에 있는 보조 시험이 출발점이다. 기대값은 AT-AS-01과 같다.
- **D-08 릴리스(R1-04).** HEJO-RELEASE-20261125 인계 v1·v2와 같은 절차를 쓴다.
  1. 버전 커밋 R(Info.plist 두 값 + `test_ship.py` 버전 단언).
  2. `refs/heads/public` 갱신.
  3. 깨끗한 트리에서 빌드.
  4. `hejo-ship prepare`. 산출물은 zip과 `prepared.json`뿐이다. 서명 검증은 `prepare` 안의 `sign_update --verify`가 한다.
  5. appcast는 사용자의 `hejo-ship publish`가 만든다. 그래서 게시 뒤 관측(spec REQ-TIDY-06 AC-03)으로 분리한다.
- **D-07 코드 정리는 2단계.**
  - 감사 범위는 추적 파일 기준이다(spec REQ-TIDY-07, R1-01). `git ls-files`로 대상 목록을 만들고, 제외한 경로와 이유를 감사 문서 첫 표에 둔다.
  - TASK-05에서 감사 목록만 만든다(코드 변경 없음). 계획 담당이 승인한 뒤 TASK-06에서 지운다.
  - 정리는 REQ-TIDY-01·02·04·05가 반영된 공개 커밋 위에서 한다. 앞 작업과 같은 파일이 겹치지 않게 하기 위해서다.

## 3. 대안

| 대안 | 판정 | 이유 |
|---|---|---|
| 정리를 Sparkle 델리게이트(설치 직후)에서만 실행 | 기각 | `get-hejo`·수동 설치 경로를 놓친다. 앱 시작이 모든 경로를 덮는다 |
| `get-hejo`에 셸 정리 추가 | 기각 | D-03. 판정 원본이 둘이 된다 |
| 이름 패턴(`hejo*.app`)으로 정리 | 기각 | 사용자가 이름을 바꾼 사본을 놓치고, 같은 이름의 다른 앱을 잘못 지울 수 있다. 번들 ID가 정확한 기준이다 |
| 코드 정리를 한 번에 진행 | 기각 | 근거 없는 삭제 위험. 감사 → 승인 → 삭제로 나눈다 |

## 5. 실패와 복구

- 정리에서 실패한 사본은 남는다. 다음 실행 때 다시 시도한다.
- 잘못 옮겨졌으면 휴지통에서 되돌린다. 앱 코드 롤백은 이전 릴리스 재설치다.
- 통합 실패(AC-04)는 푸시 전에 멈춘다. 원격에 쓰는 일이 없다.

## 6. 위험도

- **일반.** 여러 모듈, 공개 푸시, 사용자 Mac의 파일 이동이 있다.
- 공통 4절의 "데이터 삭제·비가역"에는 해당하지 않는다. 판단 근거:
  - 이동 대상이 같은 번들 ID의 더 낮은 판 앱 번들로 좁게 정해져 있다.
  - 휴지통으로 옮길 뿐이라 복구할 수 있다.
  - 사용자 자료(`~/Library/Application Support/hejo`)는 건드리지 않는다.
- 필요한 증거 수준:
  - REQ-TIDY-02: 2(대역)와 4(실물 M-01).
  - REQ-TIDY-01·04·05·07: 2.
