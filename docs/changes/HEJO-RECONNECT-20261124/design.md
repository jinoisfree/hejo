# HEJO-RECONNECT 설계 v1

[spec](spec.md)의 칸 표를 따른다. 기준 커밋과 상태는 spec과 같다.

## 지금의 흐름과 원인

```text
문: sync → 기록 1건 = 프레임 1개 … → sync_done(through, more, head_seq)
앱: 소켓 수신 → GateClient.receive(캐시 기록, applied 전진) → onFrame
    → ConversationController.receive = performUpdates { receiveFrame } → 통지 1회
    → ConversationView.refresh(사이드바·카드 전체) + 펫·설정 창 갱신
```

프레임 하나의 화면 갱신 비용은 이미 줄였지만(HEJO-PERF), 횟수가 밀린 건수와 같다. 원인은 "받을 기록이 더 남아 있는 줄 알면서도 건마다 화면을 다시 그리는 것"이다.

## 바꾸는 것

- **남은 기록을 아는 곳은 GateClient 하나다.** welcome과 `sync_done`의 `head_seq`(규격상 필수)와, 누락을 알게 한 프레임의 seq로 "알려진 head"를 연결 동안만 기억한다. 연결 시작·끊김·stop 때 버린다. 저장하지 않는다. 밖에는 "받을 기록이 남았는가"(알려진 head > applied)만 읽기 전용으로 내준다. 이름과 자료형은 구현 담당이 정한다.
- **통지를 묶는 곳은 지금도 통지 묶음을 가진 ConversationController다.** `receive`가 기록 프레임을 처리한 뒤 받을 기록이 남아 있으면, 프레임 처리는 지금과 똑같이 하되 화면 통지만 보류 표시로 남긴다. 남지 않았거나 seq 없는 프레임이면 지금처럼 반환 전에 통지한다. 보류 표시는 다음 통지가 나갈 때 함께 사라진다(통지는 항상 최신 모델을 읽으므로 따로 합칠 내용이 없다).
- 기존 0.5초 주기 점검이 보류 표시를 보면 통지한다. 새 타이머·새 상수는 없다.
- `setPaused(false)`는 쌓인 프레임을 하나의 `performUpdates` 안에서 적용한다.

`receiveFrame`의 프레임별 처리, `model.apply`, `LocalStore.append`, View의 갱신 내용은 고치지 않는다.

## 유지하는 계약

프레임 순서·저장 커서·오류 의미, 평상시 프레임의 동기 통지와 동기 캡처, 명시적 `performUpdates` 중첩, `canSend`(연결됨 + 재생 완료), `client.replayComplete`를 쓰는 기존 분기, 통신 규격 `x-sync`, 캐시 형식.

바뀌는 계약은 하나다. "변경 프레임마다 반환 전 통지 1회"가 "받을 기록이 남지 않은 프레임마다"로 좁아진다. 영향받는 소비자: `ConversationView.refresh`, AppDelegate의 `conversation.onChange` 연결(펫 활동·설정 창), 이를 세는 시험(AT-HP-01).

## 기존 경로 판정

| 경로 | 판정 | 이유 |
|---|---|---|
| `ConversationController.receive`의 프레임당 통지 | 교체(같은 자리에서 조건 추가) | 원래 책임 자리. 옆에 새 경로를 두지 않는다 |
| `setPaused` 해제 때 프레임별 `receive` 반복 | 교체 | 같은 원인. 한 묶음으로 |
| `GateClient`가 버리던 `head_seq` | 유지 + 읽기 추가 | 규격에 이미 있는 값. 문은 그대로 |
| 0.5초 주기 점검 | 유지 + 보류 통지 전달 추가 | 수신이 멈춰도 화면이 낡지 않게 |
| `LocalStore.append`(건당 fsync) | 유지 | 계측상 1~2%. 무결성 경로라 건드리지 않는다 |
| 문 `sync` 쪽 나누기 | 유지 | 원인 아님 |

## 대안

- **B. `replayComplete`가 거짓인 동안 전부 보류(기각).** 상태가 하나 적지만, head를 모르거나 남은 기록이 없는데도 보류한다. 기존 앱 시험 다수(welcome 25곳 대 `sync_done` 9곳)가 `sync_done` 없이 프레임 뒤 화면을 바로 보므로 의미 변경 범위가 불필요하게 넓다.
- **C. 전역 다음 런루프 묶음·지연(기각).** 평상시 동기 통지·동기 캡처 계약을 깨며 현재 계약이 금지한다.
- **D. 화면 한 번 갱신을 부분 갱신으로(기각, 별도 과제 후보).** 건수 비례는 그대로이고 변경 범위가 크다.
- **E. 문이 한 쪽을 프레임 하나로 묶어 전송(기각).** 통신 규격·문 변경이 필요하고 1MiB 프레임 한도와 충돌한다. 앱만으로 해결된다.

## 실패·경계

- 재생 도중 끊김: 연결 상태 통지가 지금도 화면을 다시 그린다. 보류 표시가 남아도 다음 주기 점검이 처리한다.
- 서버가 head를 알려 준 뒤 기록을 보내지 않고 멈춤: 주기 점검이 0.5초 안에 그때까지의 상태를 보여 준다.
- 캐시 저장 실패·규격 오류: GateClient의 기존 중단 경로 그대로. 보류 표시가 오류 표시를 가리지 않아야 한다(상태 통지로 갱신).
- 일시정지 중: 프레임은 지금처럼 쌓이기만 한다.

## 위험과 되돌리기

위험도 일반(화면 통지 시점 변경, 저장·규격·권한 무변경). 되돌리기는 해당 커밋 되돌림과 이전 앱 재설치이며 자료 이관이 없다.
