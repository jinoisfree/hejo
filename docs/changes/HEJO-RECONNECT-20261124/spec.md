## 문제와 근거

사용자: 앱이 끊겼다가 다시 연결되면 심하게 버벅인다.

- [확인] 재연결하면 문은 앱이 놓친 기록을 한 건씩 프레임으로 다시 보낸다(`gate/server.py` `sync`, 한 쪽 500건). 앱은 프레임마다 `GateClient.receive` → 캐시 기록 → `ConversationController.receive`를 돌고, 프레임 하나가 끝날 때마다 화면 전체 갱신(`ConversationView.refresh`)을 한 번 한다. 모두 메인 스레드다.
- [확인] 계측(기준 커밋 소스, `-O`, 실제 AppKit View 연결, 가짜 직원 8·기존 글 800건, 2026-11-24 이 Mac): 밀린 프레임 20/100/300건 처리에 1.49/6.74/20.23초. 프레임당 중앙값 약 64ms. 화면 통지 횟수는 23/103/303회로 프레임 수에 비례하고, 전체 시간의 96% 이상이 화면 갱신이다.
- [확인] 같은 입력에서 캐시 기록(프레임당 fsync 2회 포함)만의 비용은 프레임당 0.7~0.9ms로 전체의 1~2%다. 저장은 원인이 아니다.
- [확인] 개입 실험(임시 사본에서만): 밀린 기록 수신 중 화면 통지를 경계까지 보류하면 같은 입력이 0.23/0.43/0.92초, 통지 3회로 줄었다. 모델 최종 상태 비교는 이 실험에서 하지 않았다.
- [확인] 사용 중인 Mac의 캐시는 약 7분 동안 28건 늘었다(783→811). 몇 시간 끊기면 수백 건이 밀릴 수 있는 빈도다. 단, 사용자가 겪은 재연결 때의 실제 건수는 [미확인]이다.
- [확인] 이전 HEJO-PERF는 "프레임 한 건당 통지 1회"와 한 번의 갱신 비용을 줄였고, 여러 프레임이 연달아 올 때의 묶음은 범위 밖이었다. 그래서 건수에 비례하는 비용이 남았다.
- [확인] 같은 구조가 일시정지 해제에도 있다. `setPaused(false)`가 쌓아 둔 프레임을 한 건씩 `receive`해 건수만큼 화면을 갱신한다.

## 요구

REQ-HR-01: 서버가 알려 준 기록 끝(head)까지 받을 기록이 남아 있는 동안에는 기록 프레임(seq가 있는 프레임)마다 화면 통지를 내지 않는다. 통지는 다음 때에 최신 상태로 한 번 전달한다. ① `sync_done` 프레임 수신(반환 전), ② 알려진 head에 도달한 프레임 수신(반환 전), ③ 기존의 다른 즉시 통지(사용자 동작, seq 없는 프레임, 연결 상태 변화 등)가 일어날 때, ④ 기존 0.5초 주기 점검에서 보류된 통지가 있을 때.

REQ-HR-02: 일시정지 해제 때 쌓인 프레임은 순서대로 모두 적용한 뒤 화면 통지를 한 번만 전달한다.

REQ-HR-03: 화면 통지 시점 외에는 아무것도 바뀌지 않는다. 프레임 적용 순서, 저장 커서(applied)와 캐시 내용, 모델 최종 상태(글·읽음·종·질문·선택·초안), 프레임별 비화면 처리(전송 확인, 오류 표시, 방·스레드 정리), 전송 가능 조건, 받을 기록이 남지 않은 평상시 프레임의 "반환 전 최종 상태 통지 1회"를 보존한다.

NFR-HR-01: 고정 가짜 부하에서 밀린 300건 처리 시간이 2.0초 이하이고 기준 대비 90% 이상 줄어든다(상세·근거는 수락 시험 AT-HR-04).

범위 밖: 문·통신 규격·허브·캐시 저장 방식(fsync 포함)·화면 한 번 갱신의 비용 자체·전역 비동기 지연(debounce)·평상시 스트리밍 수신 빈도. 새 SwiftUI 화면 없음. 운영 서버 재시작·실제 메시지 전송 없음.

## 수락 기준

| AC | 종류 | Given / When / Then | 시험 |
|---|---|---|---|
| HR-01 | 정상 | 화면이 붙은 상태에서 welcome(head가 현재보다 N 큼) 뒤 기록 프레임 N건과 `sync_done`을 받으면, welcome부터 `sync_done` 반환까지의 화면 통지 횟수가 N=20·100·300에서 서로 같고 5 이하다. `sync_done` 반환 시점의 화면은 N건이 모두 반영된 최종 상태다. | AT-HR-01 |
| HR-02 | 경계·실패 | 받을 기록이 남은 채 수신이 멈추거나 끊겨도, 주기 점검 1회 또는 연결 상태 통지 뒤에는 그때까지 적용된 기록이 화면에 반영된다. 여러 쪽(more=true)이면 쪽마다 반영된다. head 정보가 없거나 남은 기록이 없으면 지금처럼 프레임마다 반환 전에 통지한다. 누락(seq 건너뜀)으로 다시 받는 경우에도 같은 규칙이 적용된다. | AT-HR-02 |
| HR-03 | 정상 | 일시정지 중 쌓인 프레임 M건은 해제 호출 한 번에 모두 적용되고 화면 통지는 M과 무관하게 1회다. | AT-HR-03 |
| HR-04 | 보존 | 같은 프레임 열을 기준 빌드와 수정 빌드에 적용하면 최종 관측 상태(글 ID·본문·순서, applied, 캐시 파일 내용, 읽음·종·질문, 선택·초안, 전송 대기·오류 표시)가 같다. 기존 HEJO-PERF 동결 기대값과 관련 회귀 시험이 통과한다. | AT-HR-05 |
| HR-05 | 성능 | AT-HR-04의 고정 부하에서 NFR-HR-01을 만족하고, 수신 도중 큐에 넣은 입력·방 전환이 수신 종료 전에 처리된다. 실제 소켓 재연결 경로에서도 재현 부하가 같은 예산 안에 든다. | AT-HR-04 |
| HR-06 | 실물 | 수정본을 설치한 실제 앱에서 끊김 뒤 재연결할 때 입력·스크롤·방 전환이 멎지 않는다. 가짜 부하 통과만으로 이 항목을 충족으로 보지 않는다. | AT-HR-06 |
