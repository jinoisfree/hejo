# 대화 화면 버벅임 해소 설계 — v3

요구는 [spec](spec.md), 근간은 [ARCHITECTURE](../../ARCHITECTURE.md)다. 칸은 관제 화면(app) 하나이며 새 칸·새 원본·새 설정이 없다.

## 기준
- [확인] 개발 main `236b0177468b90d9ea23a1b1190e996db78a0694`에는 지난 성능 개선(`221e84082a4230caca6b450cb3b2e0ee9d085ee8`)과 입력 개선(`404c8319979a947a43506b133257ed4d6e0ab419`)이 없다. 둘은 `role-workflow/26-26405dfc`의 `ac212cfe911168e576e2e24df5d2b6f7f30ff9b4`에 있으며, 이 커밋은 main의 후손이다(main에서 8커밋 앞, 빨리감기 가능).
- [확인] 설치된 앱(0.2.7)의 대화 화면 소스는 `ac212cf`와 같다. 설치본은 공개 이력에서 빌드됐고 개발 이력과 공통 조상이 없다.
- [사용자 결정] 개발 main에 `ac212cf`를 합친 것을 개발 기준으로 삼는다. 구현 담당이 배정 브랜치에서 빨리감기로 합치고 합친 HEAD를 기준으로 기록한다. 이동하는 브랜치 tip이 아니라 위 고정 커밋을 합친다. 공개 이력과는 합치지 않는다.
- [확인] 개발 기준과 공개 기준은 PetController·PetLayout·ConnectionsWindow가 다르다. 공개 기준으로 옮기는 일은 이 작업의 구현 범위가 아니며 검증 통과 뒤 기존 공개 통합 절차로 따로 진행한다.

## 현재 자료 흐름
```
모델 변경·선택·타이머
  → ConversationView.refresh
      → 보이는 스레드마다 threadContent → postPieces(글마다 새로 꾸밈)
      → NativeThreadList.show → apply → remeasure(전부 다시 잼)
          → NativeThreadCard.layout → textSize(기억 장치 우회) → 글자 배치 계산
      → 사이드바·입력칸·섬·서랍 갱신
```
알림 클릭: `AppDelegate.openBubble` → `PetController.showChat(preparing:)` → `setExpanded` → 대화 갱신 묶음 실행(`openFromBubble` → refresh 1회) → 화면 스냅샷 → 60Hz 전환 타이머. refresh가 끝나면 보류한 스크롤(`pendingRevealScroll`)이 `NativeThreadList.scrollTo`를 불러 지연 3회의 스크롤 애니메이션을 시작한다.

## 목표 자료 흐름
```
refresh
  → postPieces: 글의 "표시 입력"이 전과 같으면 전에 만든 변하지 않는 본문을 그대로 돌려준다
  → remeasure → textSize: 같은 본문·같은 폭이면 기억한 높이를 돌려준다
```
- 책임 하나: 본문 재사용의 소유자는 대화 화면의 글 꾸미기 경로(postPieces가 있는 자리)다. 높이 기억의 소유자는 기존 `NativeThreadCard.textSize`다. 둘 다 이미 있는 책임 자리이며 새 계층을 만들지 않는다.
- 표시 입력: 본문 결과에 영향을 주는 값 전부다. 최소한 다음을 포함한다. 글 식별자, 실제로 보여 줄 글(스트리밍 단계와 접힌 미리보기 반영 뒤), 내 글 여부, 보내는 중 여부, 스트리밍 여부, 밝기 테마, 발신자 색과 가장자리 색, 글자 크기와 말풍선 모양 설정 판(`ChatAppearance.revision`), 검색 강조어, 체크 상태. 구현자는 `postPieces`가 읽는 값을 전수 확인해 빠진 입력을 보태며, 목록을 줄이지 않는다.
- 폐기: 표시 입력이 다르면 새로 만들고 옛 값은 버린다. 개수 상한을 넘으면 오래된 것부터 버린다. 상한 값은 구현자가 정하되 보이는 범위(50개 스레드)를 담을 수 있어야 하고 시험으로 고정한다.
- 가변 문자열 제외 규칙(`NativeThreadCard.swift:116`)의 의도는 내용이 바뀔 수 있는 객체를 주소로 기억하지 않는 것이다. 이 의도를 유지한다. 재사용되는 본문은 만든 뒤 바뀌지 않는 객체여야 한다.

## 창 전환
- 유지: 전환 전 대화 갱신을 한 묶음으로 끝내고 스냅샷을 찍는 순서(`PetController.setExpanded`).
- 변경: 접힌 창을 여는 알림 이동에서는 스냅샷 전에 목적지 스레드를 최종 위치에 바로 놓는다. 이 경로에서는 지연 스크롤 애니메이션을 시작하지 않는다. 전환 중 목록 높이가 다시 재어져도 위치가 유지되도록 기존 진입 배치 장치(`NativeThreadList.enter`/`placeEntry`)의 책임 안에서 처리한다.
- 이미 창이 열려 있을 때의 이동, 검색 결과·알림 줄 이동은 기존 `scrollTo` 애니메이션을 유지한다.
- 전환 중 읽음 처리 통지 등 이 동작이 유발하는 추가 전체 갱신은 전환 전 묶음 안에서 끝나야 한다. 전환 중 도착한 실제 수신은 기존대로 처리한다.

## 기존 경로 판정
| 경로 | 판정 | 내용 |
|---|---|---|
| `postPieces`의 글마다 새 가변 문자열 생성 | 교체 | 표시 입력이 같으면 변하지 않는 본문 재사용. 같은 변경에서 매번 생성하던 경로를 없앤다 |
| `NativeThreadCard.measured` 높이 기억 | 유지 | 책임 그대로. 개수 상한(256)과 주소 기준이 보이는 범위에 충분한지 구현자가 확인하고, 부족하면 이 자리에서 고친다 |
| `NativeThreadList.remeasure`의 전체 layout 호출 | 유지 | 높이 기억이 살아나면 비용이 내려간다. 예산 미달이 계측으로 확인될 때만 같은 자리에서 줄인다 |
| 스트리밍 30Hz refresh 타이머 | 유지 | 횟수와 글자 나타나는 느낌은 범위 밖. 한 번의 비용만 줄인다 |
| `scrollTo`의 지연 3회 애니메이션 | 유지(일반 이동) / 교체(접힌 창을 여는 이동) | 여는 이동은 즉시 배치로 전환. 두 경로가 같은 이동에 함께 돌지 않는다 |
| Model의 렌더 범위 파생값(`withRenderValues`) | 유지 | 현재 계약 그대로 |
| 입력 이벤트의 국소 갱신 | 유지 | 현재 계약 그대로 |

## 유지할 계약
- 글 내용·속성·카드 높이·글 위치·스크롤 위치 규칙, 따라가기 스크롤, 긴 답글 접기, 체크, 검색 강조, 복사 표시.
- 수신 순서·저장 cursor·오류 의미, 읽음·종·질문·초안·첨부.
- 전환 애니메이션의 모양과 길이, 스냅샷 순서, 세 번 누르기 진단 표식.
- 저장 형식·통신·설정 변경 없음.

## 변경 성격
동작 보존 최적화다. 비교 방법은 같은 상태에서 새로 만든 화면과의 대조(AT-SM-02), 기존 의미 동결 시험(AT-SM-08), 전후 동일 조건 계측(AT-SM-05)이다. 창 전환의 여는 이동만 "애니메이션으로 따라가던 스크롤"이 "열릴 때 이미 제자리"로 바뀌는 작은 의미 변경이며 spec AC-04로 승인 대상이다.

## 대안
- 보이는 카드만 재고 그리기: 효과가 가장 크지만 행 높이를 모르는 상태에서 스크롤 위치·따라가기·진입 배치를 다시 설계해야 한다. 기각.
- 스트리밍 갱신 횟수 줄이기: 증상 완화이고 글자 나타나는 느낌이 달라진다. 기각.
- 카드 내용 전체를 비교해 통째로 재사용: 카드 내용에 동작 클로저가 들어 있어 같음을 판정하기 어렵다. 본문과 높이 재사용으로 예산에 미달할 때의 후속 후보로만 남긴다.

## 계측
- 시험 전용 계수기: 본문 꾸미기 횟수와 높이 계산 횟수를 글 식별자별로 센다. 조건부 컴파일 안에만 둔다.
- 기존 성능 하네스(`app/Tests/HejoPerfTests.swift`)를 재사용한다. 동결된 기존 workload와 기대값은 바꾸지 않고, 현실적 길이의 새 workload를 별도 결과 파일로 추가한다.
- 전환 프레임 간격은 기존 전환 진단(`ThreeTapDiagnostics`)과 지연 하네스의 표식을 재사용한다.

## 위험과 복구
- 위험도 일반. 근거: 여러 화면 파일 수정, 저장·권한·통신 영향 없음, 되돌리기는 작업 diff 역적용.
- 핵심 위험은 낡은 본문 표시다. AC-02의 대조 시험이 통제 수단이다.
- 사전 별도 검토: 계획 검증을 켰다(사용자 결정). 재사용 입력 누락은 화면 오표시로 이어지므로 검토 대상이다.

## v2 추가: 글에서 뽑는 값의 재사용
근거는 [verdict](verdict.md) 3회와 spec v3의 REQ-SM-08이다.

### 원칙
입력이 같으면 결과가 같은 순수 파생값은, 그 값을 이미 소유한 자리에서, 입력이 바뀔 때까지 유지한다. 새 계층·저장·설정을 만들지 않는다. 각 값마다 입력 목록을 정하고, 입력이 바뀌는 모든 경로에서 버린다.

| 값 | 소유 자리(기존) | 입력 | 버리는 때 |
|---|---|---|---|
| 스레드 판정 | `ConversationModel.assessment` | 그 스레드의 글 목록 중 판정이 읽는 필드 전부, 확인된 글 집합 | 그 스레드에 글 추가·편집·삭제·답글 상태나 버튼 변화, 확인 상태 변화, 기록 다시 불러오기 |
| 달력 버튼 | `ConversationController.calendarActions` | 글 본문, 글 시각, 달력 일정 목록, 보내는 중 여부, 역할 | 그 글의 변화, 달력 일정 변화 |
| 알림 목록 등 시각 의존 값 | `ConversationModel`의 렌더 범위 값 | 위 값들 + 현재 시각 | 기존대로 렌더 범위 종료 시. 지속하려면 시각을 입력에 포함해야 한다 |

- 구현자는 각 계산이 읽는 값을 전수 확인해 입력 목록을 확정하고 impl-report에 적는다. 목록을 줄이지 않는다.
- 렌더 범위 장치(`withRenderValues`)는 유지한다. 지속 값은 그 아래 층으로 두어 렌더 범위 값이 지속 값을 읽게 한다. 같은 값을 두 자리에 따로 기억하지 않는다.
- 개수 상한을 둔다. 스레드와 글이 삭제되면 그 항목도 버린다.

### 같은 원칙의 추가 병목
위 둘을 처리한 뒤에도 AC-05에 못 미치면 구현자는 구간별 계측으로 남은 자리를 확인한다. 그 자리가 위 원칙에 맞는 순수 파생값이면 같은 방식으로 처리하고 값·입력·버리는 때를 impl-report에 적는다. 다음은 원칙 밖이므로 하지 않고 멈춰 보고한다: 계산을 다른 스레드나 나중으로 미루기, 갱신 횟수 줄이기, 보이는 부분만 계산하기, 표시 결과가 달라지는 생략, 사이드바나 카드의 구조 변경.

### 기존 경로 판정(추가)
| 경로 | 판정 | 내용 |
|---|---|---|
| `assessment`의 렌더 범위 전용 기억 | 교체 | 입력 기준 지속 기억으로 바꾸고 렌더 범위 전용 사본은 같은 변경에서 없앤다 |
| `calendarActions`의 매번 계산 | 교체 | 입력 기준 기억으로 바꾼다 |
| 알림 목록의 렌더 범위 기억 | 유지 | 시각 의존. 지속 판정을 읽어 비용만 내려간다 |

### 위험
낡은 판정은 알림·종·질문 표시 오류로 이어진다. 본문 재사용보다 영향이 크다. 통제 수단은 AT-SM-10의 새 모델 대조와 기존 의미 동결 58단계다. 위험도는 일반을 유지한다(저장·통신·권한 영향 없음, 표시 전용, 되돌리기 가능).

## v3 보완 (4회 검토)
- **정정:** v2의 "렌더 범위 전용 사본은 없앤다"를 거둔다. 스레드 판정은 지속 값(입력 비교 후 재사용) 위에 렌더 범위 기억을 둔다. 한 그리기 안에서는 스레드마다 입력 수집과 비교를 한 번만 한다. 렌더 범위 기억은 기존 무효화 규칙(상태 변경 시 폐기, 범위 종료 시 폐기)을 그대로 따른다. 두 층은 같은 소유 자리(`ConversationModel.assessment`) 안에 있다.
- **추가:** 회원 상태 병합 결과.

| 값 | 소유 자리(기존) | 입력 | 버리는 때 |
|---|---|---|---|
| 회원 상태 병합 결과 | `MemberState.items` | 받은 상태 문서의 항목, 아직 안 보낸 변경 | 둘 중 하나라도 바뀌는 모든 경로(수신 반영, 로컬 변경, 전송 확인, 계정 전환, 저장소 다시 읽기) |

- 구현자는 두 입력을 바꾸는 경로를 전수 확인해 impl-report에 적는다. 조회 결과(`value`, `read`, 확인 여부)는 재사용 전과 같아야 한다.
- 제품 소스의 시험 전용 코드는 계수·관측 지점만 둔다. 입력 누락 변형 분기는 제품 소스에 두지 않는다.
