## 문제
[확인] 사용자가 대화 화면에서 스레드를 눌러 펼칠 때, 새 글을 쓸 때, 알림을 눌러 창이 열리며 스레드로 갈 때, 답변이 흘러나올 때, 방을 바꿀 때, 스크롤할 때 버벅임을 느낀다.

[확인] 원인(코드, 개발 기준의 행 번호):
- 다시 그리기 한 번마다 보이는 범위의 모든 글을 새로 꾸민다. `ConversationView.swift:1009`가 글마다 새 가변 문자열을 만든다. 범위는 최대 50개 스레드다(`ThreadWindow.swift:5`).
- 그 문자열은 높이 기억 장치를 통과하지 못한다. `NativeThreadCard.swift:116`이 가변 문자열을 기억 대상에서 제외하므로 매번 전체 글자 배치를 다시 계산한다. 목록은 다시 그릴 때마다 모든 카드를 다시 잰다(`NativeThreadList.swift:183`).
- 이 전체 다시 그리기가 스레드 선택(`:422`), 새 글(`:540`), 답글 더미 펼치기(`:1123`), 방 전환(`:413`), 수신, 답변 수신 중 초당 30회 타이머(`:591`)에서 일어난다.
- 알림 클릭은 전환 애니메이션 직전에 전체 다시 그리기를 한 번 수행하고(`PetController.swift:217` 이하), 이후 목적지 스크롤을 0·0.15·0.45초에 세 번 다시 시작한다(`NativeThreadList.swift:143`). 전환 애니메이션과 스크롤 애니메이션이 같은 주 스레드의 60Hz 타이머를 쓴다.

[가정] 스크롤 끊김도 같은 원인이다. 확정되지 않았다(GAP-SM-01).

## 목표
같은 상태에서 다시 그릴 때 바뀌지 않은 글의 꾸미기와 높이 재기를 반복하지 않는다. 사용자 동작 한 번이 주 스레드를 붙잡는 시간이 예산 안에 든다. 창 전환 애니메이션 중에는 이 전환 때문에 생긴 전체 다시 그리기와 스크롤 애니메이션이 끼어들지 않는다.

## 범위
- 안: 대화 칸의 글 꾸미기·높이 재기 재사용, 글 내용에서 뽑는 순수 파생값(스레드 판정·달력 버튼 등)의 재사용(v3, 사용자 승인), 재사용 값의 폐기 조건, 알림 클릭 창 전환 경로의 겹침 제거, 여섯 증상의 계측과 전후 비교.
- 밖: 보이는 카드만 그리는 구조 개조. 화면 모양, 글자 나타나는 속도와 느낌, 스크롤 위치 규칙, 읽음·알림·정렬 의미. 통신·저장 형식·서버·문. 설치 앱 교체와 운영 설정.

## 제약
- 현재 갱신 계약 중 입력 이벤트의 국소 갱신, 수신 통지 통합은 유지한다. "렌더 범위가 끝나면 파생값을 버린다"는 약속은 v3에서 바뀐다. 시각에 의존하지 않는 순수 파생값은 입력이 같은 동안 다음 그리기까지 유지한다. 시각에 의존하는 값(알림 목록 등)은 시각을 입력에 포함하거나 기존대로 렌더 범위 안에서만 재사용한다. 완료 뒤 현재 명세에 반영한다.
- 재사용 값은 화면 표현 전용이며 저장하지 않는다. 개수 상한을 둔다.
- 계측용 계수기는 시험 전용 조건부 컴파일(`HEJO_PERF_TESTING`)로만 둔다. 제품에 개인 내용 기록을 추가하지 않는다.
- 시험은 임시 HERMES_HOME과 가짜 명부만 쓴다. 실제 메시지를 보내지 않는다.

## 예산의 근거
- [확인] 화면은 초당 60장이며 한 장은 약 0.0167초다.
- [제안] 동작 한 번의 점유 상한 0.100초는 사람이 즉각 반응으로 느끼는 한계로 널리 쓰이는 값이고, 중앙값 0.050초는 화면 3장이다. 현재 달성값이 아니다.
- [확인] 짧은 글 3,200개 fixture에서 지금의 방 전환은 약 0.111초다. 실제 글은 더 길어 더 오래 걸린다.
- [확인] 전환 애니메이션 길이는 0.30초다(`PetLayout.swift`의 `genieDuration`). 간격 상한 0.050초로 0.30초를 채우려면 단계가 6번 이상 필요하고, 마지막 간격까지 더한 종료 상한이 0.350초다.
- [확인] 처음 보는 방의 글은 실제로 처음 꾸며야 하므로 "안 바뀐 글 재사용"으로는 줄일 수 없다. 이 작업은 그 경우를 빠르게 만들지 못하며 악화만 막는다. 처음 진입이 여전히 거슬리면 기준 계측을 근거로 후속 범위를 사용자와 정한다(GAP-SM-02).
- 구현자는 예산을 완화하거나 입력을 줄일 수 없다. 미달하면 병목과 근거를 보고한다.

## 실패 뒤 남는 상태
재사용 값은 화면 표현 전용이므로 실패해도 저장 자료·초안·읽음 상태에 흔적이 남지 않는다. 낡은 값이 보이는 결함은 AC-02 위반이며 완료 불가 사유다.

## GAP-SM-01 스크롤 원인 미확정
1. 기대 의도: REQ-SM-05.
2. 실제 관측: 스크롤 경로의 계측이 없다. 목록은 응답형 스크롤을 끈 상태다(`NativeThreadList.swift:43`).
3. 차이: 다시 그리기 비용인지 카드 그리기 비용인지 가려지지 않았다.
4. 영향: 스크롤 전용 수정의 범위와 위험.
5. 선택지: TASK-01 기준 계측 뒤 (가) 재사용만으로 예산 충족 → 추가 작업 없음, (나) 미충족 → 원인 보고 후 사용자에게 범위 확인.
6. 결정: (가). 기준 계측에서 스크롤 한 걸음이 중앙값 0.00002초·최대 0.0102초로 이미 예산 안이다(3회 검토, 2026-11-24). 스크롤 전용 수정은 하지 않고 실제 창 관측으로 최종 판단한다.
7. 원본 갱신 대상: 이 spec의 AC-07, tasks의 TASK-04.
8. 재검증 상태: 기준 계측 확인. 실제 창 관측 미실행.

## GAP-SM-02 처음 보는 방 전환
1. 기대 의도: 사용자가 말한 "방을 바꿀 때"의 버벅임 해소.
2. 실제 관측: 처음 보는 방은 보이는 범위의 글을 모두 처음 꾸며야 한다. 계측값은 아직 없다.
3. 차이: 선택한 범위(안 바뀐 글 재사용)는 재방문만 빠르게 한다.
4. 영향: 앱을 켠 뒤 각 방의 첫 진입은 지금과 비슷한 지연이 남는다.
5. 선택지: (가) 이번에는 악화 금지만 적용하고 계측값을 본 뒤 후속 작업 여부 결정, (나) 꾸미기를 미리 해 두는 등의 범위 확대.
6. 결정: (가)를 계획에 반영. 첫 계획의 화면 승인으로 확인받는다. (나)는 계측 뒤 사용자 결정.
7. 원본 갱신 대상: 이 spec의 AC-05, 수락 시험 AT-SM-05.
8. 재검증 상태: 미실행.

## v3에서 확인된 사실
- [확인] 현실 길이 대화(8방×100스레드×4글)에서 다시 그리기 한 번은 수정 전 약 0.6초, 본문·높이 재사용 뒤 약 0.5초다. 원본은 구현 보고와 전용 작업 공간의 계측 요약이다.
- [확인] 남은 시간의 주된 자리는 사이드바가 부르는 알림·스레드 판정 계산(스택 표본의 약 55%)과 글마다 도는 달력 버튼 계산(약 19%)이다. 둘 다 글 내용만 바뀌지 않으면 결과가 같은 계산이다.
- [가정] 이 둘을 재사용해도 예산에 못 미칠 수 있다. 그 경우 구현자는 같은 원칙(입력이 같으면 결과가 같은 순수 파생값의 재사용)이 적용되는 병목을 계측으로 확인해 이어서 처리하고, 원칙 밖의 방법이 필요하면 멈춰 보고한다.

## v4 변경 (2026-11-24, 4회 검토와 사용자 승인)
