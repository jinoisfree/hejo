# 구현 검토 기록

## 최신 판정 — 7회차: M0 핵심 실물 관문 수락 / 전체 부분 완료

대상은 후보 `6621b74e0b78d1012d761924d9a664b8259534c1`의 개인 발신 재시험이다. 최신 m0-execution 보고와 비공개 retry-machine-result/observation, 공개 요약, 화면 원본 2개 및 해시를 직접 확인했다. 현재 설치된 세 제품 파일도 후보 해시와 일치한다. 증거는 [review-07/evidence.json](logs/review-07/evidence.json)에 민감값 없이 기록했다. 다른 작업의 변경/커밋은 이 판정에 포함하지 않는다.

### 확인한 증거

- 새 probe 1개, channel/forward/comment 세 receipt, 모두 deadline 이내, complete. 기존 짝·사장·지정 방 일치. 관측 도구의 실제 종료 0 기록과 결과를 대조했다.
- 검증자가 화면 두 장을 직접 열어 채널 시험 게시물의 댓글 1개와 동일 원문 아래 봇 시험 답장 1개를 확인했다. 화면 해시가 기록과 일치하고 원본 권한은 0600이다. 개인값을 포함한 원본은 공개 문서에 복사하지 않았다.
- journal 및 bind 목록 불변. source의 probe 경로는 receive/직원 실행으로 연결하지 않고 검토된 대역 시험에서도 실행 0을 확인했다. 실물 구간 전체의 직원 호출 trace를 별도로 확보한 것은 아니다.
- 안내 발신은 probe receipt에 포함되지 않으므로 세 receipt를 봇 송신 3건의 독립 계수로 해석하지 않는다. 실제 화면은 게시물/댓글 1개씩을 확인하며 안내 포함 전체 API 호출 횟수는 코드 경로와 보고에 의존한다.
- macOS 데스크톱 형태의 화면을 확인했으나 정확한 OS/Telegram 버전은 미확인이다. 이 한계를 유지하고 최종 M1~M6에서 버전을 기록한다. 모든 클라이언트 지원 증거로 일반화하지 않는다.

### 설계 적합성 — 4.2 및 처분

동일 봇의 게시물 자동 전달 수신과 원문별 댓글 표시가 실제 환경에서 확인됐다. 사람별 채널·게시물별 댓글이라는 설계의 핵심 가정이 충족됐고, 기존 gate/앱 무수정 경계도 유지된다. **V-05의 M0 핵심 가능성 미확인 차단은 해소**한다. 전체 제품 완료나 사용자 방 전환 완료는 아니다. 고위험 기능 전체의 독립 검토·최종 실물 수락은 후속 구현 뒤 별도 필요하다.

M0 관문은 TASK 2~4를 검토·착수할 수 있는 기술 조건으로 수락한다. 정확한 클라이언트 버전, 전체 직원 실행 추적, 안내 포함 발신 횟수의 독립 계수는 최종 실물 인계에 보완할 증거 한계로 기록한다. 재시험을 반복해서 이미 확인한 자동 전달을 다시 증명하도록 요구하지 않는다.

### 남은 작업과 원인 분류

전체 **부분 완료**. 원인 분류는 **환경·외부 요인(후속 구현 승인 범위 대기)**이며 기존 단계 계획에 남은 TASK 2~4 및 TASK 5 미수행이다. 새로운 구현 결함은 확인되지 않았다.

다음 실행 계획은 기존 승인된 4판 TASK 2(인증된 질문/댓글/첨부 수신), TASK 3(원문별 답변·첨부 발신, 중복/불확실 전송 복구), TASK 4(해제·복구·안내·회귀) 순서다. 사용자 구현 승인은 앞서 TASK 1과 M0로 한정됐으므로 후속 서버 구현·대역 시험 범위를 승인받아 전달한다. 승인 전 제품을 수정하지 않는다. 후속 구현 승인은 운영 배포·실제 bind·추가 실물 발신·푸시를 포함하지 않는다. 일반 댓글 기능 완성·검증 후 TASK 5의 단일 방 실물 수락 및 최종 고위험 검토를 거친다.

## 6회차: 신원 경계 조사 수락, 재시험 필요 / 부분 완료

검토 대상은 동일 후보의 명령 판별 코드와 새 조사 보고·민감값 제거 증거·비공개 auth-boundary-evidence 및 새 대역 시험이다. 네 작업 파일 해시가 조사 증거와 일치한다. 실제 Comments.command에 대한 가짜 입력 6개 시험을 검증자가 직접 실행해 종료 0을 확인했다. [실행 기록](logs/review-06/run.json), [로그](logs/review-06/pytest.log). 제품 전체 회귀는 바이트 무변경으로 반복하지 않았다.

시험 전 native factory 연결 성공, 시험 시각의 admission 완료 및 core 권한 거부, 발신자와 기존 짝 불일치가 증거에 있다. 두 로그의 같은 시각 거부는 하나의 사건으로 취급한다. 조사자는 사용자 제공 명령 형식 정상과 그룹 명의 익명 발신 화면을 확인했다고 기록했다. 이 검토에서 화면 원본을 다시 열지는 않았으며, raw Update도 없어 실제 sender_chat과 chat.type을 복원했다고 주장하지 않는다. 익명 발신에 따른 신원 불일치가 가장 강한 설명이나 전체 Update 경로를 직접 포착한 확정 증거와 구별한다. 뒤의 종료/primary_unavailable은 최초 거부보다 늦어 최초 원인으로 삼지 않는다.

### 설계 적합성 — 4.2

기존 짝 사장의 개인 명령만 허용하고 sender_chat 명령은 거부하는 설계와 실제 코드가 일치한다. 익명 발신 허용으로 인증을 완화할 이유가 없다. 제품 변경 없이 실행 전 개인 계정 발신 확인을 보완하는 처분을 수락한다. 자동 전달·댓글 묶음의 실물 적합성은 여전히 미확인이다.

원인 분류는 **환경·외부 요인(시험 입력의 신원 조건 불충족이 유력)**이며, 기획의 운영 안내에도 개인 발신 확인이 부족했다. V-05의 원인 조사 단계는 수락하지만 실물 통과 차단은 남긴다. 다음 재시험까지 제품 완료·TASK 2~4 착수는 금지한다.

재시험 계획: 기존 짝 사장 개인 계정으로 발신하도록 사용자가 익명/그룹·채널 명의 발신을 해제한 뒤, 동일 시험 그룹·직원 방에서 probe 1회와 정상 봇 발신 최대 3건을 별도 승인받는다. 재배포·재시작 없이 현재 후보/연결 상태와 동시 종료 작업 부재를 먼저 확인한다. 승인 및 관측 준비 뒤 정확한 기존 명령을 안내한다. 60초 관측 동안 probe 예약과 세 receipt·journal/직원 실행 여부·사용자 댓글 화면을 확인한다. 자동 재시험·bind·인증 완화·추가 발신은 금지한다. 새 종료나 연결 이상이면 발신 전에 보고한다.

## 5회차: M0 미통과, 전체 부분 완료

검토 대상은 운영 배포된 후보 `6621b74e0b78d1012d761924d9a664b8259534c1`이다. 최신 m0-execution 보고, 기존 impl-report와 실행 인계, 실제 배포 명령 기록, 최초/최종 probe 관측 및 제한 진단을 직접 읽었다. 현재 RELEASE와 설치된 세 gate 제품 파일의 SHA-256이 승인 후보와 일치한다. 배포·재시작 명령은 각각 종료 0으로 기록됐다. 별도 작업의 앱/문서 커밋은 검토 범위 밖이다.

### 실제 증거와 판정

[검토 증거](logs/review-05/evidence.json)에 민감값 없는 대조 결과를 기록했다. 최초와 약 60초 후 관측 모두 요약 도구 종료 0, `no_probe`다. 사용자도 무응답을 확인했다. journal 크기/해시는 시험 전후 동일하다. 실행 후 runtime의 running/Telegram connected/active_agents=0은 관측 시점의 상태이며 전체 구간 직원 호출 0의 독립 증명은 아니다.

M0는 **미통과**다. pending 예약이 생겼다는 증거 자체가 없으므로 deadline 초과나 자동 전달/댓글 API 기능 부재로 해석하지 않는다. 요약 도구 종료 0은 파싱 성공일 뿐 M0 성공이 아니다. 제품 코드가 이전 검토본과 같아 제품 회귀 시험은 반복하지 않았다. 이번 검토에서 probe·재시작·롤백·실제 발신을 수행하지 않았다.

### 설계 적합성 — 4.2

앱 무수정과 단일 gate 책임, 동일 봇 자동 전달을 실물 관문으로 확인하는 설계는 여전히 요구에 적합하다. 실패한 실물 시험을 대역 성공으로 대체하지 않는 관문도 지켜졌다. 다만 실물 수신과 native 처리기 접수까지의 연결을 입증하지 못해 실제 환경 적합성은 미확정이다. 제어 명령의 개인 계정·짝·supergroup·정확한 텍스트 조건과 native 처리기 등록/우선순위를 확인해야 한다. 코드상 명령은 @bot 접미사나 여분 공백을 받지 않지만 실제 전송문이 그 형태였다는 증거는 없으므로 원인으로 단정하지 않는다.

### 차단 지적과 원인

- V-05 (차단, 보낼 곳: 구현/환경 조사): REQ-HTC-05.AC-04 및 M0의 세 receipt·댓글 화면 증거 미충족. 위치는 native 수신부터 probe 예약 이전 경계. 받은 관측은 no_probe·무응답이며 댓글 실행 가능 여부를 판정할 수 없다.
- 원인 분류: **미확정**. 환경·외부 요인(전송 대상/봇 수신/처리기 등록)과 구현 오류(명령·신원·초기화 판정)를 구분할 증거가 부족하다. 기존 V-01~V-04 처분을 되돌릴 근거는 없다.

### 다음 수정·조사 계획

1. 기존 단일 gateway의 해당 시험 시간 구간 증거에서 후보 로드, hejo primary 준비, native factory 등록 성공/실패 및 우선순위를 읽기 전용으로 확인한다. Telegram connected만으로 등록 성공을 대신하지 않는다. 전체 로그나 개인정보는 출력하지 않고 관련 표식·오류 종류·횟수만 남긴다.
2. 이미 보낸 명령에 관한 자료로 전송 그룹 유형, 전송 봇, 기존 짝 사장과 개인 발신자 일치, sender_chat 유무, 실제 명령의 @bot 접미사/공백·방 키를 확인한다. 승인된 제한 자료가 없을 때만 사용자에게 기존 명령 메시지 내용을 요청한다. 토큰이나 전체 금고는 읽지 않는다.
3. 기존 receipt/admission 상태와 수신 계수에서 업데이트 도착 여부를 판별할 수 있는지 확인한다. 별도 getUpdates/webhook·봇 API 송신·두 번째 소비자는 만들지 않는다. no_probe를 근거로 자동 명령 재전송이나 구버전 복귀를 하지 않는다.
4. 대역으로 재현 가능한 결함을 찾으면 원인·재현·최소 수정안을 제출한다. 이 조사 인계는 운영 파일 수정·새 배포·추가 재시작·재시험을 허용하지 않는다. 수정 후보와 필요한 재시험 범위를 먼저 검토하고 승인받는다. 원인을 특정하지 못하면 관측의 한계와 필요한 정보만 반환한다.

전체 완료와 TASK 2~4 착수는 M0 및 사람 화면 증거 확보 전까지 차단한다. 후보는 현재 운영에 남아 있고 추가 운영 조치는 하지 않는다.

## 4회차: M0 로컬 준비 수락, 전체 부분 완료

별도 구현 대화의 M0 준비 보고와 기존 impl-report·handoff-m0, 실제 후보·복구 저장소 및 receipt 요약 도구를 기존 기획 대화에서 검토했다. 후보는 `6621b74e0b78d1012d761924d9a664b8259534c1`, 복구 원본은 `0bcf63535df381e491c99af9cbef41179b7cd79f`다. main의 별도 앱 작업 커밋은 이번 후보나 완료 증거에 포함하지 않는다.

직접 확인: 두 로컬 저장소 HEAD 일치·작업 트리 깨끗함·원격 없음, 후보 변경 목록 정확히 네 gate 파일, 검토된 네 파일 해시 일치, 기존 설치 42개 파일의 내용·실행 속성 일치. [integrity.json](logs/review-04/integrity.json)에 결과를 기록했다. 제품 바이트가 3회차와 같아 통과한 76개 제품 시험을 반복하지 않았다.

요약 도구 코드를 읽고 가짜 스냅샷 시험 6개를 직접 실행했다(종료 0). 입력 불변·식별자 비노출, 정상/누락/기한 초과 및 손상/중복/미지원 상태의 기대 결과를 확인했다. [summary-check.json](logs/review-04/summary-check.json). 운영 스냅샷에는 실행하지 않았다. 요약 도구는 마지막 probe의 제한된 상태를 보여 주므로 여러 시험을 섞지 않고 승인된 단일 시험과 대응시켜야 한다. 종료 0 자체는 M0 성공이 아니며 complete·세 receipt·일치 조건과 별도 화면 증거를 함께 판정한다.

### 설계 적합성 — 4.2

기존 봇의 단일 수신자 유지, 앱 무수정, 승인된 gate만 분리한 후보, 기존 설치 전체를 복구 원본과 대조하는 방식은 요구에 적합하다. 요약 도구는 제품 후보에서 제외된 읽기 전용 관측 보조이며 origin·실행 봇 동일성·직원 호출 0·화면 성공의 증거를 대신하지 않는다. probe 후 구버전 복귀 시 예약 차단이 사라지는 위험은 인계의 선행 유입 차단 조건을 계속 적용한다.

## 구체적 재개 계획과 남은 조건

1. 호스트에서 사용자 구현 승인 기록을 확인하여 승인된 계획 해시·범위와 함께 전달한다. 기록이 없다면 사용자 승인 절차를 거친다. 과거 문서의 승인 대기 문구는 작성 당시 상태이며 현재 승인 근거를 대신하지 않는다.
2. 승인 확인 후 기존 4판 TASK 1과 해당 대역 시험만 수행한다. 앱·본체·운영 설정은 변경하지 않는다. impl-report에 변경 파일, 대상 커밋/작업 트리, 실제 시험 명령·종료 코드·로그와 미실행 범위를 기록한다.
3. TASK 1 검토 후 M0 별도 인계에 실행 봇/서버·단일 수신자·배포 및 롤백·발신 범위를 고정하고 사용자 승인을 받는다. M0와 화면 증거 전 TASK 2~4를 시작하지 않는다.
4. 이후 기존 TASK 2~5, 고위험 독립 검토와 실물 수락을 충족해야 제품 완료를 판정한다. 지금은 현재 명세 반영이나 푸시 단계가 아니다.

기능 계약·수락 기준은 변경하지 않는다. 이번 반환 계획은 승인 및 구현 인계 누락을 해소하는 재개 절차다.
