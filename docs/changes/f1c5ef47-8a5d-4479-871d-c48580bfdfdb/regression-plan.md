# TASK-CS-04 보완: AT-UC-32 원인 분리

승인된 공개 통합을 검증·적용하기 위한 범위 내 보완이다. 사용자 적용 승인은 유지한다. 새 기능·새 공개 계약은 없다. 위험도 일반, 필요 증거 1·2·3 유지.

1. 기존 staged 통합본과 기준 원본 실행 파일·로그를 보존한다. 공개 작업 공간에서 app/Tests/UICleanPolishTests.swift에 진단을 추가하는 것을 허용한다. 필요하면 TestMain의 격리 진입점 또는 기존 fixture 정리 helper를 사용하되 운영 환경·시험 기준을 바꾸지 않는다.
2. 실패 직전 가짜 자료만 기록한다: 실제 FileChip title/replyWord/image 유무·갯수·순서, question의 모델 버튼/assessment, 선택 key·openThread·isHome, history의 표시/실현 영역, view/window 가시성·높이·프레임, 레이아웃 완료 시점. 실패를 어떤 항목이 일으키는지 먼저 분리한다. 동일한 실행 환경·시험 순서에서 기준/통합 각 1회로 비교하며 관측 없이 전체 재실행을 반복하지 않는다.
3. 같은 key를 두 번 chooseThread하면 접히는 구현을 확인했다. 시험이 의도한 ‘질문 스레드가 열린 상태’인지 관측한다. 고정 0.5초 뒤 검사와 실제 표시 완료의 차이도 확인한다. 스레드 선택, 전역 외관/창/타이머·기존 fixture 정리, 가상화에 의한 미실현을 구분한다. 새 연결 시험이 실행되기 전에 실패하므로 시간적 선후를 보존해 원인을 설명한다.
4. 시험 fixture/관측 오류가 증명되면 UICleanPolishTests 또는 해당 fixture helper에서 준비·정리·실제 완료 대기만 고친다. ‘승인·거절·의견·확인’ 네 개의 순서 및 이미지 없음 단언은 그대로 유지한다. 임의 sleep 증가·무한 대기·재시도 성공을 합격으로 채택·skip·오류 삼키기 금지. 유한 대기 기한은 기존 시험 규약 또는 실측 근거를 기록하며 실패 때 상태를 남긴다. 정렬로 잘못된 화면 순서를 숨기지 않는다.
5. 이번 ConnectionsWindow 수정의 실행 부작용이 원인이면 그 기존 책임에서 수정하고 동일 고장을 잡는 회귀 검사를 추가한다. 판단 버튼 제품 로직이나 공개 데이터/인증/저장 계약 변경이 필요하면 원인 증거와 최소 수정안을 보고하고 해당 변경은 착수하지 않는다. 이 조사 때문에 불필요하게 다른 앱·서비스를 종료하지 않는다.
6. 원인이 확정되지 않으면 남은 경쟁 가설과 구분 가능한 관측을 보고한다. 기준 1회 통과만으로 기존 시험 문제라고 단정하지 않는다. 기대값의 변경이 필요하면 계획 담당에게 근거를 돌린다.
7. 수정 후 같은 기본 앱 전체 순서에서 원래 실패가 사라졌는지 확인한다. 공개 통합 최종 트리의 bash scripts/test.sh를 격리 환경에서 끝까지 실행하고 개인정보·설정 메타데이터 보존·새 AC·전체 후속 fixture를 확인한다. 미변경 구간 재사용 여부를 명시하되 전체 앱 회귀를 분리 시험만으로 대체하지 않는다.
8. 통과 후 application-plan TASK-CS-04~05를 이어서 수행한다. 원격 최신 기준 확인·필요한 통합·커밋·배포 빌드·새 백업·정상 종료·교체·실제 실행 확인. 이미 사용자 승인됐으므로 다시 설치 허락을 묻지 않는다. 실패 시 기존 번들을 보존/복구한다. 직접 Git 푸시는 금지다.
9. 원본 impl-report에 원인 분류·관측·수정 전후·최종 커밋·전체 로그·설치 증거를 기록한다. 배포 문서 사본은 이번 원본의 최신 판정/보고와 맞추고 완료 전 문서를 적용 완료로 미리 표시하지 않는다. 공개 통합 원본 및 개발 worktree를 보존한다.
