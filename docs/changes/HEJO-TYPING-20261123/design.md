# 설계 v3

칸·원본은 [spec](spec.md)의 표를 따른다. 내부 버그이므로 외부 기술 조사는 생략했다.

[확인] 입력→serialize→setText→홈 refresh→sidebar/threads/threadContent/history.show→composer→drawer→needsLayout 흐름이다. 높이 변경은 이미 editor.onHeight에서 실제 높이 차이가 있을 때만 needsLayout을 설정한다(ConversationView.swift:170). DraftScrollView.measure는 텍스트 레이아웃을 측정한다. 이 경로는 우선 유지하며 계측으로 추가 병목이 확인될 때만 같은 책임 안에서 줄인다.

[제안] 입력 이벤트에서는 초안을 즉시 저장하고 입력에 의존하는 받는 사람 강조·힌트·전송 가능 상태·서식 표시·높이만 갱신한다. 전체 refresh와 입력 경로가 같은 입력 표시 계산을 공유하도록 기존 composer 부분을 국소적으로 추출한다. 전체 refresh의 모델/방 전환·외부 초안 복원과 사용자 편집 중 표시 갱신은 구분하여 편집 중 textStorage 교체나 undo 초기화가 발생하지 않게 한다. 한글 marked text 보호와 멘션 완성은 기존 AppKit 경로를 유지한다.

| 기존 경로 | 판정 | 근거 |
|---|---|---|
| textDidChange의 홈 전체 refresh 호출 | 교체 | 입력 표시 갱신으로 바꾸고 옛 호출 제거 |
| 전체 refresh 안 입력 의존 표시 계산 | 통합 | 단일 계산을 두 호출자가 사용, 중복 수신자 규칙 금지 |
| controller.setText·drafts·전송·수신 통지 | 유지 | 초안 원본 및 전달 계약 보존 |
| DraftEditor 입력/조합/높이 | 유지 | 계측 없는 재작성 금지 |
| 목록·서랍·알림 계산 | 유지 | 문자 입력에서만 호출 차단, 모델 변경에는 그대로 실행 |

대안: 전체 refresh를 debounce하는 방식은 불필요한 일을 남기고 수신 표시 지연·초안 전환 순서를 흔들 수 있어 기각. 별도 초안 저장소/전역 캐시도 추가하지 않는다.
위험도 일반: 앱 화면 갱신 버그 수정, 영구 저장/권한/동시성 계약 변경 없음. 증거 수준 1(빌드), 2(가짜 모델 통합), 3(실제 AppKit 창 입력). 되돌림은 이 작업 diff만 역적용하고 앱 후보를 폐기한다. 데이터 이관 없음.

## 기준 불일치와 착수 확인
[확인] 추적되지 않은 docs/spec/current/hejo-performance.md는 적용 커밋 221e84082a4230caca6b450cb3b2e0ee9d085ee8을 명시한다. git merge-base --is-ancestor <그 커밋> <base_commit>는 종료 1이었다. 현재 View에는 해당 문서의 렌더 범위 캐시 호출을 확인하지 못했다. 이전 작업 문서만 보고 현재 브랜치나 설치 앱에 반영됐다고 가정하지 않는다.
TASK-00에서 해당 커밋의 실제 diff와 배정 브랜치, 설치 앱 빌드 식별자를 읽기로 대조한다. 필요한 성능 변경이 배정 소스에 빠져 있거나 다른 진행 작업과 겹치면 제품 수정 전에 근거를 보고하고 기준 통합 결정을 받는다. 자동 cherry-pick/merge 또는 문서 계약 하향은 하지 않는다. 독립적인 입력 경로 계측은 진행 가능하다.

## 계획 검토 반영
- 전송 버튼은 spec AC-02의 단일 조건을 전체 갱신과 입력 갱신이 공유한다. 공백만 있는 본문·첨부 없음은 비활성, 첨부가 있으면 선택/연결 조건 충족 시 활성이다. 선택 없음 또는 연결 불가는 항상 비활성이다. 초안의 원문 공백을 지우거나 sendCurrent의 대상/전송 계약을 바꾸지 않는다.
- TASK-00은 홈·직접방·단체방 각각의 입력과 지연을 별도로 기록한다. 직접방/단체방의 전체 refresh 비호출은 기준에서도 통과할 수 있다. 홈 외 지연은 같은 원인으로 단정하지 않고 serialize/measure/자동완성/주변 수신 작업의 기여를 조사해 보고한다. 범위 밖 원인이 확인되면 계획 담당에게 반환한다.
- 성능 커밋이 든 브랜치와 main 중 어느 것을 구현 기준으로 할지는 설치 빌드·두 브랜치 변경·진행 작업의 비교 후 결정한다. 현재 base_commit은 조사 기준이며 구현 기준 확정으로 보지 않는다. TASK-00의 비교 결과를 계획 담당에게 반드시 반환하고 새 기준을 고정한 인계 전 TASK-01을 시작하지 않는다.
- 기존 성능 하네스는 221e84082a4230caca6b450cb3b2e0ee9d085ee8의 app/Tests/HejoPerfTests.swift, HejoPerfRegressionTests.swift, hejo_perf.py와 Fixtures/HejoPerf에 있다. 현재 HEAD에는 없다. 기준 비교 단계에서 재사용 가능성·의존 파일·실제 키 입력 측정 지원 여부를 함께 조사한다. 성능 브랜치를 기준으로 정하면 기존 가짜 데이터/하네스를 우선 확장하고, main을 택할 경우 필요한 시험 전용 부분의 이관 범위를 먼저 계획 담당이 확정한다. 동결 기대값을 재생성하거나 성능 제품 코드를 시험 도구에 섞어 가져오지 않는다. 신규 하네스는 재사용 불가능 근거가 있을 때만 제안한다.

## TASK-00 검토 후 확정 — v3 (앞선 기준 미확정 절을 대체)

현재 개발 기준 `6bf9c3c6f6b9c563e3b4d44bf69d1014569579c0`에 고정 성능 개발 커밋 `221e84082a4230caca6b450cb3b2e0ee9d085ee8`을 merge하여 구현 기준을 만든다. 공통 조상은 `39f954c1bd3a50fd27d4f11a3b03774d0e74aa41`. 현재 기준 쪽 변경은 문서뿐이며 성능 커밋의 제품은 app의 기존 책임 5파일이다. 단순 파일 복사보다 선행 동결 시험 커밋까지 계보를 보존하는 개발 이력 merge를 택한다. 성능 브랜치의 후속 문서 tip이나 공개 snapshot 커밋은 가져오지 않는다. 현재 근간·텔레그램·UI 문서를 보존하며 공개 이력과 개발 이력을 합치지 않는다. 예상 밖 제품 변경/의도 충돌이 발견되면 임의 해결하지 않고 보고한다.

통합 직후 새 HEAD·부모·diff를 기록하고 이 커밋을 입력 수정 전 기준으로 고정한다. 성능 제품 API와 원래 하네스/fixture/TestMain/app 시험 스크립트는 함께 유지한다. 홈 refresh는 해당 성능 커밋에도 남아 있어 통합만으로 사용자 문제 해결로 판정하지 않는다. 성능 통합과 새 입력 수정은 별도 커밋으로 구분한다.

시험 도구는 기존 가짜 fixture와 View 조립을 재사용하되 입력 전용·수신 병행·단체방·갱신 횟수 측정을 추가한다. 기존 동결 fixture와 HP 시험 의미는 불변이다. 준비/fixture/최초 refresh/layout/warm-up/입력 제출·시작·완료에 시각과 단계 로그를 남기고 회차별 결과를 즉시 저장한다. timeout 발생 시 자식을 종료하고 회수한 실제 종료 코드, 마지막 단계, 표본 수를 남기며 관리 프로세스도 실패로 종료한다. 180초 timeout을 입력 지연으로 환산하지 않는다. 기준의 장시간 실행이 막히면 단계 증거를 보존하고 예산·입력을 완화하지 않은 채 반환한다. 기존 실패 probe는 같은 조건으로 무작정 반복하지 않는다.
