## 2. 요구·수락 기준

REQ-GD-01~05, NFR-GD-01~02의 전체 AC. 해제 시 해당 직원 계정 표시·사용·전용 자격 제거, 다음 연결은 새 계정 선택, 공용 자격/다른 직원 보존, 취소/실패/늦은 완료/동시 처리에 안전해야 한다. 기존 Google 기능을 화면만 남기거나 삭제하여 통과하지 않는다.

## 3. 유지할 계약

다른 서비스 해제·회사 OAuth·역할별 권한·쓰기 승인·배경 제한·기존 Google 명령 기능/출력을 유지한다. Hermes 본체 및 ddots는 수정하지 않는다. 문은 플랫폼 플러그인 계약만 사용한다. 운영 비밀 파일 열기, 실제 Slack/고객 메시지 전송, 에이전트 git push는 금지한다. 토큰을 앱이나 공개 저장소에 보관하지 않는다.

## 4. 책임·흐름

앱 → 문(기기/직원/작업 소유권 검사) → 기존 account CLI → 직원별 Google 연결 시설 → 사장 금고·전용 인증. 메일·캘린더·Workspace·worker는 같은 시설의 계정/자격을 읽고 기존 팩이 업무·승인 경계를 집행한다. 시설 원본을 config·별도 장부의 계정 사본으로 대체하지 않는다.

## 5. 기존 경로 판정

상세는 design 소비자 표. 전환 직원 개인 연결의 공용 토큰 fallback·상태만 켜는 재연결·공용 계정 단위 poll·즉시 undo는 제거한다. 미전환 직원/회사 경로는 호환 유지한다. 공존 기준은 금고 직원 항목 존재 여부이며 항목이 생긴 직원은 다시 기존 경로를 선택하지 않는다. 지원되는 직원 모두가 전환되고 기존 참조가 사라진 뒤에만 공용 개인 호환 경로의 철거를 별도 판단한다. 이번 작업에서 공용 토큰을 정리하지 않는다.

## 6. 위험·증거·롤백

고위험: 인증·개인정보·삭제·동시성·영구 원본. 증거 2(격리 통합), 3(실제 AppKit), 4(사용자 직접 OAuth). 계획 독립 검증과 구현 비참여 모델 검증 필요. 설계자 검증 외 고위험 결과 검토도 필요하며 별도 리뷰는 호스트가 처리하거나 사용자가 검토한다. 자동으로 다른 에이전트를 만들지 않는다.

기존 app_connect의 before 바이트 장부는 자격/금고 전체 저장에 사용하지 않는다. 해제는 먼저 접근을 차단하며 부분 삭제 실패를 완료로 숨기지 않는다. 전환 원본이 있는 동안 이를 모르는 구버전 배포·롤백을 차단한다. 복구는 미연결 보존·기능 비활성·수정 버전/재인증으로 한다. 상세는 design.

## 7. 변경 성격

의미 변경. Google 개인만 ‘잠시 끔/값 재사용’에서 ‘직원 연결 제거/계정 선택’으로 바뀐다. 다른 서비스와 미전환 기능은 전후 동일 fixture로 비교한다. 기존 Google 개인 보존 수락 기준은 새 spec 적용 범위에서만 대체한다.

## 9. 작업 범위·선행·병렬

첫 구현 인계는 TASK-01~05(개발·격리 검증·운영 인계 준비)다. TASK-06 실제 운영 변경은 별도 승인 전 금지. TASK-07은 기획설계·검증 담당 소유.

## 10. 가정·미확정과 차단 범위

- OAuth 클라이언트의 실계정 허용 사용자/권한/동의 화면은 미확인. 운영 비밀 파일을 열어 조사하지 않는다. 개발은 가짜 공급자로 진행 가능하며 실제 인증 TASK-06에서 확인한다.
- 같은 Google 계정을 여러 직원이 고르는 경우도 파일·연결은 직원별 분리한다. 외부 제공자의 세션 유지나 토큰 발급 정책을 앱이 바꾼다고 약속하지 않는다.
- 운영 설치/재시작·실계정 동의는 미승인. TASK-01~05를 차단하지 않는다.
- 5판 계획 검증은 통과했다. 계획 재검증 완료를 제품 구현 완료로 취급하지 않는다. 운영 적용·푸시 승인은 별개다.
- 새 소비자·본체 의존 계약이 발견되어 설계와 다르면 기획에 보고한다. 본체 수정/기능 삭제로 우회하지 않는다.

## 11. 사용자 확인

사용자가 해제 시 직원 연결 제거와 다음 연결 시 계정 선택을 골랐고, 연합개발·계획 검증 켜기를 선택했다. 직원별 금고 원본과 전용 인증 위치 배치 제안에 ‘너의 추천대로 진행하자’라고 승인했다. 운영 실행/푸시 승인은 포함하지 않는다.

## 인계 전 점검

G1: 사용자 방향·범위와 spec AC 작성. G2: 기준 소스와 소비자·스키마·기존 경로 판정 기록. G3: 수락 명세 연결 완료, 5판 독립 계획 검증 APPROVED. G4: 위험·복구·작업 분해·운영 경계 기록, 실제 착수 전 격리 공간 및 base 변경 영향 확인 필요.

확인한 기준 커밋은 동일하나 두 저장소 모두 dirty다. 변경 중인 다른 작업을 포함한 깨끗한 기준이라고 주장하지 않는다. 격리 착수 때 영향 파일 차이를 확인하고 동작 차이가 있으면 기획에 반환한다.

문서 자체 점검: 6개 Markdown의 로컬 링크, AC 중복, AC→시험 전체 연결, 저장소 검사기의 일반 개인값 패턴을 Python으로 검사해 종료 코드 0. AC 16개·시험 명세 20개. 로그: `.build/google-disconnect-plan/document-check.log`. 이 검사는 운영 금고와 명부를 읽지 않았으므로 전체 개인값 검사/제품 시험/독립 계획 검증을 대신하지 않는다.
