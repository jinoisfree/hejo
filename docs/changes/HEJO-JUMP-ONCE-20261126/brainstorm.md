## 목적
가운데 카드창의 카드를 누르면 대화가 한 번에 이동해 멈추고, "갱신 중" 표시 때문에 화면이 밀리지 않는다. 누르면 기다림 없이 움직인다.

## 하는 것 / 하지 않는 것
- 한다: 이동을 한 번으로(목적지 하나), 카드창에 뜬 카드의 대화 미리 받기, "갱신 중"을 자리 차지 없는 표시로, 글 안내는 아래쪽으로, 같은 이동을 쓰는 다른 입구(알림 섬, 말풍선에서 열기, 검색 결과, 방 알림 줄)에도 적용.
- 하지 않는다: 문·허브·기록장 형식·통신 규격 변경, 카드창의 카드 내용·정렬 변경, 선택이 바뀔 때 도는 전체 갱신의 구조 변경(화면에 드러나지 않게만 한다), 새 버전 빌드·배포.

## 실측
- [확인] 카드 클릭 한 번에 이동 명령이 6번 나간다. `ConversationView.selectDrawerCard`가 `history.scrollTo(key.thread)`를 부르고, `NativeThreadList.scrollTo`가 0·0.15·0.45초에 각각 감속 이동을 시작한다. 본문을 받은 뒤 `HistoryCoordinator`의 `onAnchor`가 `scrollTo(thread,message:)`로 다른 목적지(글 가운데)에 세 번 더 이동한다.
- [확인] 선택이 바뀌면 `HistoryCoordinator.inputsChanged`가 진행 중 작업을 취소하고 전체 갱신을 시작하며 `history.refreshing`이 켜졌다 꺼진다.
- [확인] 갱신 중이면 카드창은 경고 줄을 카드 위에 끼우고(`TodoDrawerView.show`), 대화 목록은 맨 위에 `history-status` 줄을 끼운다(`ConversationView.refresh`).
- [확인] 영상에서 카드창 경고 줄이 약 0.3초 나타났다 사라지며 카드가 한 줄만큼 오르내린다. 대화는 0.5~1초에 걸쳐 여러 단계로 움직인다. 픽셀 값은 영상 해상도 때문에 재지 못했다.
- [미확정] 클릭으로 읽음이 바뀌어 갱신이 한 번 더 도는지. TASK-01 기준본 기록에서 확인한다.

## 선행 조사
생략. 앱 자체 스크롤 코드의 중복 호출과 표시 위치를 고치는 일이라 가져다 쓸 외부 기술이 없다.

## 대안과 선택
| 항목 | 선택 | 기각 |
|---|---|---|
| 이동 방식 | 준비되면 한 번만 이동(사용자) | 즉시 점프(어디로 갔는지 따라가기 어려움), 바로 출발 후 목적지만 통일(받는 동안 보정이 남음) |
| 속도 | 카드창에 뜬 카드의 대화를 미리 받아 둠(사용자) | 누른 뒤 받기만(기다림이 생김) |
| 갱신 표시 | 자리 차지 없는 표시 + 글 안내는 아래쪽(사용자) | 짧은 갱신만 숨김(오래 걸리면 다시 밀림), 줄 자리 고정(빈 줄이 늘 남음) |
| 범위 | 다른 입구도 함께(사용자) | 카드 클릭만 |

## 가정
- 사용자 결정: 위 표의 네 선택.
- 에이전트 제안: "함께 모두 고치자"에서 전체 갱신 자체는 줄이지 않고, 갱신이 돌아도 미리 받은 대화가 버려지지 않고 화면이 움직이지 않게 하는 것으로 범위를 잡는다. 조사 결과 갱신 중에도 받은 값은 화면에 남는다(`HistoryProjection.beginContext`의 주석과 코드).
- 에이전트 제안: 미리 받는 범위는 카드창에서 보이는 카드와 그 위·아래 한 화면(HEJO-AUTOLOAD의 "받는 범위"와 같은 규칙). 새 숫자를 만들지 않는다.
- 에이전트 제안: "갱신 중"은 글 없이 작은 표시(↻)로, 실패·경고 문구는 아래쪽 고정 줄로.

## 열린 질문
- 표시(↻)의 정확한 자리와 아래쪽 안내 줄의 모양은 구현 담당이 시안 그림을 만들고 사용자가 본다(수락 시험 AT-JO-15).
