## 1. 문제와 목표

- 문제: 사장이 가운데 칸(처리할 일)의 답 요청 카드를 이미 봤어도, 대화를 열어 답을 쓰기 전에는 카드가 남는다. 마감 카드는 우클릭 두 번이 필요하다.
- 목표: 카드에 마우스를 올려 ✓ 띠를 한 번 누르면 5초 되돌리기 뒤 종결된다. 답 요청 카드는 직원에게 "확인" 글이 가고, 직원이 답하면 그 스레드는 기존 규칙대로 초록(완결)이 된다.

## 2. 범위

- 안: 답 요청·마감·알림 카드의 ✓ 띠, 알림 카드 직접 선택 시 읽음 처리 결함 재현·수정(REQ-CD-07), 답 요청 "확인" 전송과 되돌리기, 마감 "완료로 닫기" 단축, 되돌리기 줄 하나 규칙, 실패 표시, 손쉬운 사용 동작.
- 밖: 문(gate)·안내판·직원 규칙·저장 형식, 대화 안 "확인"·답 버튼 동작, 우클릭 메뉴 항목, 앱 빌드·배포(별도 릴리스 작업), `docs/spec/current` 반영(TASK-02).

## 3. 요구와 수락 기준

**REQ-CD-01 ✓ 띠 표시.** 카드에 마우스가 올라가 있는 동안 종결할 수 있는 카드의 오른쪽 끝에 카드 높이 전체, 폭 44pt의 초록 띠와 흰 ✓가 그려진다.
- AC-01(정상): 종결할 수 있는 카드 = (a) 답 요청 카드 중 대화 키·글 id가 있고 문 연결로 보낼 수 있는 것(`canSend`) (b) 마감 카드 중 마감 참조(`deadlineRef`)가 있는 것 (c) 알림 카드 중 대화 키가 있는 것(3판, REQ-CD-06).
- AC-02(경계): 마우스가 없으면 띠가 없고 카드는 지금과 같게 그려진다. 띠가 보이는 동안 시간·상태 글자는 띠 아래에 그려지지 않는다(띠 왼쪽 8pt 앞에서 말줄임).
- AC-03(실패): 문 연결이 끊겨 보낼 수 없으면 답 요청 카드에 띠가 없다. 마감 카드는 우클릭 메뉴와 같은 조건으로 띠가 있다.

**REQ-CD-02 띠 누르기.** 띠를 누르면 대화로 이동하지 않고 종결 동작만 한다. 띠 밖을 누르면 지금처럼 대화로 이동한다.
- AC-01(정상): 답 요청 카드의 띠 → 카드가 즉시 목록에서 빠지고 아래 되돌리기 줄 `‘<제목>’ 확인 보냄 · 되돌리기`가 나온다. 5초가 지나면 그 카드의 대화(카드의 대화 키, 받는 사람 = 카드의 직원)로 글 `확인`을 한 번 보낸다. 보내는 길은 사장이 그 스레드에서 글을 쓸 때와 같은 전송 경로다.
- AC-02(정상): 마감 카드의 띠 → 우클릭 "완료로 닫기"와 같은 동작(`outcome = done`, 기존 되돌리기 줄 `‘<제목>’ 닫음 · 되돌리기`).
- AC-03(경계): 5초 안에 "되돌리기" → 아무것도 보내지 않고 카드가 다시 나온다.
- AC-04(경계): 되돌리기 줄은 하나다. 기다리는 것이 있을 때 다른 카드의 띠나 우클릭 닫기를 누르면 기다리던 것을 바로 보내고 새것이 5초를 기다린다(종류가 섞여도 같다).
- AC-05(경계): 5초 안에 앱이 끝나면 기다리던 것은 보내지 않는다.
- AC-06(경계): 같은 카드를 두 번 보내지 않는다. 기다리는 중·보내는 중·문 반영 대기 중인 답 요청 카드는 목록에 나오지 않는다.
- AC-07(정상): 직원이 정한 버튼이 있는 요청이어도 띠는 버튼을 누르지 않는다. 나가는 프레임은 `send` 한 건(`text="확인"`)뿐이고 `click` 프레임은 0건이다.

**REQ-CD-03 보낸 뒤 결과.** "확인" 전송의 결과는 기존 전송 경로가 그 글의 `client_msg_id`로 정하는 네 가지 중 하나다. 카드 ✓는 어떤 경우에도 스스로 다시 보내지 않는다(같은 카드의 자동 추가 전송 0건).

| 결과 | 기존 경로에서 정해지는 때 | 카드 | 카드창 경고 |
|---|---|---|---|
| ① 즉시 실패 | `sendText`가 `false`(연결 없음·대상 확인 실패·쓰기 시작 전 오류) | 그때 다시 보임 | 있음 |
| ② 사후 거절 | 문이 `type=error`, `ref=<그 client_msg_id>`를 보냄, 또는 재연결 뒤 `sync_done`에서 미확인으로 실패 처리 | 그 프레임 처리 때 다시 보임 | 있음 |
| ③ 결과 미확정 | 기록 모드에서 쓰기 시작 뒤 오류로 대기 글(`pending`)이 남음(기존 "전송 결과를 확인하고 있어요.") | 결과가 정해질 때까지 숨김. 보낸 때부터 75초가 지나면 다시 보이되 그 카드에는 띠·VoiceOver 동작이 없다. 뒤에 ④가 되면 ④, ②가 되면 ② | 없음(기존 미확정 알림 그대로) |
| ④ 접수 | 같은 `client_msg_id`의 글이 돌아옴, 또는 영수증 `accepted`/`deleted` | 문 답 요청 목록에서 그 글이 빠질 때까지 숨김. 접수 때부터 75초 안에 안 빠지면 다시 보임(띠 있음) | 없음 |

- AC-01(정상, ④): 접수 뒤 목록에서 빠지면 숨김이 풀리고 카드가 없다. 목록에 그 글이 다시 생기면 다시 보인다.
- AC-02(실패, ①·②): 카드가 다시 나오고 카드창 경고 줄 `확인을 보내지 못했어요. 다시 해 주세요.`가 나온다. 기존 전송 실패 표시(섬 `transferFailure`, 그 스레드 실패 초안에 "확인" 복원)는 지금 전송 경로 그대로다. 다음 ✓ 누르기나 카드창을 다시 열면 경고가 지워진다.
- AC-03(경계, ③): 위 표 ③. 75초 뒤 다시 보인 카드를 눌러도 아무것도 보내지 않는다(띠가 없음).
- AC-04(경계, ④ 상한): 접수 뒤 75초 안에 목록에서 빠지지 않으면 다시 보이고 경고는 없다. 75초는 마감 닫기 응답 대기(`closeResponseSeconds`)와 같은 값이다.

**REQ-CD-04 초록 완결(기존 규칙 회귀).** 직원 요청 글 → 사장의 일반 글 `확인`(answer_to 없음) → 직원 글(작성 완료) 순서의 스레드는 문과 앱 모두 완결(settled)로 판정하고, 사장 글이 마지막인 동안에는 답 요청 카드가 없다. 이 작업은 판정 코드를 바꾸지 않는다.

**REQ-CD-05 손쉬운 사용.** 종결할 수 있는 카드는 VoiceOver 사용자 동작 하나를 가진다: 답 요청 = `확인 보내기`, 마감 = `완료로 닫기`. 동작은 띠 누르기와 같다.

**REQ-CD-06 알림 카드 ✓(3판, D-06).** 알림 카드의 띠를 누르면 되돌리기 없이 즉시 그 알림을 읽음 처리한다. 쓰는 길은 사장이 알림 카드·스레드를 직접 골랐을 때의 기존 읽음 처리(`markNoticeRead` → 기록 모드 `notice` 읽음 요청, `bell:`·`thread:` 기록)와 같다. 직원에게 글을 보내지 않고 대화로 이동하지 않는다.
- AC-01(정상): 띠 누름 → `notice` 읽음 요청 1건(그 카드의 대화 키), 성공 뒤 카드가 목록에서 빠진다. 되돌리기 줄은 나오지 않고, 기다리던 다른 되돌리기는 건드리지 않는다.
- AC-02(실패): 읽음 요청이 실패하면 기존 REQ-AS-01처럼 키가 바뀌지 않고 카드가 남는다. 다시 누르면 다시 요청한다.
- AC-03(경계): 요청 중 같은 카드를 다시 눌러도 요청은 1건이다. VoiceOver 동작 이름은 `읽음으로 표시`다.

**REQ-CD-07 직접 선택하면 알림이 꼭 빠진다(3판, D-07 결함).** 사장 보고: 알림 카드나 스레드를 직접 눌렀는데도 알림이 남는다. 현재 명세 REQ-AS-01의 직접 선택 입구(가운데 창 카드 클릭·Enter·화살표, 채팅 스레드 클릭, "답글", 말풍선·섬, 검색 결과, 스레드 링크, "의견")는 어떤 상태에서 눌러도 그 스레드의 알림을 읽음 처리해야 한다.
- AC-01(재현 범위): 기록 모드 실제 하네스에서 아래 상태마다 직접 선택 입구를 눌러 카드가 빠지는지 본다. (a) 그 스레드가 이미 선택·활성 상태(앱이 방에 들어갈 때 자동으로 잡은 스레드 포함)에서 다시 누름 (b) 채팅이 열려 그 스레드를 보고 있는 동안 그 스레드에 새 알림이 생긴 뒤 누름 (c) 홈 방(펫 이름 방)·직원 방·단체방 각각 (d) 기록 갱신 중(`refreshing`)에 누름 (e) 카드창에서 화살표로 고른 뒤 Enter.
- AC-02(정상): 재현된 실패마다 원인 자리에서 고치고, 고친 뒤 모든 (a)~(e)에서 `notice` 읽음 요청이 나가고 카드가 빠진다. 앱이 자동으로 잡은 답글 대상 자체는 지금처럼 읽음 처리하지 않는다(사장이 누를 때만).
- AC-03(재현 안 됨): (a)~(e)가 기준본에서 모두 통과하면 제품을 고치지 않고 그 결과를 보고한다(기획설계가 사장에게 실제 사례를 받는다).

**NFR-CD-01 한 원본.** 되돌리기 대기·전송은 컨트롤러의 한 대기 자리를 쓴다(마감 닫기와 공유). 마감 닫기 경로를 복제하지 않는다. 새 저장·새 프레임·문 변경 없음.

**NFR-CD-02 회귀 없음.** 기존 시험(`bash scripts/test.sh`)에서 착수 커밋 대비 새 실패가 없고 개인값 검사(`scan_private.py`)를 통과한다. 우클릭 메뉴·카드 클릭·화살표·Enter 동작은 그대로다.

## 4. 실패 후 남는 상태

- 되돌리기·앱 종료: 아무것도 보내지 않음, 저장 변화 없음.
- 전송 실패(①·②): 기록장 변화 없음, 카드 다시 보임, 경고 줄, 그 스레드 실패 초안에 "확인"(기존 전송 경로 동작).
- 결과 미확정(③): 기존 대기 글 유지, 카드는 띠 없이 75초 뒤 보임.
- 마감 닫기 실패: 기존 동작(`마감을 닫지 못했어요. 다시 해 주세요.`).
