## 3. 바뀐 뒤의 책임과 흐름

- **대화 목록(`NativeThreadList`)**: 받는 범위에 걸친 **카드 id**와, 펼친 스레드에서 받은 답글의 맨 위·맨 아래가 범위에 들었는지를 알린다. 지금의 "보이는 글 id" 알림은 고정(pin)용으로 그대로 둔다.
- **대화 화면(`ConversationView`)**: 그 알림을 조정자에 "지금 필요한 것 목록"으로 넘긴다. 버튼 조각을 그리지 않고 로딩/실패 조각을 그린다.
- **조정자(`HistoryCoordinator`)**: 유일한 요청 주체로 남는다. 자동 요청은 "필요한 것 목록"에서 매번 다시 계산한다(일회성 줄 세우기가 아님). 그래서 선택 변경으로 줄이 비워져도 다음 알림에서 다시 채워지고, 범위를 벗어난 대기 요청은 보내지 않는다.

지켜야 할 조건:

1. 자동 요청은 선택·펼침·읽음·스크롤을 건드리지 않는다. `onAnchor` 스크롤과 `select`는 사용자가 직접 열 때만 일어난다.
2. 자동 요청 하나의 실패는 그 대상(스레드 또는 글)에만 기록한다. 조정자 전체 실패 상태(`failure`)나 화면 맨 위의 "대화를 불러오지 못했어요" 카드로 번지지 않고, 줄의 다른 요청을 막지 않는다. 연결 끊김처럼 모든 요청이 실패하는 경우는 기존 전체 실패 표시를 그대로 쓴다.
3. "다시 시도" 표시가 된 대상은 그것을 누르거나 새 연결(session)이 맺어지기 전에는 자동으로 다시 요청하지 않는다. 어떤 실패가 이 표시가 되는지는 조건 11이 정한다.
4. 최근 답글(REQ-ALD-04): 가진 마지막 답글을 가리켜 조회해 바로 다음 쪽을 받는다(닿을 때마다 한 쪽). 최신 쪽으로 건너뛰지 않으므로 빈틈이 생기지 않는다. 스크롤은 옮기지 않는다.
5. 요청 순서는 지금처럼 한 번에 하나다. 대기 대상은 보이는 영역에 걸친 것이 앞서 받기 대상보다 먼저다.
6. 선택된 스레드: 목록 갱신의 선택 스레드 요청은 그대로 갱신이 소유한다(범위 무관, 실패는 갱신 실패). 자동 경로는 "앱에 본문이 있는가"로 필요 여부를 판단하므로 갱신이 받은 스레드를 겹쳐 요청하지 않는다. 문맥이 새로 발급돼도 이 판단은 바뀌지 않는다. 갱신이 받은 쪽에 원문이 없으면 자동 경로는 원문만(id 지정 조회) 받는다.
7. 답글 쪽 상태의 분리: 다음 쪽(조건 4)을 받은 응답이 그 스레드의 이전 쪽 커서를 덮어쓰지 않는다. 이전 쪽 커서와 "더 최근 답글이 남았는가"는 따로 기억한다.
8. 맨 위 닿음(`loadOlder`)의 세 가지 중 **비워진 본문 복원만** 받는 범위 알림으로 옮긴다. 목록 창 넓히기와 이전 스레드 쪽 요청은 `loadOlder`가 그대로 소유한다.
9. 목록 갱신 실패 중의 대기열: 조정자가 갱신 실패 상태인 동안 자동 요청은 나가지 않고, 자동 요청을 넣는 일이 그 실패 상태를 지우지 않는다. 대기 대상은 "지금 필요한 것 목록"에 남아 있으므로 갱신이 성공하면("다시 시도", 새 글 도착, 새 연결) 조정자가 이어서 보낸다. 진행 책임은 조정자에 있다.
10. 무효가 된 이전 쪽 커서: 저장된 커서의 문맥이 지금과 다르거나 서버가 커서 만료(409)를 답하면, 앱이 아는 그 스레드 답글 중 가장 이른 글(본문이 비워진 글 포함)을 가리켜 한 번 조회해 그 앞을 가리키는 새 커서를 얻는다. 요청은 무효 한 번에 1건이고 최신 글까지의 거리와 무관하다(3판의 "최신 쪽부터 거슬러 오기"와 10쪽 상한 가정은 폐기). 이 조회는 "더 최근 답글이 남았는가"를 바꾸지 않는다. 가리킨 글이 삭제돼 찾지 못하면 그다음 이른 글로 한 번 더 한다. 다시 얻기를 연속 2번 하고도 이전 쪽을 한 쪽도 받지 못하면 멈추고 대상별 "다시 시도"로 바꾼다.
11. 실패 분류: 재시도 불가 오류는 대상별 "다시 시도". 재시도 가능 오류(서버 묶음 한도 등)는 표시 없이 60초 뒤 한 번만 자동으로 다시 요청하고, 또 실패하면 대상별 "다시 시도". 시간은 조정자의 기존 주기 점검(`tick`)과 시험에서 바꿀 수 있는 시계로 잰다. 새 타이머 주체를 만들지 않는다.
12. 목록 맨 끝에서의 위치 유지: 자동 불러오기가 보이던 마지막 글 **아래에** 내용을 붙인 반영에서는, 화면이 목록 맨 끝에 있었더라도 글 기준점으로 읽던 위치를 유지한다. 판단과 스크롤의 소유자는 지금처럼 대화 목록(`NativeThreadList`) 하나이고, 대화 화면은 그 반영이 자동 불러오기로 아래에 붙인 것임을 목록에 알릴 뿐 스크롤을 직접 옮기지 않는다. 그 밖의 반영(새 글 도착, 답변 스트리밍 따라가기, 방 들어가기, 직접 열기·보내기·검색 열기)은 지금 규칙 그대로다. 두 번째 스크롤 보정 경로를 만들지 않는다.
13. 한도와 자동 요청의 반복 방지: 비워진 본문의 자동 복원 대상은 **보이는 영역에 걸친 글**뿐이다(앞서 받기 범위 제외). 보이는 글은 기존 규칙대로 고정되어 비워지지 않는다. 앞서 받기로 받은 본문이 한도로 다시 비워진 대상은 보이는 영역에 걸칠 때까지 다시 요청하지 않는다. 그래서 한도가 받는 범위보다 작아도 복원↔비움이 되풀이되지 않는다. 이 판단은 조정자의 "지금 필요한 것 목록" 계산에 둔다(요청 횟수를 세는 별도 차단 장치를 덧대지 않는다).
14. 이전 답글 요청의 판정 시점: "받은 답글의 맨 위가 받는 범위에 있는가"는 열기의 종류와 무관하게 같은 규칙으로 본다(검색·알림 열기에 예외를 두지 않는다). 한 쪽이 붙고 위치 유지가 끝난 뒤 다시 판정한다. 그래서 (가) 중간 글에서 연 직후에는 이전 쪽 하나를 받고, 그 쪽이 받는 범위보다 길면 거기서 멈춘다. (나) 원문이 보이는 위치처럼 붙은 뒤에도 맨 위가 범위에 남으면 스레드 처음까지 한 쪽씩 이어 받는다. (나)의 요청 수는 스레드 길이에 비례한다. [가정] 스레드 답글은 수백 개 수준이다. 수천 개 스레드에서 원문을 보고 있으면 수십 쪽을 이어 받게 되며, 이때도 보이지 않는 본문은 한도로 비워지고 조건 13 때문에 다시 받지 않는다.
15. 한 덩어리 규칙: 한 스레드에서 화면에 그리는 답글은 언제나 서버 순서로 이어진 한 덩어리다. (가) 새로 받은 쪽이 가진 덩어리와 겹치지도 맞닿지도 않으면(예: 중간 묶음을 가진 채 눌러서 다시 열어 최신 쪽을 받음, 다시 연결한 뒤의 갱신) 가진 덩어리를 내려놓고 새 쪽에서 다시 시작한다. 내려놓은 본문은 그리지 않고 상주 목록에서도 뺀다. (나) 덩어리에 속하지 않는 상주 글은 그리지 않는다. 단 덩어리가 스레드 끝까지 닿아 있을 때(더 최근 답글 없음) 도착한 새 글은 덩어리의 끝에 붙인다. (다) 답글 쪽을 한 번도 받지 않은 스레드(앱이 켜진 동안 새로 생겨 원문과 답글이 모두 실시간으로 온 스레드)도 답글이 그려져야 한다. 방법은 둘 중 하나다: 원문이 이번 연결에서 실시간으로 온 스레드를 "끝까지 닿은 덩어리"로 보거나, 받는 범위의 카드에 쪽 상태가 없으면 자동 경로가 그 스레드 쪽을 한 번 받는다. 어느 쪽이든 빈틈 있는 표시는 만들지 않는다. (라) 더 최근 답글이 남은 스레드에 사장이 답글을 보내면, 보내는 순간 그 스레드를 앵커 없는 열기로 다시 받아 최근 쪽 한 덩어리로 바꾸고(가) 화면을 보낸 글로 옮긴다. 보내기 경로의 기존 스크롤 규칙을 따르며 새 스크롤 주체를 만들지 않는다. 이 판단은 모델의 답글 쪽 합치기 한 곳에 두고, 화면은 모델이 준 순서만 그린다.

## 4. 기존 경로 판정

| 경로 | 판정 | 내용 |
|---|---|---|
| "원문 불러오기" 버튼과 "원문을 아직 불러오지 않았어요" 문구 | 교체 | 로딩/실패 조각으로 바꾸고 버튼 코드는 같은 변경에서 지운다 |
| "긴 원문 불러오기"·"이전 답글 보기"·"최근 답글 보기"·"이전 본문 다시 불러오기" 버튼 | 교체 | 위와 같음 |
| 조정자의 `open`(직접 열기, 스크롤 포함) | 유지 | 클릭·검색·알림으로 여는 경로가 계속 쓴다 |
| 조정자의 `messages`·`content`·`restore` 요청 종류 | 유지 | 자동 경로가 같은 요청을 쓴다. 두 번째 요청 주체를 만들지 않는다 |
| `loadOlder`·`restoreNewer`의 비워진 본문 복원 부분 | 통합 | 받는 범위 알림으로 옮기고 옛 호출은 지운다. 같은 일을 하는 경로를 둘로 두지 않는다 |
| `loadOlder`의 목록 창 넓히기와 이전 스레드 쪽 요청, 맨 위 줄 "이전 글 보기" | 유지 | 지금 동작 그대로. 자동 경로는 스레드 목록 쪽을 요청하지 않는다 |
| 목록 갱신의 선택 스레드 요청 | 유지 | 갱신이 소유. 3절 조건 6 |
| 전체 실패 카드 "대화를 불러오지 못했어요"와 `retry()` | 유지 | 목록·집계 갱신 실패와 연결 실패용 |
| 목록 맨 끝의 "맨 끝에서의 거리 유지"(`readerAnchor`의 2pt 예외와 `keep(old)`) | 유지(범위 한정) | 새 글·스트리밍 따라가기에 계속 쓴다. 자동 불러오기가 아래에 붙인 반영만 글 기준점을 쓴다(조건 12) |
| 기존 복원 시험 5종의 "휠 전 복원 없음"·요청 수·단계 순서 단언 | 교체 | REQ-ALD-05로 계약이 바뀌었다. 새 기대값은 수락 시험 명세의 "기존 회귀 시험의 기대값 변경" 절. 커서·끝 여부·안 읽음 수 보존, 원문 고정, 삭제 정리, 위치 유지 단언은 유지 |
| 전량 수신 모드 화면 | 유지 | 손대지 않는다 |

## 5. 유지할 계약

- 문과의 HTTP/WS 규약 전부(요청 종류·필드·한도). 문 코드는 바꾸지 않는다.
- 본문 상주 한도와 고정 규칙, "비움은 삭제가 아님".
- "전체 복사"는 명시 동작에만.
- 미로딩·실패를 빈 대화·삭제로 바꾸지 않는다.

## 6. 대안

| 대안 | 판정 | 이유 |
|---|---|---|
| A. 화면에 닿으면 앱이 자동으로 받는다 | 채택 | 앱만 고치고 기존 요청·한도를 그대로 쓴다 |
| B. 서버가 스레드 목록에 원문을 넣어 준다 | 기각 | 규약 변경과 서버 재설치가 필요하고 목록 응답이 커진다 |
| C. 방에 들어가면 최근 N개만 미리 받는다 | 기각 | 그 밖으로 가면 버튼이 다시 필요하다 |
| E. 최근 답글·무효 커서를 최신 쪽부터 거슬러 받아 메운다(3판) | 기각 | 최신 글까지의 거리만큼 요청이 늘어 상한이 없다(계획 검증 3회차). 글을 가리킨 조회 1건으로 같은 결과를 얻는다 |
| D. 조정자 밖에 자동 불러오기 전용 요청자를 따로 둔다 | 기각 | 요청 주체가 둘이 되어 취소·세션 확인이 갈린다 |

## 7. 실패·복구

- 자동 요청 실패: 대상별 표시 + "다시 시도". 데이터는 바뀌지 않는다.
- 되돌리기: 앱 코드만 바뀌므로 이전 앱 판으로 되돌리면 끝난다. 서버·저장 형식 영향 없음.

## 8. 사전 별도 검토

필요로 판정한다. 이유: 화면 스크롤과 자동 요청이 맞물리는 동작이라 실패 조건(흔들림·중복 요청·빈틈)의 불확실성이 있다. 계획 검증(교차 모델)으로 충족한다.
