# HEJO-POST-GROUP 브레인스토밍 결정 요약 (2026-11-22)

**목적:** 같은 직원이 스레드 답글 칸에 연달아 낸 것(파일 글, 작업 중 표시, 최종 답)을 처음부터 얼굴·이름 한 번 아래 이어서 보인다.

**하는 것:** 앱 대화 화면의 답글 칸에서 바로 앞 답글이 같은 직원이면 얼굴·이름을 생략한다(`Post.continuation`). 바로 앞이 같은 직원이면 입력 중·생각 중 표시의 얼굴·이름도 생략한다. 작업 줄("답변을 준비하고 있습니다 · N초 ■")은 그대로.
**하지 않는 것:** 문(gate)에서 파일과 답을 한 메시지로 합치기, 기록·프로토콜 변경, Hermes 본체 변경, 사장 글(말풍선) 묶기, 스레드 첫 글(top)과 답글 사이 묶기.

**칸·원본·쓰기 주체·수명:** 앱 대화 화면 표시(`app/Sources/ConversationView.swift` `threadContent`·`postPieces`). 새 원본 없음. 기존 `NativeThreadCard.Post.continuation` 재사용. 화면을 그릴 때마다 계산, 저장 없음.

**실측:** [확인] `gate/adapter.py:838` `send_document`는 파일을 별도 메시지로 기록. [확인] `ConversationView.swift:916` 답글마다 `postPieces`로 얼굴·이름 있는 글을 만들고 같은 사람 묶기 규칙 없음. [확인] `:936` 입력 중 표시와 `:965` 생각 중 글은 `TypingBubbleView`가 얼굴·이름을 늘 그림. [확인] ddots(`Sources/NativeThreadContent.swift:61`)도 `continuation`은 버튼 뒤 나머지 글에만 쓰고 같은 사람 묶기는 없음 → 사장이 고른 hejo 고유 동작.

**선행 조사:** 생략(Slack·카카오톡이 같은 사람 연속 글을 묶는 것은 널리 알려진 관례. 앱 안 작은 표시 변경).

**대안과 선택:**
1. (선택) 앱 표시에서 묶기 — 한 파일, 작업 중·끝난 뒤 모습이 같음.
2. (기각) 문에서 파일을 최종 답에 합치기 — 파일이 답보다 먼저 오고, 기록·프로토콜 변경 필요.
3. (기각) 입력 중 표시만 생략 — 최종 답이 따로 이름을 다시 달아 사장 요구(전부 묶기)에 못 미침.

**가정:** 사장 결정 — 연속 글 모두 묶기, 끝난 모습도 "이름 한 번 아래 이어짐". 에이전트 제안 — 답글 칸에서 타임라인상 바로 앞 답글이 같은 직원일 때만 묶음(다른 사람·사장 글·"이전 답글 N개" 더미가 끊음), 시간 제한 없음, 사장 글은 그대로, 묶인 글의 시간은 글에 마우스를 올리면 보임.

**열린 질문:** 없음.
**위험도 1차:** 일반(표시 동작 변경, 한 파일 + 시험).
**진행 방식:** 연합개발, 계획 검증 켬.
