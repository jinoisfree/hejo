# M0 실행 전 인계 — 기존 봇·서버

최초 작성 당시 상태: **준비 중, 배포·재시작·실제 발신 미승인**. 현재 승인은 문서 마지막 절을 따른다. 사용자가 기존 봇·서버에서 시험 준비를 선택했고 채널·토론 그룹은 아직 없다고 답했다. 기존 TASK 1 승인은 유지되지만 실제 M0 승인과 구별한다.

## 고정된 범위

- 목적: 동일 봇이 발행한 채널 시험 게시물의 자동 전달을 native handler로 받고, 그 원문에 시험 댓글을 달 수 있는지 확인한다. 직원 실행·앱 journal 질문 기록은 0이어야 한다.
- 사용: 기존 짝 사장 계정, 기존 Telegram 봇, 기존 서버의 단일 gateway. 두 번째 polling/webhook 수신기를 만들지 않는다.
- 준비 코드: TASK 1 검토 3회차에서 수락한 네 gate 파일. 해시는 [검증 기록](../a6291a01-a451-4239-b635-ac5ef2f23e69/logs/review-03/integrity.json)이 기준이다. 실제 실행 후보와 해시를 다시 대조한다.
- 별도 앱 작업이 공유 인덱스에 있으므로 현재 작업 트리에서 직접 release하거나 포괄 commit하지 않는다. 앱·본체·team-kit 변경과 TASK 2~4 구현은 범위 밖이다.
- M0에서는 probe만 실행한다. **bind 금지**: TASK 1은 일반 댓글 처리까지 구현하지 않았으므로 운영 방을 댓글 목적지로 전환하면 안 된다.

## 사용자가 준비할 것

1. 시험용 비공개 채널 하나와 비공개 일반 그룹 하나를 만들고 채널의 토론 그룹으로 연결한다. 포럼/토픽 그룹은 사용하지 않는다.
2. 기존 짝 사장 계정이 양쪽 소유자여야 한다. 기존 봇을 양쪽 관리자로 지정하고 채널 게시 권한을 부여한다. 다른 관리자는 두지 않는다. 공개 사용자 이름을 설정하지 않는다.
3. 시험할 1:1 직원 방 하나를 정한다. 실제 이름·채팅 id·초대 링크는 공개 문서에 적지 않는다. 토큰을 채팅이나 문서로 전달하지 않는다.
4. 배포 승인과 시험 시작 안내 전에는 probe/bind나 일반 글을 새 공간에 보내지 않는다. 기존 처리기가 실행되는 단계와 시험용 코드 단계가 섞이지 않게 한다.

## 실행 전 후보·복구 준비

읽기 확인한 공용 RELEASE는 `0bcf63535df381e491c99af9cbef41179b7cd79f`다. 이는 준비 시점 관측값이며 실행 직전 다시 확인해야 한다. install/hejo-release는 작업 트리의 gate/hub/schemas/config/install을 복사하고 HEAD를 RELEASE에 쓰므로 미커밋 제품을 현재 작업 트리에서 배포하면 릴리스 표지가 부정확해진다.

구현 담당은 운영 쓰기 없이 격리된 로컬 후보를 준비한다. 현재 설치 파일 집합과 RELEASE의 일치를 먼저 확인하고, 검토된 gate 변경만 적용한 후보를 별도로 고정한다. 설치 범위의 다른 차이가 있으면 덮어쓰지 말고 보고한다. 후보의 전체 커밋·파일 해시·검증 결과와 원복할 설치 파일 집합을 비공개 실행 기록에 고정한 뒤 승인 대상으로 제시한다. 공유 인덱스의 타 작업 staged 파일은 건드리지 않는다. 원격 푸시는 하지 않는다.

실제 경로는 추적 제외 실행 기록에서 `CANDIDATE`, `RELEASE_DIR`, `ROLLBACK_SOURCE`로 채운다. 승인 전에는 아래 명령을 실행하지 않는다.

```sh
bash "$CANDIDATE/install/hejo-release" "$RELEASE_DIR"
hermes --profile default gateway restart
```

기존 운영 상태 확인 도구의 안전한 상태 요약으로 유일 수신자와 active 작업 0을 확인한다. 전체 프로세스 인자·환경·비밀 파일을 출력하지 않는다. 처리 중 작업이 있으면 재시작하지 않고 대기 사실을 보고한다. 과거 다른 작업의 강제 재시작 승인은 재사용하지 않는다. 정해진 gateway 명령 내부의 정상 설정 읽기는 실행 승인 범위에 포함해 요청하되 에이전트의 비밀 파일 직접 열람은 금지한다.

## 승인 후 M0 순서와 메시지 예산

1. 고정한 후보만 배포하고 gateway를 1회 재시작한다. 기존 연결과 오류 상태를 확인한다. 기존 봇의 두 번째 소비자를 띄우지 않는다.
2. 필요하면 사장이 기존 짝 그룹에서 `/hejo_comments_rooms`로 방 식별자를 조회한다. 봇의 목록 안내 1건이 발생한다.
3. 사장이 새 토론 그룹에서 `/hejo_comments_probe <room>`을 **1회** 보낸다. 코드가 권한을 검사하고 첫 시험 발신 전에 채널·그룹 예약을 영속화한다.
4. 예상 봇 발신은 채널 시험 게시물 1건, 그룹의 시험 시작 안내 1건, 자동 전달 원문에 시험 댓글 1건이다. Telegram의 자동 전달 사본은 별도 봇 send가 아니다. 실패 안내가 발생할 수 있으며 자동 재시험은 하지 않는다.
5. 관측 기한은 probe 예약부터 60초다. 동일 probe의 채널 receipt·일치 origin 수신 receipt·댓글 receipt와 complete 상태를 민감값 제거 요약으로 확인한다. 원본 금고를 직접 출력하지 않는다. 허용된 요약 수단이 없으면 이를 먼저 준비하여 검토받는다.
6. 사장이 댓글 버튼을 눌러 시험 답장이 해당 게시물 아래에 있는지 확인한다. 클라이언트와 후보 릴리스, 확인 시각·결과를 남기며 공개 증거에는 채팅 id·개인 이름을 넣지 않는다. 앱 질문 기록·직원 호출 0도 확인한다.
7. bind 없이 종료하고 결과를 기획 담당에게 반환한다. M0 미수신은 기능 부재의 증명이 아니며 자동 재시도·일반 그룹 발신 우회·TASK 2~4 착수 근거가 아니다.

## 복구 경계

- 첫 probe 전 배포/연결 실패: 신규 시험 채팅에서 입력하지 않은 상태로 gateway를 안전하게 정지하고 고정된 이전 설치 원본을 복원한 뒤 1회 재시작한다. 이전 RELEASE 및 설치 파일 집합, 기존 연결 회복을 확인한다.
- probe 예약 이후: 구버전은 예약 채팅을 차단하지 못한다. **곧바로 구버전으로 내리지 않는다.** 먼저 사장이 새 채널·그룹 양쪽에서 시험 봇을 제거해 이 봇으로의 업데이트 유입을 차단하고, 해당 상태와 대기 입력 처리 방법을 운영 인계에서 확인한다. 차단을 확정할 수 없으면 기존 코드 복귀를 보류하고 gateway 정지 상태에서 보고한다. 금고 예약 삭제·journal/첨부 복원·강제 재전송은 하지 않는다.
- 이전 원본 복원 명령은 `bash "$ROLLBACK_SOURCE/install/hejo-release" "$RELEASE_DIR"` 및 안전한 gateway 재시작이다. 복구 원본 전체 경로와 파일 검증, 신규 채팅 차단 방법이 확정되기 전 배포 승인을 요청하지 않는다.

## 현재 남은 준비

채널·그룹 및 시험 방, 격리 후보 커밋, 실제 복구 원본, 단일 수신자 상태, 비밀값 없는 receipt 요약 수단이 아직 확정되지 않았다. 이 준비를 마쳐 구체적인 실행안을 제시한 뒤 사용자에게 배포·재시작·위 시험 발신 범위를 한 번에 승인받는다. 이번 문서는 실행 승인 자체가 아니다.

## 최신 상태 — 사용자 M0 실행 승인

사용자는 비공개 채널 생성, 기존 시험 그룹과의 토론 연결, 양쪽 봇 관리자 및 채널 게시 권한 부여를 확인했고 시험 직원 방을 지정했다. 이어 배포·유휴 시 재시작 1회·probe 1회 및 정상 시험 발신 최대 3건, 앱 무수정·bind 금지 범위를 제시받고 **“승인”**이라고 답했다. 앞 절의 미승인/미준비 문구는 당시 기록이며 이 승인을 다시 요구하는 근거가 아니다.

승인 후보는 `6621b74e0b78d1012d761924d9a664b8259534c1`, 복구 원본은 `0bcf63535df381e491c99af9cbef41179b7cd79f`다. 실행 담당은 기존 비공개 경로 기록과 검토 4회차 증거를 재사용한다. 작업 트리의 다른 앱 변경은 배포하지 않는다.

운영 쓰기 전에 후보/복구와 현재 설치 일치, 유일 수신자, 진행 작업 0, 지정 방의 실제 식별자, 시험 공간, 허용된 관측·복구 절차를 확인해 비공개 실행 기록에 고정한다. 조건 미충족이면 변경 전에 멈추고 해당 원인만 보고한다. 기존 사용자 승인이 없다는 이유로 다시 보류하지 않는다. 토큰·인증 비밀 파일·전체 금고 직접 열람은 계속 금지한다. 운영 스냅샷의 수집/요약 방법이 아직 구체화되지 않았다면 제품 코드와 검토된 로컬 요약 도구의 범위 내에서 방법을 명시하고, 기존 허용 범위를 넘는 접근은 실행하지 않는다.

배포 및 연결 확인 이후 사장에게 새 시험 토론 그룹에서 보낼 정확한 `/hejo_comments_probe <room>` 명령을 안내한다. 사용자 계정으로 대신 메시지를 보내지 않는다. 방 식별자를 얻기 위한 추가 목록 명령 발신이 필요하면 이유와 1건의 추가 안내 발생을 알린다. 명령 전송 대기 중에는 실행 완료로 보고하지 않는다. 60초 관측 뒤 기계 증거와 사용자의 댓글 화면 확인을 받아 반환한다. 실패 자동 재시도·bind·TASK 2~4·푸시는 승인되지 않았다. 복구는 위의 probe 전/후 경계를 그대로 따른다.

## 첫 관측 이후 개인 발신 재시험 계획 — 아직 미승인

첫 명령은 익명 발신 신원 불일치로 거부됐다는 설명이 조사 증거에 가장 부합한다. raw Update 미보존의 한계를 유지한다. 개인 계정 확인 없이 재시험을 요청하지 않는다. 사용자가 기존 짝 사장 개인 명의로 보낼 준비를 마치고 재시험 1회(정상 봇 발신 최대 3건)를 승인하면, 현재 후보/연결과 동시 종료 작업 부재를 확인하고 재배포·재시작 없이 같은 공간·방에서 시험한다. 그룹·채널 명의 및 익명 발신은 허용하지 않는다. 60초 관측·세 receipt·사람 댓글 화면을 확인하고 bind·후속 TASK는 계속 금지한다. 최초 1회 승인을 추가 재시험 승인으로 재사용하지 않는다.

## 개인 발신 재시험 승인

사용자가 익명 설정 해제 방법을 물으며 “재시험하자”라고 답했다. 직전에 제시한 동일 공간·방, probe 1회·정상 봇 발신 최대 3건의 재시험을 승인한 것으로 기록한다. 설정 해제 완료는 아직 확인되지 않았다. 실행 담당은 재배포·재시작 없이 현재 후보/연결과 동시 종료 작업 부재를 확인하고 관측을 준비한다. 사장의 개인 발신 준비가 확인된 뒤 기존 정확한 명령을 한 번 안내한다. 이전 1회 시험의 관측과 새 시험을 구별하고 자동 추가 재시험·bind·TASK 2~4·푸시는 하지 않는다.
