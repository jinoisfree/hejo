# 다수방 댓글 연결 보완

상태: 사용자 구현 승인, 자체 점검 진행. 기준 후보 5ea5a03e7a9d148b79e802602b416f6b736acee4. 기존 앱·Telegram 앱·Hermes 본체·기록장 형식 불변.

## 칸과 책임

기존 gate 문이 수신/발신 및 연결 관리, 금고 telegram.json이 hub 참여 방, 기존 journal이 방·대표·구성원·대화의 원본이다. sent.jsonl v3의 room 구분을 그대로 재사용하며 새 저장 칸은 없다. 금고 밖에 실제 채팅 id를 복제하지 않는다.

## 요구 및 수락

- GR-01: 기존 일반 방도 댓글 연결 대상으로 조회한다. 방 제목은 기존 journal에서 읽는다. 보관/삭제 방, 유효 대표가 없는 방은 입력 불가.
- GR-02: 댓글 또는 방 토픽의 사장 입력은 해당 방의 현재 대표 1명에게 전달한다. 기존 targeted 내부 계약으로 room과 employee를 함께 지정한다. Telegram 일반 방 댓글에서 멘션은 수신자를 바꾸지 않는다. 앱의 기존 멘션/스레드 주인 규칙은 변경하지 않는다. 대표 변경 후 다음 입력은 새 대표에게 전달하며 같은 방·thread를 유지한다.
- GR-03: 첨부는 대표 직원의 기존 파일 입구에 임시 저장한다. 비동기 다운로드 중 대표 변경 시 실행하지 않고 해당 임시 파일을 정리한다. 스레드 입력 중복은 다운로드/실행 전에 차단한다.
- GR-04: /hejo_comments_add <방 식별자...>를 기존 공용 토론 그룹에서 짝 계정의 개인 발신으로 수행한다. 동일 hub의 방 추가만 허용하며 기존 방·epoch·generation·댓글 대응은 변경하지 않는다. 기존/신규 전체 방의 진행 중 수신·세션·typing·전송, unresolved delivery, inflight가 있으면 busy. 권한/짝/원본 재검증 후 금고 한 번 쓰기로 추가한다. 신규 방에만 cutover/epoch를 부여한다. 이미 참여한 대상의 재요청은 무변경이다. 제거/재연결/새 외부 쌍 생성은 범위 밖.
- GR-05: 발신은 실제 room/thread를 유지하고 현재 유효한 구성원의 메시지만 전송한다. 동일 thread id라도 다른 방과 섞지 않는다. 일반 방 busy는 room 세션 주소와 구성원 profile별로 검사한다. 자동 보고/앱 글도 같은 질문 묶음으로 보낸다.
- GR-06: 새로 연결된 방의 전환 전 기록은 자동 복사하지 않는다. 이후 이어 쓰기는 기존 continuation 정책을 적용한다. 기존 DM과 연결 정보·사진/파일·권한 실패·재시작 대역 회귀를 유지한다.

위험도: 인증/동시성 경계가 있어 고위험. 자체 점검을 독립 검증으로 부르지 않는다. 대역(수준 2) 후 실제 대상 확인·배포/추가 승인·실물(수준 4)을 분리한다. 기존 off는 hub 전체에 영향을 주므로 부분 복구에 사용하지 않는다. 추가 후 구버전으로 무조건 복귀하지 않으며, 저장 사본과 최신 입력을 보존하고 새 코드를 유지한 채 전송을 중단하여 진단한다.

구현 순서: 대상·대표·첨부 및 busy → 명시적 add/원자적 추가 → 출력 경계 → 대역·전체 서버 시험 → 운영 인계. 같은 파일을 변경하므로 병렬 갈래 없음. 구현 범위는 gate/telegram_comments.py, gate/telegram.py, gate/adapter.py, 개발자 시험, gate/README.md. adapter는 파일 잠금 안에서 내부 expected_lead와 현재 대표·보관 상태를 재검사한다. 실제 추가는 사용자에게 대상과 영향 범위를 제시한 후 수행한다.
