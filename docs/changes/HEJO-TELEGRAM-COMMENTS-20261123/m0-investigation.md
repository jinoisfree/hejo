# M0 무응답 읽기 전용 조사

## 결론

사용자가 제출한 기존 명령과 화면에서 **그룹 이름으로 익명 발신**한 사실을 확인했다. 입력창에 익명 전송 표시가 있고 보낸 명령의 발신자도 개인 계정이 아닌 그룹이다. 사용자가 붙여준 명령은 안내한 형식과 방 키에 일치하며 @bot 접미사나 여분 공백이 없다. 실제 식별자·명령의 개인 방 키·화면 원본은 공개 문서에 옮기지 않는다.

시험 시각의 Telegram core 권한 거부 기록에서 from_user는 기존 짝 사장과 불일치했다. 이 시각과 일치하는 admission 완료 기록도 한 건 있다. 익명 발신 화면, 시각, 발신자 불일치를 함께 보면 명령의 신원 조건 불충족으로 native 제어 명령이 선택되지 않고 core에서 거부된 경로가 가장 강하게 뒷받침된다. raw Update 전체를 보존한 기록은 없어 sender_chat의 실제 값까지 직접 복원했다고 주장하지 않는다.

이는 댓글 자동 전달 기능의 실패 증거가 아니다. 안전 조건을 제거하거나 모든 발신자를 허용하는 코드 변경은 필요하지 않다. 재시험 준비 시 기존 짝 사장 **개인 계정 발신**을 사용하도록 안내를 보완하는 것이 최소 수정안이다. 재시험은 별도 범위 확정 후 수행해야 하며 이번 조사에서는 요청하거나 실행하지 않았다.

## 수신·초기화 경계

- 승인 후보 RELEASE 및 설치 manifest 재대조: 일치. 파일 설치와 runtime에서 실제 모듈 바이트가 로드됐다는 사실은 구별한다.
- 23:32:30 Telegram의 hejo native factory 연결 성공 표식, 23:32:42 hejo 및 Telegram 연결 표식을 확인했다. 시험 전 처리기 등록 성공 증거가 있다. 성공 표식만으로 모든 시점의 primary 메모리 상태를 단정하지 않는다.
- source의 Telegram 처리기 등록은 첫 연결 시 core 이전, 늦은 등록 시 group 내 첫 core 처리기 앞으로 배치한다. hejo는 group 0의 범위 판별 처리기를 쓴다. 당시 실제 handler 배열을 직접 덤프한 증거는 없지만 우선순위 구현과 등록 성공은 확인했다.
- 23:33:56 Telegram core의 unauthorized user 거부 기록이 있다. 파일 두 곳에 나타난 동일 시각 기록을 두 개의 메시지로 세지 않는다. admission 완료 한 건의 시각도 대응한다. admission 완료는 probe 수락이 아니며 거부 처리도 완료로 기록될 수 있다.
- 23:34:40 SIGTERM/종료 및 primary_unavailable, 23:35:03 연결 재수립 표식이 있다. 이 실행 담당의 추가 재시작 명령은 없으며 발신 주체는 미확인이다. primary_unavailable은 최초 거부 이후 종료 구간에 있어 최초 무응답 원인으로 단정하지 않는다. 다음 시험은 동시 운영 작업을 피할 필요가 있다.
- 실제 그룹의 chat.type은 원본 Update 부재로 직접 확인하지 못했다. 로그 식별자의 supergroup 형태와 사용자 화면만으로 Bot API 타입 검증을 완료했다고 하지 않는다. 최초 권한 문제를 해결한 뒤에도 기존 probe의 권한·그룹 타입·연결 검증을 그대로 거쳐야 한다.

## 대역 관측과 최소 변경안

제품 코드의 실제 Comments.command에 가짜 메시지를 넣어 exact 개인 발신, 다른 개인 발신, sender_chat, @bot 접미사, 추가 공백, basic group을 검사했다. 6개 모두 예상과 일치했다. 정확한 개인 발신만 선택되고 나머지는 선택되지 않았다. 명부/금고 불변 및 Bot API send 0도 확인했다. 이 대역은 명령 판별 경계만 재현하며 운영 Update 전체나 실제 화면 성공의 대체 증거가 아니다.

명령에 @bot 접미사/추가 공백을 허용하는 변경은 이번 실제 입력에 해당하지 않아 제안하지 않는다. 익명 sender_chat을 허용하는 변경도 사장 인증 계약을 약화하므로 제안하지 않는다. 제품 최소 수정안은 **없음**이며, 실행 인계에 개인 발신 확인(그룹·채널 이름 또는 익명 발신 아님)을 재시험 선행 조건으로 명확히 기록하도록 기획 담당에게 제안한다.

## 증거와 범위

- `.build/telegram-comments/test_m0_command_boundary.py`에 대한 pytest: 종료 0, 6 passed. 실행 명령·해시는 logs/task1-runs.json 마지막 항목, 출력은 logs/task1-check-11.log.
- 설치/로그 제한 요약/receipt 계수/짝 사장과 발신자 비교 스크립트: 각각 종료 0. 공개 민감값 제거 증거는 logs/m0-investigation.json.
- 비공개 ingress-investigation.json, ingress-timeline.json, auth-boundary-evidence.json은 `.build/telegram-comments/m0/`에 있다. 명령 본문이 로그에 없어 사용자에게 기존 메시지를 요청했고 사용자 답변 및 첨부 화면으로 보완했다. 새 메시지 전송은 요청하지 않았다.
- 사용자 화면의 OS/Telegram 정확한 버전은 미확인이다. 이번 화면은 익명 발신 진단 증거이고 댓글 묶음 성공 증거가 아니다.

제품/운영 파일 변경, 새 배포, 추가 재시작, Bot API 송신, 별도 polling, 롤백, bind, TASK 2~4, 푸시는 수행하지 않았다. 운영 후보는 유지한다. M0는 아직 미통과이며 기획 담당이 재시험 조건과 범위를 확정해야 한다.
