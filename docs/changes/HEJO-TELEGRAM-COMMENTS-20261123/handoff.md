## 4. 책임·흐름

기존 Telegram 문이 단일 책임자다. native 첫 매치 handler로 승인된 자동 전달/댓글을 기존 receive에 넣고, 기존 settled queue가 방별 단일 목적지를 선택해 channel root 또는 discussion reply로 보낸다. 연결 명령은 이미 짝지은 사장만 허용한다.

## 5. 기존 경로 판정

포럼은 미전환 직원/단체방의 실사용 경로로 유지한다. 전환 방은 같은 route selector에서 topic 수신·발신·sync를 제외한다. 댓글을 별도 미러로 중복 발신하지 않는다. sent 대응은 기존 파일에 버전 구분해 통합한다. app 및 대화 원본은 유지한다. 자세한 표는 design 6절.

## 6. 위험·증거·롤백

고위험: 인증·외부 발신·영속 대응·동시성. 증거 수준 2 대역 통합 및 4 실제 Telegram 표시를 모두 요구한다. planning reviewer 통과는 구현 최종 검증을 대체하지 않는다. 다른 모델의 구현 독립 검토와 설계 미참여 추가 검토 전까지 최종 완료를 선언하지 않는다.

실패하면 보류/정지하며 다른 목적지로 보내지 않는다. 정상 off, 불확실 결과 resolve/abort, 구버전 코드 롤백의 선행 안전 조건은 design 5·7절. 과거 journal/첨부 덮어쓰기 금지. TASK 5는 이번 구현 승인 범위가 아니다.

## 검토 6회차

신원 경계 조사와 대역 6개 시험을 수락했다. 익명 발신에 따른 짝 불일치가 유력하며 제품 수정 없이 개인 발신 안내를 보완한다. 전체 부분 완료 및 V-05 실물 차단 유지. handoff-m0.md에 동일 후보·공간·방의 개인 명의 재시험 1회 계획을 추가했으며 별도 사용자 승인을 기다린다. 재배포·재시작·자동 재전송은 하지 않는다.

## 최신 상태 — 검토 7회차 M0 핵심 관문 수락

개인 발신 재시험 complete와 세 receipt 기한 내 완료, 원문별 댓글 화면 두 장을 검증자가 직접 확인했다. V-05 핵심 가능성 차단 해소, 전체는 부분 완료다. 검토 7회차에 클라이언트 버전·전체 실행 trace·발신 계수 관측 한계를 남겼다. 다음은 기존 4판 TASK 2→3→4 서버 구현 및 대역 시험의 사용자 승인이다. 기존 TASK 1/M0 승인을 후속 구현 승인으로 확대하지 않는다. 재배포·bind·추가 시험·푸시는 현재 승인 범위 밖이다.

## 최신 사용자 승인 — TASK 2~4

사용자가 TASK 2~4 서버 구현과 자동 시험 진행 여부에 “ㅇㅇ”라고 답해 승인했다. M0 핵심 관문은 검토 7회차에서 수락됐다. 기존 4판 tasks.md의 TASK 2→3→4를 기존 구현 담당이 순차 수행한다. 앱 무수정·기존 gate 단일 책임·임시 홈 및 가짜 자료 시험·수락 기준 보존을 유지한다. 과거 TASK 1 한정/후속 승인 대기 문구는 이 승인 이전 기록이다.

이번 범위는 인증된 질문/댓글/첨부 수신, 원문별 답변/첨부 발신, 중복 및 불확실 전송 복구, 해제·안내·회귀 시험이다. 운영 배포·gateway 재시작·실제 bind·추가 실물 메시지·TASK 5·푸시는 포함하지 않는다. 현재 운영 M0 후보는 그대로 두고 개발 작업 트리에서 구현한다. impl-report에 변경 파일·변경본 해시/커밋·실제 명령과 종료 코드·로그·미실행 범위를 기록하여 검토로 반환한다. 다른 작업 변경을 덮어쓰거나 포함하지 않는다.

## 최신 사용자 구조 변경 — 5판 재검증 대상

사용자가 “이구조가 좋겠다 이렇게 가보자”로 기존 사람 토픽+공용 채널/토론 그룹 한 쌍을 승인했다. 4판 사람별 외부 쌍 구조와 해당 TASK 계속 진행 지시는 대체된다. 현재 gate 미커밋 구현과 기존 시험/M0 증거는 보존한다. spec/design/tasks/수락 명세를 5판으로 갱신했으며 기존 4판 APPROVED를 새 계약 승인으로 쓰지 않는다.

계획 검증 대상으로 5판을 제출한다. 통과 후 기존 구현 담당이 H1→H4를 수행하며 사람별 binding·토픽 차단·채널 글 신규 질문 실행을 제거하고 기존 인증/중복/전송 복구 코드를 재사용한다. 제품·운영 변경은 이번 기획 턴에 하지 않았다. 기존 M0는 native 가능성 증거이고 공용 링크 UX는 미검증이다. 운영 후보를 유지하고 H5는 구체적 별도 인계와 승인 후 실행한다. 개인 이름/id/링크를 공개 문서에 옮기지 않는다.
