## 4. 책임·흐름

기존 Telegram 문이 단일 책임자다. native 첫 매치 handler로 승인된 자동 전달/댓글을 기존 receive에 넣고, 기존 settled queue가 방별 단일 목적지를 선택해 channel root 또는 discussion reply로 보낸다. 연결 명령은 이미 짝지은 사장만 허용한다.

## 5. 기존 경로 판정

포럼은 미전환 직원/단체방의 실사용 경로로 유지한다. 전환 방은 같은 route selector에서 topic 수신·발신·sync를 제외한다. 댓글을 별도 미러로 중복 발신하지 않는다. sent 대응은 기존 파일에 버전 구분해 통합한다. app 및 대화 원본은 유지한다. 자세한 표는 design 6절.

## 6. 위험·증거·롤백

고위험: 인증·외부 발신·영속 대응·동시성. 증거 수준 2 대역 통합 및 4 실제 Telegram 표시를 모두 요구한다. planning reviewer 통과는 구현 최종 검증을 대체하지 않는다. 다른 모델의 구현 독립 검토와 설계 미참여 추가 검토 전까지 최종 완료를 선언하지 않는다.

실패하면 보류/정지하며 다른 목적지로 보내지 않는다. 정상 off, 불확실 결과 resolve/abort, 구버전 코드 롤백의 선행 안전 조건은 design 5·7절. 과거 journal/첨부 덮어쓰기 금지. TASK 5는 이번 구현 승인 범위가 아니다.

사용자가 “진행하자”라고 요청했다. 호스트 인계의 planReview는 4판 hash에 대한 stage=done/outcome=passed로 남아 있음을 읽기 전용 확인했다. 5판 독립 승인은 없고 직접 호출할 workflow 도구도 현재 세션에 없다. 상태 파일은 수정하지 않는다. 이전 실패를 덮거나 검증 관문을 생략하지 않는다.

재개 범위는 기존 4판 후보에 대한 V-07 환경/fixture 실패 진단으로 한정한다. 이는 새 5판 구현에 의존하지 않는 이미 요청된 검증 보완이다. 구현 담당은 임시 홈·대역에서 adapter.connect 실패의 실제 예외 경계를 관측하고 재현 환경·명령·종료 코드·증거 해시를 보고한다. 진단용 계측이 필요하면 격리 복사본에만 적용하고 제품 작업 트리를 바꾸지 않는다. 의존성을 전역 설치하거나 fixture assert를 완화하지 않는다. 운영 홈/비밀 파일/리스너 변경·실제 메시지 발신 금지. 5판 H1~H4는 독립 계획 검증 후에만 착수한다.

독립 계획 검증의 전달 문제와 V-07 진단을 별개로 관리한다. 이번 인계는 새 계획 승인이나 4판 제품의 완료 판정이 아니다.

## 사용자 역할 변경 — 직접 구현

사용자가 “이제 너가 직접 구현한다”라고 명시해 이 대화가 5판 서버 구현과 자체 점검을 맡는다. 이전 독립 계획 검증 전달 대기로 구현을 반복 차단하지 않는다. 이는 사용자 최신 직접 구현 지시에 따른 역할 변경이며 독립 검증 통과를 새로 얻었다는 뜻은 아니다. 앱 무수정·운영 배포/재시작/실물 발신 별도 승인·직접 push 금지는 유지한다. 기존 후보는 보존한다.

구현 중 확인한 수신 경계: 실제 Hermes wrapper 이전에 미디어가 다운로드될 수 있으므로 활성 참여 토픽도 기존 native handler가 먼저 소비한다. 같은 Telegram/Comments 소유권 아래서 등록 토픽과 댓글을 처리하고 비참여 포럼은 기존 wrapper에 둔다. 중복 방지는 파일 staging/직원 호출 전 영속화한다. wrapper 경로도 동일 accept_input으로 합류하며 두 번 실행하지 않는다. 별도 리스너나 새 원본을 만들지 않는다.


## 직접 구현 결과 — 공용 hub

H1~H4 서버 구현은 현재 대화에서 수행했다. 기존 사람별 토픽 + 공용 외부 쌍 하나 + 질문별 카드/댓글 구조를 적용했다. native의 참여 토픽 선점, room을 포함한 v3 대응, 카드 보류 편집과 unknown 복구를 포함한다. 독립 검증을 받았다고 선언하지 않으며 verdict에 자체 점검으로 기록했다.

최종 서버 및 gateway 증거는 logs/hub/server-runs.json, 최종 관련 시험과 해시는 target-runs.json, 변이는 mutation-runs.json에 있다. 전체 scripts/test.sh의 앱 버튼 시험 실패는 full-runs.json/full.log에 보존했다. 기존 후보의 앱 소스·시험과 동일하며 변경하지 않았다. 운영 M0 후보는 그대로이고 실제 bind/배포/재시작/발신/푸시는 하지 않았다.
