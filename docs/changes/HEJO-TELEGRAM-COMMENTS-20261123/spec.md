## 목적과 범위

기존 HEJO 포럼의 사람별 토픽을 질문 목록으로 유지한다. 직원 수와 무관하게 비공개 공용 채널 하나와 연결 토론 그룹 하나만 사용한다. 토픽의 새 질문마다 짧은 질문 카드와 `대화 열기` 버튼을 남기며 답변·첨부·후속 대화는 해당 게시물 댓글에 모은다. 앱 시작 대화와 직원 보고도 해당 사람 토픽에 카드가 생긴다. 토픽 안에서 접어 펼치는 UI가 아니라 댓글 화면으로 이동한다. 보관/음소거는 사용자 선택이며 봇이 채팅 목록을 숨기거나 고정한다고 보장하지 않는다.

공용 공간은 사람별 접근 격리가 아니다. 사장 개인 사용을 전제로 하며 초대된 사람은 다른 직원 대화도 볼 수 있다. 기존 토픽 수는 유지하고 이 기능의 외부 공간 증가는 고정 두 개다. 첫 활성화는 명시한 1:1 방 목록에만 적용하며 이후 새 방은 자동 편입하지 않는다.

안: 기존 문에서 채널 댓글 수신·발신, 연결/해제 명령, 질문별 단일 본문 전송 경로, 권한·영속 대응·오배송 방지, 운영 준비 및 사용자 실물 수락 절차.

밖: `app/` 수정·빌드·설치, 앱 wire 프레임 변경, Hermes 본체/텔레그램 플러그인 수정, 별도 polling/webhook, 사용자 계정 자동화, 채널/그룹 자동 생성, 과거 대화 이관·삭제, Telegram 편집/삭제 양방향 동기화, 새 일감 관리 기능. 첫 판은 직원 1:1 방만 참여시킨다. 기존 단체방 토픽은 유지한다. 댓글의 단일 사진·문서는 지원하고 앨범·음성·영상·기타 미디어는 명시적으로 거부한다.

첫 판은 공식 클라우드 Bot API(`api.telegram.org`)만 지원하며 자체 호스팅·대체 API endpoint에서는 연결을 거부한다. 관리자 전체 목록 옵션이 조용히 무시되는지를 응답만으로 탐지한다고 가정하지 않는다.

채널과 연결된 비공개 일반 슈퍼그룹은 사장이 Telegram에서 만든다. 사장과 현재 봇 외에는 게시 권한을 가진 관리자가 없어야 한다. 채널은 봇의 질문 게시물 출력용이다. 사람이 직접 쓴 채널 글은 직원 지정 근거가 없으므로 실행하지 않는다.

## 요구와 수락 기준

### REQ-HTC-01 연결과 전환

- AC-01 정상: 기존 짝의 사장이 기존 짝 그룹에서 `/hejo_comments_rooms`를 보내면 전환 가능한 1:1 방 식별자·이름을 받는다. 다른 사람·채널 명의·짝 없음은 정보/변경 0건.
- AC-02 정상: 사장이 공용 토론 그룹에서 `/hejo_comments_bind <room...>`을 보내면 명시한 1:1 방 목록을 단 하나의 공용 쌍에 원자 연결한다. 양방향 linked_chat_id, 비공개·일반 슈퍼그룹, 사장 소유, 양쪽 봇 관리자와 채널 게시 권한, 동일 대상 M0 기계 조건을 확인한다. 같은 목록의 중복 요청은 같은 연결, 활성 중 목록 변경·두 번째 쌍 등록은 거부한다.
- AC-03 실패: 다른 관리자/게시 봇, 권한 부족, 공개·포럼 대상, 잘못된 방 목록, 원격 실패, 예약 충돌·은퇴 대상은 전환하지 않는다. 기존 경로와 금고는 유지한다.
- AC-04 경계: 과거 기록은 이동·삭제·재전송하지 않는다. 참여 방의 진행 차례/전송/불확실 전송이 있으면 busy다. 성공 뒤 기존 사람 토픽 수신·sync는 유지하고 본문 답변의 토픽 미러만 중단한다. 비참여 방·단체방은 종전 동작이다.

### REQ-HTC-02 입력과 신원

- AC-01 정상: 참여 사람 토픽의 개인 사장 새 글은 해당 방의 새 질문 하나로 접수한다. 알려진 질문 원문·카드에 답장하면 그 스레드를 이어간다. 알 수 없는 답장 대상은 새 질문으로 추측하지 않는다. 공용 채널 글과 자동 전달은 새 질문/직원 호출을 만들지 않으며 봇 발행 receipt와 일치할 때 닻만 등록한다.
- AC-02 정상: 사장 개인 계정이 원문 또는 그 대화의 답변/첨부에 댓글을 달면 같은 hejo 스레드에 들어간다. 댓글창에서 답장 지정 없이 보낸 글도 검증된 원문 thread id로 연결된다.
- AC-03 실패: 다른 계정, sender_chat을 사용하는 익명 댓글, 수동 전달, 출처 불일치, 알 수 없는 닻/교차 채팅 답장, 연결 전 메시지, 편집 update는 질문으로 실행되지 않는다. 관리 대상의 거부 입력을 Hermes 기본 에이전트로 우회 전달하지 않는다. 권한 검사를 마쳐 사전 시험 대상으로 예약한 채널·그룹도 연결 전부터 관리 대상이다. 시험 진행·성공·실패·취소·관측 시간 종료 후에도 예약을 유지하고, 명시 bind 전의 일반 글·자동 전달·댓글은 직원 실행 및 기본 처리기 전달 없이 소비한다.
- AC-04 정상/경계: 텍스트·캡션과 단일 사진/문서를 기존 파일 검증·기록 경로로 수용한다. 다운로드 실패·크기 초과·앨범·미지원 미디어는 부분 질문을 실행하지 않고 사장에게 지원 범위를 알린다. 수신 파일 한도는 Bot API getFile 20MB와 기존 문 한도 중 작은 값이다.
- AC-05 보안: 새로운 질문/댓글 실행과 발신 전에 연결·사장·봇 권한을 재확인한다. 검증 실패는 해당 연결을 일시 정지하고 정보성 오류만 남긴다. 서명 문자열이나 display name으로 개인을 인증하지 않는다.

### REQ-HTC-03 발신과 표시

- AC-01 정상: 직원 답변·앱의 사장 후속 글·첨부는 공용 그룹의 해당 질문 원문에 대한 답장으로만 보낸다. Telegram 댓글 입력은 이미 외부에 있으므로 다시 미러하지 않는다. 토픽에서 접수한 후속 글은 댓글에 한 번 표시한다. 다른 방·질문으로 섞이지 않는다.
- AC-02 정상: 토픽 질문·앱 새 대화·직원 새 보고마다 공용 채널 root 하나와 사람 토픽 카드 하나를 만들고 자동 전달 닻을 확인한 뒤 후속 글/첨부를 댓글로 보낸다. 카드에는 제목·상태·대화 열기와 댓글의 원래 사람 토픽 복귀 안내가 있다. 답변마다 카드나 채널 게시물을 추가하지 않는다. 봇 원문은 사장 질문으로 실행하지 않는다.
- AC-03 보존: 정착 후 직원 글, 작성 중 판단, 방/스레드 삭제 검사, 글쓴이 표시, 기존 버튼 안내와 첨부 소유권을 유지한다. 분할한 모든 텍스트와 첨부 id가 같은 스레드에 대응된다.
- AC-04 실패: 원문 삭제·권한 상실·닻 미확인 시 댓글을 일반 그룹 글로 보내지 않는다. `message_thread_id`를 포럼처럼 사용하지 않으며 `allow_sending_without_reply`는 false다. 부분 전송/결과 불확실은 재전송하지 않고 보류 상태를 표시한다.
- AC-05 전환 경계: 전환 전에 시작한 스레드를 전환 후 앱 또는 직원이 이어 쓰면 현재 목적지에 `이전 대화 이어쓰기 — 전환 이후 내용` 표시의 새 묶음을 만든다. 과거 본문·첨부는 복사하지 않고 전환 이후 새로 생성한 글만 담으며 hejo 스레드는 유지한다. 댓글 전환·정상 off·abort 뒤 토픽 복귀·재연결 모두 같은 규칙이다. 같은 목적지라도 전환 세대가 다르면 과거 닻을 재사용하지 않는다. 현재 세대에 이미 닻이 있는 대화는 그 닻을 계속 쓰고, 닻 삭제는 새 묶음 생성 사유가 아니다.

### REQ-HTC-04 영속성과 중복

- AC-01 경계: 채널/그룹이 다른 동일 메시지 id, 서로 다른 방의 동시 글, 재시작·중복 update가 서로 섞이지 않는다. 수신 중복은 파일 저장 및 직원 호출 이전에 판정하고 기존 journal client_msg_id도 확인한다.
- AC-02 경계: 채널 원문 발신 전 의도, 성공 receipt, 자동 전달 닻을 영속 기록한다. 성공 응답을 잃었거나 기록 중 중단되면 unknown으로 남기고 자동 재발신/새 질문 실행을 하지 않는다. 자동 전달이 send 응답보다 먼저 도착해도 대응을 보존한다.
- AC-03 실패: 대응표 손상·지원하지 않는 버전은 댓글 경로를 닫고 기존 앱 기록을 유지한다. 이전 형식의 토픽 sent 레코드는 계속 읽힌다. 댓글 형식 손상을 조용히 빈 대응표로 취급하지 않는다.
- AC-04 경계: 닻/receipt 복구는 사장 명시 명령과 원문 답장으로만 가능하며 불확실 작업과 실제 게시물을 대조한다. 잘못된 채널·중복 복구·다른 방 연결은 거부한다. 복구 불가 시 사장의 명시 abort만 해당 연결을 은퇴시키고 미전송 항목을 취소한다. 원본은 보존하며 늦은 update나 취소 항목을 재실행하지 않는다. Bot API 전송의 exactly-once 또는 중단된 직원 실행 자동 재개는 보장하지 않는다.

### REQ-HTC-05 해제·보존·운영

- AC-01 정상: 공용 토론 그룹의 사장 `/hejo_comments_off`는 참여 방 모두에 대한 전환이다. 진행 작업이 있으면 busy, 안전한 경계에서 기존 토픽 본문 출력으로 돌아간다. 공용 게시물·댓글·journal은 삭제하지 않고 보류 댓글을 토픽으로 재전송하지 않는다.
- AC-02 보안: 앱 전체 끄기는 모든 Telegram 발신/질문 실행을 끈다. 앱 연결 해제/재짝짓기는 모든 댓글 권한을 무효화한다. 이전 채널/그룹 id는 금고에 비활성 예약으로 남아 Hermes 기본 경로에 질문이 새어 들어가지 않게 한다. 새 짝이 이전 연결을 자동 재사용하지 않는다. 첫 판은 은퇴한 외부 채팅 예약을 기간 제한 없이 금고에 보존하고 해제 명령을 제공하지 않는다. 앱 연결 해제·재설치로도 지우지 않으며, 같은 채널/그룹의 재등록은 짝이 바뀌어도 거부한다. 이는 늦은 글의 기본 에이전트 유입을 막기 위한 의도된 제한이다.
- AC-03 실물: 공용 쌍 하나와 서로 다른 직원 두 방에서 M1~M6을 통과해야 사용 가능이다. 대상·릴리스·롤백·발신 범위를 별도 운영 인계에 고정하고 승인을 받는다. 실제 Slack·고객 메시지는 금지한다.
- AC-04 사전 실물: 핵심 댓글 구현 전 M0에서 봇이 발행한 시험 게시물의 자동 전달 사본을 동일 봇의 native handler가 수신하고, origin/그룹 닻을 연결하여 댓글 답장을 보낼 수 있음을 확인한다. 유효한 M0 증거가 없으면 H2~H4 및 실제 bind 활성화를 보류하고 계획 담당에게 환경 근거와 함께 반환한다. 별도 polling·사용자 계정·수동 닻 지정으로 시험을 대체하지 않는다. 관측 시간 제한은 진행 중 probe의 완료 기한이다. 기한 내 완료된 probe에는 별도 시간 기반 유효기간이 없으며 대상/짝/계약 변경 및 권한 재검사는 계속 적용한다. bind의 자동 판정은 probe 수신/답장 receipt의 완결성이며, 사장의 화면 확인 증거는 H2~H4 착수 관문으로 별도 기록한다.

### NFR-HTC-01 무수정·공개·회귀

- AC-01: 앱·앱 wire·Hermes 본체·타 앱·team-kit 무변경. 금고 외 저장/로그/오류/시험 증거에 실제 채널·그룹·계정 id 및 비밀값 없음. 금고와 대응 파일 0600, 시험은 임시 HERMES_HOME과 가짜 명부·Bot API만 사용. 실제 식별자를 포함한 대화/복귀 링크는 승인된 Telegram 화면 출력에만 허용하고 공개 로그·대응 파일에 저장하지 않는다.
- AC-02: 기존 텔레그램 및 전체 프로젝트 시험 통과. native 재연결/재등록 시 처리기 중복 없음. 관리하지 않는 채팅은 기존 처리기에 정확히 한 번 전달된다. group-99 관찰 및 update admission은 정상 유지.

위험도: 고위험(인증, 영구 대응, 동시성). 필요한 증거: 대역 통합 2 + 실제 Telegram UI 4. 계획 검증 및 구현에 참여하지 않은 다른 모델 검토, 설계에 참여하지 않은 추가 검토가 필요하다. 사용자 실물 수락은 마지막 검토의 자료로 남긴다.
