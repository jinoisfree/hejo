## 2. 목표

사장이 에이전트 연결 화면에서 직원마다 자기 연결만 짧은 목록으로 보고, 일부를 못 읽어도 읽은 것은 보며, 연결은 쉬운 말과 클릭으로 끝낸다. 실패하면 서버 로그에 원인이 남는다.

## 3. 범위

- 안: 문의 표 만들기·실패 처리·로그, 앱 연결 화면, team-kit의 앱 연결 흐름·안내 문장·값 찾기(시놀로지·Obsidian), 서버 적용, 앱 0.2.2 공개 준비(아이메시지 작성 중 표시 포함).
- 밖: Hermes 본체 고치기(묶음 이름 검사 결함은 보고만), X·Instagram·Slack·Notion 값을 서버가 대신 받아 오기(사람만 받을 수 있는 값), 새 연결 종류, ddots 앱 수정. 직원 B의 반쯤 저장된 값을 에이전트가 직접 지우거나 고치기(사장이 화면에서 이어 가기 또는 되돌리기).

## 4. 요구와 수락 기준

수락 기준의 시험 대응은 [수락 시험 명세](../../../tests/acceptance/HEJO-CONNECTIONS.md).

### REQ-HC-01 한 가지를 못 읽어도 나머지는 보인다
- AC-01(실패): 직원 한 명의 묶음 설정 요청 하나가 400을 줘도 그 직원의 표가 만들어지고 다른 줄은 모두 있다. 그 묶음 줄은 남고 설정 정보만 빠진다.
- AC-02(실패): 목록 요청(도구 묶음·키·MCP·OAuth·MCP 목록·team-kit 상태·앱 목록·런타임 상태) 하나가 실패해도 나머지 부분의 줄은 나온다. 그 직원에게 `unread: [{part, reason}]`이 붙는다.
- AC-03(실패): 다른 직원의 실패가 이 직원의 표에 영향을 주지 않는다.
- AC-04(정상): 앱은 `unread`가 있으면 "일부 항목을 읽지 못했어요"를 회색 안내로 보이고 읽은 줄은 그대로 보인다.
- AC-05(경계): 다시 읽기가 통째로 실패해도 앱은 이전에 받은 그 직원의 표를 지우지 않고, "마지막으로 확인한 내용이에요"와 실패 문장을 함께 보인다.

### REQ-HC-02 실패하면 서버 로그에 원인이 남는다
- AC-01: 부분 실패마다 문 로그에 한 줄 `connections_part_failed`(직원 id, 부분 이름, 이유 코드, HTTP 상태)가 남는다. 응답 본문·토큰·입력값은 없다.
- AC-02: 표·동작 요청이 통째로 실패하면 `connections_failed`(요청 종류, 직원 id, 이유 코드)가 남는다.
- AC-03: 앱에 보내는 실패 이유는 실제 이유다. `admin_unavailable`은 관리 서비스에 닿지 못했을 때(연결 거부·시간 초과·설정 파일 문제)만 쓴다.
- AC-04(실패): 관리 서비스가 2xx로 답했지만 본문이 JSON이 아니거나 1MB를 넘으면 이유는 `invalid_response`이고, 관리 기능 꺼짐 안내는 나오지 않는다(design 2.2a).

### REQ-HC-03 직원마다 자기 것만, 짧게
- AC-01: 키 줄은 그 직원에게 값이 있는 키와, 그 직원이 켠 도구 묶음이 필요로 하는 키만 나온다. 관리 서비스 목록의 나머지 키는 줄이 되지 않는다.
- AC-02: 연결할 수 없는 앱 줄과 아직 설치하지 않은 MCP 목록 줄에는 `hidden_by_default: true`가 붙는다.
- AC-03: 앱은 그 줄을 기본으로 숨기고, "연결할 수 없는 항목도 보기"를 켜면 보인다. 위쪽 개수 요약도 숨긴 줄을 세지 않는다.
- AC-04(실측 기준): 현재 서버 자료로 한 직원의 기본 표시 줄 수는 도구 묶음 + 그 직원 키 + OAuth + 연결됨·가능 앱 + 채널 + 게이트웨이이며 100개 이하다(M3).

### REQ-HC-04 연결 안내는 쉬운 말과 클릭으로
- AC-01: 시놀로지 연결은 서버가 주소 두 개를 찾으면 묻지 않는다. 찾는 순서·후보 규칙은 design 4.1(이 직원의 초안 → 연결된 다른 직원 → 서버의 Synology Drive Client 자료, 후보 하나는 한 연결의 값 묶음). 찾은 값은 형식 검사(기존 `nas.settings` 규칙)를 통과해야 쓴다. 완전 후보(주소 두 개가 함께 검사 통과)가 하나면 건너뛰고, 여럿이면 클릭으로 고르게 한다. 부분 후보는 아는 칸을 채우고 빠진 칸만 묻는다. 없으면 주소 단계를 쉬운 말로 묻는다. 주소 단계 완료는 주소 두 개가 모두 있고 검사를 통과할 때만 기록한다.
- AC-02: 시놀로지 아이디는 같은 출처(다른 직원의 연결 또는 Drive Client 자료)에서 찾으면 미리 채우되 사장이 고칠 수 있다. 비밀번호는 미리 채우지 않고 다른 직원 값을 복사하지 않는다. (2026-11-08 결정 "아이디를 미리 채우지 않는다"를 이 요구가 대체한다. 사장이 계획 확인 때 승인.)
- AC-03: 주소가 틀리면 주소 단계로 돌아가 무엇이 틀렸는지 한 문장으로 알린다. 폴더 고르기로 가지 않는다.
- AC-04: Obsidian 보관함은 서버의 Obsidian 보관함 목록에서 찾아 고르기(클릭)로 준다. 못 찾을 때만 폴더를 묻는다.
- AC-05: 모든 연결 안내(시놀로지·Slack·ddots Slack·Notion·Obsidian·X·Instagram·Mac 앱 안내)를 design 4.4절 기준과 연결별 판정표대로 다시 쓴다. 사람이 넣는 칸은 표의 칸뿐이고 안내 단계 수는 표의 최대를 넘지 않는다. "API", "토큰", "OAuth", "manifest", "scope" 같은 말은 화면 문장에 쓰지 않거나 처음 한 번 쉬운 말로 풀어 쓴다. 단계는 사람이 실제로 해야 하는 일만 남긴다.
- AC-06: 시놀로지 화면에서 사람이 넣는 값은 비밀번호(필요하면 2단계 인증 안내)뿐이고 나머지는 클릭이다(서버가 값을 찾은 경우).

### REQ-HC-05 화면 문장이 사실과 맞다
- AC-01: "서버의 관리 기능이 꺼져 있어요"는 관리 서비스에 닿지 못했을 때만 나온다.
- AC-02: 입력 창의 빨간 글은 그 입력의 결과(입력 오류, 저장 실패)만 보인다. 표 다시 읽기 실패 문장은 입력 창에 나오지 않는다.

### REQ-HC-06 연결 도중 멈추지 않고 이어 간다
- AC-01: 주소를 넣고 "확인하고 저장"을 누르면 같은 입력 창에 다음 단계(로그인)가 보인다.
- AC-02: 입력 창이 어떤 이유로 닫혀도 연결 창과 메뉴·설정의 "에이전트 연결…"은 계속 반응한다. 연결 화면의 확인 창은 연결 창에 붙은 창으로 띄우며 앱 전체를 막는 확인 창을 쓰지 않는다.
- AC-03: 진행 중인 연결(시설의 `progress.next`가 있는 앱)은 줄과 자세히 화면에 "이어서 하기"를 주 버튼으로 보이고, 누르면 멈춘 단계부터 이어진다.
- AC-04: 진행 중인 연결에는 "처음부터 다시"(시설의 `app undo`)가 있어 반쯤 저장된 값을 되돌린다. 되돌린 뒤 그 직원의 금고 초안 칸과 진행 기록은 없어지고, `.env`와 다른 직원의 값은 그대로이며, 그 앱은 연결 가능 상태로 돌아간다(AT-HC-49로 실제 시설 코드에서 확인).
- AC-05: 지금 직원 B의 시놀로지 초안은 그대로 두고, 고친 화면에서 "이어서 하기"를 누르면 로그인 단계가 나온다(M5. "처음부터 다시"는 M5의 합격 조건이 아니며 AT-HC-49가 확인한다).

### REQ-HC-07 공개
- AC-01: 앱 0.2.2(빌드 번호 +1) 공개 준비물이 만들어지고, 공개 스냅샷은 `main` HEAD 트리(아이메시지 작성 중 표시 포함)다. 공개(publish)·푸시는 사장이 한다.

### NFR
- NFR-HC-01: 로그·응답·시험·문서에 비밀값·응답 본문·개인값(이름·주소·QuickConnect ID 실제 값·절대 경로)을 넣지 않는다. 시험은 임시 `HERMES_HOME`과 가짜 자료만 쓴다.
- NFR-HC-02: 표 읽기는 쓰기를 하지 않는다. 문의 `document()`도 되돌리기 기록을 지우거나 잠금 파일을 만들지 않는다(design 2.2b). team-kit 목록 조회·값 찾기도 읽기만 한다.
- NFR-HC-03: Synology Drive Client 자료는 읽기 전용으로 열고(SQLite `mode=ro`), 없거나 형식이 다르면 조용히 "못 찾음"으로 넘어간다.
