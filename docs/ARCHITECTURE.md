# hejo 근간 설계: 사장 · 직원 · 공항

hejo 저장소의 모든 기획·설계·구현·검토가 따르는 현장 원본이다. 다른 문서는 이 문서를 복사하지 않고 링크한다.

- 결정: 2026-11-13~14 브레인스토밍([brainstorm.md](changes/HEJO-FOUNDATION-20261114/brainstorm.md)). 상태: 승인(2026-11-14 사용자, HEJO-FOUNDATION 계획과 함께).
- 운영자의 비공개 운영 저장소(`<운영 저장소>`)의 근간(`<운영 저장소>/docs/ARCHITECTURE.md`)과 같은 비유를 쓴다. 이 문서는 hejo 키트가 놓이는 자리만 정한다.

## 1. 완성 상태

**사장이 hejo 앱 하나로 자기 공항(Hermes)의 직원과 대화하고, 직원을 만들고 키우고 관리한다. hejo 저장소 자체가 공개판이며 개인값은 각 공항의 금고·지시서에만 있다.**

## 2. 핵심 단어

> 사장이 직원을 고용해 가이드북을 읽히고 도구를 쥐여 주며 사장 규칙을 지키게 한다.

| 단어 | 정의 | 원본 칸 |
|---|---|---|
| 사장 계정 | 공항 금고 안의 계정. 새 기기 등록에만 로그인(아이디·비밀번호, 구글), 평소는 기기 출입증, 위험한 일은 Touch ID 재확인 | 사장 금고 |
| AI 연결 | 공항당 Claude 1 + Codex 1 구독. 로그인은 공식 도구, hejo는 상태·계정·사용량만 표시 | 사장 금고(공식 도구 저장) |
| 직원 | 직무 없는 빈 사람 + 성격 | 직원 명부·직원 성격 |
| 두뇌 | 모델+추론. 가이드북 > 직원 > 공항. 가이드북 두뇌는 시간표 일에만 | 직원 카드·가이드북·지시서 |
| 가이드북 | 일하는 방식 + 이럴 땐 이렇게 + 필요한 도구 + 시간표(= 직책 명세서) | 기본 선반 / 내 선반 |
| 도구 | 행동. 필요한 능력·안전 수준만 선언 | 기본 선반 / 내 선반 |
| 세트 | 성격+가이드북+도구+두뇌 틀 | 기본 선반 / 내 선반 |

직무는 저장하지 않는다(가진 가이드북이 직무). `SOUL.md`·설정은 조립 결과다(공통 → 성격 → 가이드북, 매번 바뀌는 글 제외).

## 3. 칸 표

`<HOME>`은 그 공항의 Hermes 홈(`HERMES_HOME`, 기본 `~/.hermes`)이다. 코드는 경로를 박지 않고 찾는다.

| 칸 | 원본 위치 | 둘 것 | 두지 않을 것 | 쓰기 주체 | 수명 |
|---|---|---|---|---|---|
| 공항 시설 · 탑승교(hejo 문) | `gate/` (설치하면 `<HOME>/plugins/hejo`로 연결) | 플랫폼 어댑터, 출입증 검사, 앱 연결·분배, 이력·첨부 제공, 서버 안 직원 전용 전송 입구 | 직원 이름·id, 계정, 주소, 포트 외 개인값 | 개발 | 갱신 때 교체 |
| 공항 시설 · 안내판(통신 규격) | `schemas/` | 앱↔문 프레임 규격, 서버 안 전송 규격(`hejo-local-v1.json`) | 구현 세부, 개인값 | 개발 | 갱신 때 교체 |
| 기본 선반(키트) | `kit/` | 기본 가이드북·도구·세트 예시 | 개인값, 특정 가게 업무 | 개발 | 갱신 때 교체 |
| 관제 화면(hejo 앱) | `app/` | AppKit 앱. Mac별 화면 설정(창 크기·펫 위치·마지막 seq)은 `~/Library/Application Support/hejo/hejo-local.json`, 기록장 조회용 캐시는 같은 폴더 `cache/`(지워도 재동기화). 회원 전체에 맞추는 읽음·배치는 허브 회원 상태(아래 허브 행) | 직원 목록·버튼 규칙 사본, 토큰 평문, 홈 경로 상수 | 앱은 개발, 화면 설정은 사장 | 앱은 갱신 때 교체 |
| 정비 격납고 | `install/`, `scripts/`; 설치 영수증 `<HOME>/hejo/install-receipt.json` | 설치 도우미, 개인값 검사, 빌드·시험, 설치 전 상태 기록 | 제품 기능, 비밀 파일 읽기·쓰기 | 운영자 / 설치 도우미 | 코드는 갱신 때 교체, 영수증은 제거 뒤에도 표시만 바꿔 남김 |
| 허브(hejo 서버, 18판 추가) | `hub/`(Mac 한 대에 하나, 회원마다 자기 공항 연결); 자료는 허브 자료 폴더 | 회원 계정(비밀번호 해시·Google 연결), 기기 출입증, 회원 설정(펫 이름 등 16 KiB), 회원 상태(읽음·종·확인·체크·화면 배치, 항목별 최신 승리) | 대화 글·첨부(회원의 문 기록장), 직원 정의 | 허브(회원 요청) | 회원이 있는 동안. 갱신·제거가 건드리지 않음 |
| 사장 금고 | `<HOME>/hejo/`(0600 파일), 각 홈 `.env`, 앱은 키체인 | 기기 출입증 해시, 페어링 코드, 문 포트·주소, 디스코드 짝 정보(서버·사장 계정·짝 표지)와 짝짓기 코드 해시(`discord.json`), (이후) 사장 계정 | 규칙·결정 | 사장 / 문(발급·취소) | 영구. 갱신·제거가 건드리지 않음 |
| 사장 지시서 | `<HOME>/owner/policy.yaml`, `<HOME>/config.yaml` | 보고 전송 플랫폼(`delivery.platform`), 받을 곳 규칙, 공항 기본 두뇌, 캐시 정책 | 값(금고로) | 사장 | 영구 |
| 사장 공방(내 선반) | `<HOME>/owner/workshop/` | 사장이 만든 가이드북·도구 상자·세트 | 기본 선반 복사 이외의 시설 코드 | 사장(앱·Paseo 공방) | 영구 |
| 직원 명부·성격 | 조립 층 원래 자리(`owner/team.yaml`, `soul/personas/`), 직원 사진은 각 프로필 홈 `assets/avatar.png`, 색은 `profile.yaml` `ui_meta.hermes-bots.color`(18판) | 이름·별칭·장착 목록·성격·사진·색 | 값, 규칙 | 사장(앱 경유) | 영구 |
| 직원 사물함 | 각 홈의 sessions·`state.db`, 마감 장부 `state/deadline-watch.json` | 대화 원본, 기억, 마감 항목 | 정의·규칙 | 직원·런타임. 마감 닫기만 사장도 한다(앱 우클릭 → 문 → team-kit `hermes-deadlines close`, 행동 기록 남김, [HEJO-DEADLINE-CLOSE](changes/HEJO-DEADLINE-CLOSE-20261122/spec.md)) | 영구 |
| 공용 창고 | `<HOME>/shared/` | 앱 대화 기록장(`shared/hejo/journal`), 첨부(`shared/hejo/files`), 행동 기록, 디스코드 켜짐·방↔포럼 채널 대응표·보낸 글 대응표(`shared/hejo/discord`, 금고 밖에서는 서버 id 대신 짝 표지), 단체방 기록, 사장 프로필(이름 `shared/hejo/owner.json`, 사진 `shared/hejo/pictures/owner.png`, [현재 명세](spec/current/hejo-owner-profile.md)) | 한 직원 전용 상태 | 시설 런타임(문 단독 쓰기) | 영구. 삭제는 사장이 따로 |

**칸이 아닌 것(조립 결과).** 각 홈의 `config.yaml` 중 조립 대상 부분, `SOUL.md`, 조립된 `skills/`, `cron/jobs.json`은 조립 결과다. hejo가 직접 고치지 않고 원본 칸에 쓴 뒤 조립기를 돌린다.

## 4. 문(탑승교)의 구조

- 문은 Hermes 플랫폼 플러그인(`kind: platform`, 이름 `hejo`)이다. Hermes 본체를 고치지 않는다.
- 멀티플렉스 게이트웨이에서 리스너(포트 하나)는 **기본 프로필 어댑터만** 소유한다. 다른 프로필 어댑터는 어떤 경우에도 포트를 묶지 않는다. 다른 프로필 어댑터의 역할(비활성 또는 같은 프로세스 문으로 넘기는 전달자)은 작업 명세가 정한다.
- 앱이 보낸 글은 대상 직원 id를 `source.profile`에 찍어 그 직원 홈에서 처리한다(`hermes-agent/gateway/platforms/webhook.py`의 선례). 답장은 `metadata.hermes_profile`로 직원을 구분해 앱에 보낸다.
- 직원별 1:1 대화는 `chat_type: dm`, `chat_id` = 직원 id, `thread_id` = 앱이 만든 스레드 id다. 방 대상 전송은 `hejo:room:<방 UUID>`를 사용하며 글쓴이는 보낸 직원이다. 직원 표시가 없는 기본 프로필의 글은 기본 프로필 자신이 쓰고, 방 대표로 바꾸지 않는다. 글쓴이는 방 구성원이어야 한다.
- 방의 사장 글을 받을 직원은 멘션 → 스레드 주인 → 방 대표 순으로 정한다. 주인은 첫 직원 글의 작성자 또는 첫 사장 글의 수신자이며 현재 명부·구성원에 남아 있어야 한다. 다른 직원을 멘션해도 주인은 바뀌지 않는다. 주인 계산은 기존 기록장을 읽고 별도 주인 장부를 만들지 않는다.
- 서버 안 보고·감시 프로그램은 기본 프로필 문이 여는 Unix 입구로 직원 글을 보낸다. 입구는 같은 기록장·첨부 저장 경로를 쓰며 사장 글을 만들지 않는다. HTTP 계약 원본은 [hejo-local-v1.json](../schemas/hejo-local-v1.json), 사용 안내는 [문 README](../gate/README.md)다. TCP에는 이 입구를 열지 않는다.
- 이관 대상 보고·알림은 team-kit 공통 전송을 거친다. 전송 스위치는 사장 지시서의 `delivery.platform` 하나이며 이를 판정하는 곳은 공통 전송의 `platform()`이다. 받을 곳의 실제 값은 금고에 두고, 다시 보낼 열쇠와 조각별 진행 상태는 각 생산자의 기존 상태에 둔다.
- hejo 사용 중에도 Slack 쓰기를 허용하는 이름은 `vault_backup`과 `slack_session` 두 개다. 전자는 Slack에 남긴 금고 백업 승인 흐름에 한정하고, 후자는 현재 도구 호출이 사장의 Slack 대화임을 확인할 때만 허용한다. 이 예외로 일반 보고·예약·배경 작업의 Slack 쓰기를 열지 않는다. 일 넘기기·프로젝트 허브와 위키 일일 보고·금고 백업 질문 및 승인의 이전은 이번 범위 밖이며 Slack에 남긴다.
- 접속은 루프백과 Tailscale 주소로만 받는다. 인터넷 전체에 열지 않는다.
- 아이메시지(photon)는 hejo를 거치지 않는다. hejo의 텔레그램 문은 HEJO-TELEGRAM-REMOVE에서 없앴다(서버 Hermes 텔레그램도 꺼짐).
- 디스코드는 방의 두 번째 문이다(HEJO-DISCORD). 기록장이 원본이고 디스코드는 보조 창이다. 문은 `register_platform_handler`로 받은 디스코드 봇에 hejo 듣기(`add_listener`) 하나만 붙이고 Hermes 원래 처리기는 감싸지도 바꾸지도 않는다. 원래 처리기는 **닫힘 운영**(Hermes 디스코드 허용 사용자 없음, 봇 글 거부)으로 모든 글을 들이기 단계에서 거부하며, 문은 글마다 같은 판정 함수로 닫힘을 확인하고 열려 있으면 그 글을 맡지 않고 앱에 알린다. 짝지은 서버에서 쓸 수 있는 방마다 포럼 채널 하나를 두고(방은 앱에서만 만들며 채널이 따라간다, 보관·삭제는 `hejo 보관` 분류로 옮김) 포럼 글을 그 방 사장 글(첨부 포함)로 올리며, 모든 방의 직원 남은 글과 앱·다른 창의 사장 글을 그 방 채널의 글 묶음으로 채널 웹후크(직원 이름 표시, 멘션 해제)로 보낸다. 글 묶음이 스레드다. 웹후크 토큰은 문 프로세스 메모리에만 두고, 로그에는 종류 이름만 남긴다. 기록장의 레코드 종류는 늘리지 않는다. 창끼리 직접 주고받지 않는다.

## 5. 원칙

1. 먼저 칸을 정한다. 새 칸·두 번째 원본을 만들지 않는다. 맞는 칸이 없으면 멈추고 보고한다.
2. 코드·시험·키트에 사람 이름, 직원 id, 계정, 주소, 절대 경로를 넣지 않는다. 시험은 가짜 홈을 쓴다.
3. 값은 금고, 규칙은 지시서, 코드는 집행만 한다.
4. 공항은 조립식 한 종류다. 조립 층이 없는 공항에는 키트가 조립 층을 함께 설치한다(공개 전 작업).
5. 있으면 감지해서 쓴다: team-kit(버튼·안내원), Paseo(공방). 없으면 기본 동작.
6. 원격 쓰기(직원 생성·도구 부여·해고)는 출입증 + 재확인이 필요하고 행동 기록을 남긴다.
7. 구독 로그인은 공식 도구로만 한다. hejo는 토큰을 보거나 보관하지 않는다.
8. 연합개발 결정(구현 담당 선택·승인·푸시)은 Paseo 앱에서만 한다. hejo는 의뢰와 읽기 전용 상태만.
9. UI는 AppKit 기본. SwiftUI는 성능 문제가 없는 단순 설정·안내·확인 화면에만 쓰고 작업 문서의 SwiftUI 예외 목록에 이유를 적는다.
10. ddots와 hejo는 다른 앱이다. ddots 코드는 한 번 베껴 오고 이후 따로 관리한다(번들 ID·설정·키체인·업데이트 경로 분리).

## 6. 설치·갱신·제거 때 보존과 삭제

| 동작 | 바꾸는 칸 | 보존하는 칸 |
|---|---|---|
| 설치 | 문 연결, 기본 프로필의 플러그인 켜기, 금고 빈 칸 | 이미 있는 사장 칸 |
| 갱신 | 시설(문·안내판)·기본 선반·앱 | 금고·지시서·공방·명부·성격·사물함·공용 창고 |
| 제거 | 문 연결 해제·플러그인 끄기 | 금고·공방·사물함(사장이 따로 지울 때까지) |

## 7. 단계 경계

1. 1단계(Slack 병행): 문·1:1 대화·예약 보고·답장 버튼 → 계정·기기 → 직원 카드·세트 → 공방·AI 연결 → 펫·구글 로그인.
2. 2단계: 단체방+안내원, ddots 부가 기능, 같은 Mac의 두 번째 사장 공항과 그 노트북, MCP 연결, 직원별 캐시·사용량 그래프.
3. Slack 은퇴: 단체방과 ddots 부가 기능을 hejo에서 매일 쓸 수 있을 때. 현재 이관 대상 보고·알림·고객 대화의 hejo 전환과 방 전송·주인 규칙은 적용됐다. Slack 연결과 위 4절의 남긴 길은 유지한다. 실제 초안·승인 경로의 사용자 확인, 다음 날 잔여 Slack 알림 관찰과 운영 기록이 남아 있어 완전 은퇴로 판정하지 않는다.
4. 3단계: 공개 검토(조립 층 키트 포함, 전체 git 이력 개인값 검사, 라이선스 쪽지, 공식 서명).

## 8. 새 기능 점검표

설계(brainstorm·spec·handoff) 첫 절에 아래 표를 채운다.

```markdown
## 칸·원본·쓰기 주체·수명
| 다루는 것 | 칸 | 원본 위치 | 쓰기 주체 | 수명 |
|---|---|---|---|---|
```

1. 각 부분이 어느 칸인가? 두 번째 원본이 없는가?
2. 쓰기 주체는 누구인가? 시설 코드가 사장 칸을 사장 요청 없이 쓰지 않는가?
3. 갱신·제거 때 누가 보존·삭제하는가?
4. 개인값이 코드·키트·시험에 없는가(개인값 검사 통과)?
5. 다른 사장의 공항에서도 코드 수정 없이 같은 방식으로 동작하는가?

허브의 HTTP는 루프백·Tailscale 경계 안에서만 사용하며, Mac 사이 전송은 Tailscale의 WireGuard 암호화로 보호한다(D56-01).
