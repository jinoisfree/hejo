# HEJO-PERF 수락 시험 명세

원본 요구: [spec](../../docs/changes/60f149af-b64e-4d3a-9e8e-a1c7d4ea1045/spec.md).
상태: v3 수치 확정. TASK-01A 하네스·58단계 동결 및 기준 계측, HP-01/02·렌더 무효화·최종 개선·실제 앱 검증 수락(검증 판정 1~4회). 아래 기대값·예산은 유지하며 app/Tests의 기존 검사 및 실제 앱 증거를 따른다.
모든 자동 시험은 임시 HERMES_HOME·LocalStore와 가짜 명부·기록만 사용한다. 운영 기록·개인값을 fixture로 복사하지 않는다.

## AT-HP-01: 최종 화면 통지

가짜 직원·방·메시지를 구성하고 controller.onChange 횟수와 관측 상태를 수집한다. welcome/roster/message/edit/state/delete/typing/sync_done 및 오류·전용 응답을 시험한다. 변경 프레임의 일반 receive 경로는 반환 전 최종 상태 한 번을 전달한다. 중첩 performUpdates·transaction 밖 notice 변경·열기/닫기 동기 캡처는 기존 ConversationUpdateTests의 기대를 보존한다. 잘못된 입력 뒤 오류 표시와 모델/저장 커서 의미가 기준과 같다.

## AT-HP-02: 반복 도출 제거

동일 방의 카드가 여럿 있는 화면을 갱신하여 sidebar·카드 종·drawer가 같은 알림 결과를 소비하게 한다. 계측을 통해 한 동기 갱신·동일 상태·동일 방의 전체 notices 계산 횟수가 한 번 이하인지 확인한다. 기본 구현의 내용과 순서·배지·종 결과를 비교한다. 계측은 테스트 전용으로 두며 제품에 개인 내용 로그를 추가하지 않는다.

같은 동기 렌더·동일 상태에서 notices 정렬 비교자 및 assessment/originalSeq가 같은 스레드의 timeline을 다시 전수 도출하지 않는지도 계측한다. 상태 변경 시의 폐기·재계산은 허용한다.

## AT-HP-03: 의미와 갱신 경계

기준 빌드/수정 빌드에 같은 프레임·사용자 동작·고정 시각을 순서대로 적용한다. 각 단계에서 글 ID/본문/순서, 선택·초안, 알림 ID/순서/개수, 읽음·종·질문 상태를 비교한다.

제품 수정 전에 기준 커밋의 가짜 입력과 관측 결과를 기준값 fixture로 동결하고 입력·결과 해시와 실행 출처를 남긴다. 수정 구현으로 기준값을 재생성하거나 덮어쓰지 않는다. 동률 정렬 등 계약이 정하지 않은 순서는 정규화 규칙을 먼저 기록한다. 기준 구현의 결함 발견 시 계획 담당에게 보고한다.

- 정상: 글/스트리밍 편집/최종 편집/삭제, 직접방·단체방·홈, 읽음·확인·음소거, 방 보관 및 명부 변경.
- 경계: 빈 기록, 없는/삭제된 방, 중복 프레임, 재연결 replay 종료, 홈 범위 변경, 알림 발생 전·24시간 직전·정각·직후, 명시적 now.
- 실패: 프로토콜/모델 오류, 전송 실패, 부분 처리 뒤 다음 정상 입력. 같은 범위 안 상태 변경 및 다음 refresh에서도 오래된 결과가 남지 않아야 한다.

## AT-HP-04: 성능 및 실제 앱

계획 담당이 TASK-01A 원시 계측을 검토하여 제품 수정 전에 다음 예산을 확정한다. 이는 현재 달성값이나 외부 표준이 아니라, 사용자 요청인 자연스러운 입력·전환을 위해 동기 작업이 수십 초씩 점유하지 않도록 정한 제품 수락 예산이다. 기준 96.703초 입력 대기·434.344초 CPU 작업량에서 작은 비율 개선만으로 통과하지 않게 절대 예산과 상대 개선을 함께 요구한다. 구현자가 기준을 완화할 수 없다.

| 측정 지표 | 수정 빌드 합격선 |
|---|---|
| receive 소요 | 전체 20개 표본 중앙값 ≤0.25초, 최대 ≤0.5초 |
| 입력 큐 대기·방 전환 큐 대기 각각 | 5회 중앙값 ≤0.25초, 최대 ≤0.5초, 음수/누락 불허 |
| 방 전환 동작 | 5회 중앙값 ≤0.25초, 최대 ≤0.5초 |
| 편집 4개 전체 구간 벽시계 및 CPU 시간 각각 | 5회 중앙값 ≤2초, 최대 ≤3초 |
| CPU 작업량 개선 폭 | 동일 완료 구간 CPU 시간 중앙값이 기준 대비 99% 이상 감소 |

기준 CPU 중앙값은 434.34438899999986초이며 비교 원본은 구현 worktree의 `.build/hejo-perf-evidence/measure/performance.json`이다. 작업 완료 구간의 CPU 비율에는 상한을 두지 않는다. 약 100%여도 처리 시간이 짧아질 수 있기 때문이다. CPU 시간은 같은 구간의 user+system 증가량으로 비교한다. receive 구간은 실제 기준 하네스대로 store.append를 포함한다. warm-up 1회 제외·5회 측정, 전체 workload 및 기존 동결 기대값은 그대로 사용한다. 목표 미달 시 값을 완화하거나 입력을 줄이지 않고 병목과 근거를 보고한다.

수정 전 같은 머신·최적화 옵션으로 기준 앱을 준비한다. 가짜 방 8개, 방당 스레드 100개, 스레드당 글 4개에 질문·알림·완료·스트리밍 사례를 섞는다. 규모는 재현용 입력이며 운영 자료량 추정이 아니다. 프레임 순서·시각·열린 화면을 고정하고 warm-up 후 5회 수신/갱신 소요·입력 처리 지연·프로세스 CPU를 기록한다. 수정 빌드는 같은 조건으로 실행하여 중앙값과 범위를 비교한다. 수신→화면 반영 중앙값이 감소하고 연속 수신 중 입력·방 전환 이벤트가 수신 종료 전 처리되어야 한다.

실제 설치 앱은 BuildInfo와 실행 바이너리를 확인하여 수정 전후 증거를 구분한다. 기존 포화 상황에서 CPU·3초 sample을 다시 수집하고 스크롤·입력·방 전환 응답을 관측한다. 실제 메시지는 보내지 않는다. 기존 포화가 남거나 입력·전환이 멎으면 불합격이며 추가 원인을 조사한다. 운영 측정은 사라진 재현 조건으로 합격을 대신하지 않는다. 배포/실사용 검증이 안 되면 미실행으로 보고하고 전체 완료를 선언하지 않는다.

### 렌더 회귀와 보완 관측

기존 semantic 동결은 실제 View가 붙지 않은 모델 관측이다. HP-02/03 추가 시험에서는 View를 붙여 반복 렌더·같은 동기 범위 안 상태 변경·다음 렌더·다른 모델 인스턴스·명시적 now를 검사한다. 날짜/읽음/확인/홈 범위 변경이 오래된 파생값에 가려지지 않아야 한다. 첨부·버튼 표시 및 열기/닫기 캡처 회귀는 관련 기존 시험과 추가 검사를 매핑한다. 직접방 replyButton 결과는 기준과 같고 해당 조건 평가에서 홈 정렬이 일어나지 않아야 한다. 홈 정렬은 기존 날짜·ID 순서를 유지한다.

기준의 직접방 합성 측정만으로 홈·표시된 화면의 반응을 대신하지 않는다. 같은 가짜 3,200개 입력의 홈 화면에도 View를 붙여 입력/전환/수신 지연을 추가 관측하고 위 지연 예산을 적용한다. 홈 추가 측정은 별도 결과 파일로 남기고 동결 기준 출력·직접방 workload를 변경하지 않는다. 실제 설치 앱에서는 검증된 산출물 확인 뒤 입력·스크롤·방 전환을 반복 관측하고 CPU·sample을 함께 남긴다. 실제 메시지는 전송하지 않으며, 측정할 수 없는 화면 응답이나 실제 수신 빈도를 확인한 것처럼 보고하지 않는다.
