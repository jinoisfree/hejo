- 판: 3판(spec 3판과 짝, 검증 2차 V-1 반영: 출시 경로 확인 요청 소실을 재현 대상으로 바로잡음) · 상태: 명세 확정 / 코드 2판 기준 작성(미커밋, 3판 기대값으로 갱신 필요) / 2판 기준본 실행 완료 / 독립 검토: 계획 검증 2회차 APPROVED(2판), 3판은 이 검증 담당이 고침([plan-review.md](../../docs/changes/HEJO-ALERT-SEEN-20261125/plan-review.md))

- **앱 시험의 관측 환경:** 출시 경로인 기록 나눠 받기 모드에서 관측한다(`app/Tests/HistoryTransportHarness.swift` + `gate/tests/history_transport_app.py` 같은 실제 HTTP 대역 문). 관측값은 (1) 문이 받은 읽음 요청(action·room·thread), (2) 그 뒤 문의 허브 상태 `bell:`·`thread:` 키, (3) 컨트롤러의 가운데 창 스냅숏(`drawerSnapshot`)에 그 카드가 있는지다. 레거시 참조 모드 시험(`app/scripts/test.sh`)의 기존 AT-TD-39·AT-UC-17·AT77은 회귀로 함께 통과해야 한다.
- 증거 수준: 공통 5절 2(대역 통합). 실제 서버·설치 앱 확인은 릴리스 작업.
- **기준본 실행(F1):** 모든 시험을 제품 코드를 고치기 전에 착수 커밋 위에 먼저 작성해 실행하고, 아래 "기준본 기대" 열과 맞는지 로그로 남긴다. **보존**은 기준본에서 이미 통과해야 하는 시험이다(실패하면 시험이 틀렸거나 현황이 설계와 다르므로 제품을 고치지 말고 멈추고 보고). **재현**은 기준본에서 실패해야 하는 시험이다(통과하면 재현이 안 된 것이므로 멈추고 보고). 수정본에서는 모두 통과해야 한다.
- 각 선택은 그 동작 직후 조정자 작업이 끝날 때까지 기다린 뒤 관측한다. 읽음 요청 관측은 action별로 센다(`thread`와 `notice`는 서로 다른 요청).
