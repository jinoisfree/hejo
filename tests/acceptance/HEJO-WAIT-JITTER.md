# HEJO-WAIT-JITTER 수락 시험 (5판, 2026-11-25, 계획 검증 4회차 반영)

명세: `docs/changes/HEJO-WAIT-JITTER-20261125/spec.md`(용어 "내용 변화 사건·구간·목표 위치·되튐·실물 왕복"은 거기가 원본). 상태: 명세 확정 / 코드 미작성(구현 담당이 `app/Tests/`의 AppKit 하네스로 옮김) / 실행 전 / 독립 검토는 계획 검증.

## 공통 장치
- 실제 `NativeThreadList`를 창에 붙이고(`ScrollTests.swift`의 AT91 방식) `clock`·`automaticallyTicks`·`reduceMotion`을 주입한다. 지연 예약까지 실제로 돌도록 런루프를 1/60초 단위로 진행시키며 매 단계 `contentView.bounds.minY`를 기록한다. 카드는 가짜 이름·가짜 본문만 쓴다.
- **목표 위치 기록**: 같은 하네스 입력을 기준 커밋(handoff 0절 base_commit)의 `NativeThreadList`에 넣되, 각 구간마다 그 구간의 입력 상태에서 갱신을 한 번만 적용하고 리더 입력 없이 0.5초 정착시킨 원점을 잰다. 기준 커밋에서 먼저 실행해 로그(`.build/wait-jitter/targets-*.log`)로 남기고, 수정 뒤 시험은 이 로그 값을 기대값으로 읽는다. 수정본 코드로 기대값을 다시 만들지 않는다.
- **되튐 판정**: 구간마다 1/60초 표본의 |원점−목표|가 직전 최소값보다 0.5pt 넘게 커지면 되튐 1회.
- **반전 판정**: 같은 구간 1/60초 표본에서 이동 방향이 바뀌고 반대 이동이 0.5pt를 넘으면 반전 1회. AT-WJ-01~04는 되튐과 반전을 모두 0으로 요구한다.
- 사건 시각은 고정 순서 표에 적어 실행마다 같게 한다(무작위 없음).

## 거짓 통과·거짓 실패 방지
- 거짓 실패 방지: 독립된 두 사건(줄 추가·제거)은 서로 다른 구간이라 정당한 반대 방향 이동이 되튐으로 세지지 않는다.
- 거짓 통과 방지: 기준 커밋에서 AT-WJ-01~07을 먼저 실행해 결과(통과·실패 수치)를 남긴다. 실물 분석은 사용자 원본 영상에서 왕복을 1회 이상 잡아야 유효하다(양성 대조). 기준 커밋에서 하네스가 되튐을 재현하지 못하면 그 사실과 함께 멈추고 보고한다(하네스가 결함을 못 잡는다는 뜻).
